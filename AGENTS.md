
# Liftsmith: guide for agents

Liftsmith is an Android-first adaptive strength training app. It plans each workout from the lifter's equipment, recovery and training block, then gets out of the way while they lift. This file holds the rules that apply to every change. The decisions about each feature, and why, are in one file per topic under `docs/decisions/` (listed under "Decision record" below), so threads working on different features don't edit the same file (Melvin, 2026-11-09). Follow them. Before working on a feature, read its topic file. If a task seems to need a decision changed, raise it with the owner (Melvin) first, and when a decision changes, update its file in the same change. A new topic gets a new file and one line in the list below.

The full plan with stages lives in the plan doc: https://claude.ai/artifact/S24kx43ZkQ8g3gGtGew34n

node scripts/e2e-devices.mjs # layout on 13 phones and tablets (DEVICES=ios|android|full|names)
DEVICE='iPhone 16' node scripts/e2e.mjs  # the playthrough on another device
node scripts/e2e-a11y.mjs    # axe WCAG 2.2 AA on every screen

There is no Android SDK in cloud sessions; APKs and AABs build in GitHub Actions (`.github/workflows/android.yml`).

## Platform parity (rule, Melvin, 2026-11-09)

- **Every feature goes in both apps, plus the web app wherever it makes sense** (Melvin, 2026-11-09). Each feature lands on Android and iOS in the same change: native Android code (Java or Kotlin in `android/`) and native iOS code (Swift in `ios/`) for anything the web layer can't do. The web app (`/app/`) gets it too when the browser can do it (for example, `.ics` files instead of calendar access, and manifest shortcuts instead of widgets).
- **One-platform features are allowed when they're very useful** (Melvin, 2026-11-09). If a feature is very useful on one platform but the other ecosystem can't support it, build it anyway. Record the gap in [Platform deltas](docs/decisions/platform-deltas.md), and in the pull request description, say what each platform does instead.
- Platform equivalents: Health Connect ↔ HealthKit (Apple Health); foreground-service notification ↔ Live Activity (lock screen and Dynamic Island); Play Billing ↔ StoreKit; Sign in with Google ↔ Sign in with Apple (both offered on iOS); Wear OS ↔ Apple Watch.
- CI builds both apps together (`android` and `ios` jobs in `ci.yml`) whenever a pull request or a push to `staging` or `main` touches native code, Capacitor or dependencies, and `release.yml` builds both on every promotion. Both always run or skip together.
- **Live workout notification today:** Android runs a foreground service (`WorkoutService.java`) with an ongoing notification: lock-screen rest countdown (redrawn once a second), next set and plates, heart rate, workout progress bar, and Log set / +30 s buttons; when rest ends the same card says "Rest over" (no second notification) while the service sounds and buzzes. On Android 16 it's promoted as a **Live Update** (status bar chip with the rest time left or the set, "2/4"; Samsung's Now Bar on One UI 8); while resting it says the time left in its text and chip and shows a rest bar, redrawn once a second during rest only, details in [Workout screen](docs/decisions/workout-screen.md). iOS (`WorkoutSessionPlugin.swift`) runs a **Live Activity** (lock screen and Dynamic Island: rest countdown or the set, next set and plates, heart rate, a rest bar while resting and the workout progress bar otherwise, Log set / +30 s links; drawn by the `LiftsmithWidgets` extension) and schedules a time-sensitive rest-over notification with the same two buttons. Heart-rate-only changes reach the Live Activity at most every 15 s, because iOS budgets updates. **Log set and +30 s work with the app closed:** the tap is kept with its time and logged when the app opens, and the notification or Live Activity steps through the next sets the app sent ahead (`ahead`, `workout/sessionAhead.ts`; [Workout screen](docs/decisions/workout-screen.md)). Both are driven by the same `WorkoutSession` calls in `src/lib/sessionNotify.ts`, which also send the workout to the **watch apps** (Wear OS module `android/wear`, Apple Watch target `LiftsmithWatch`): set, weight and reps or the rest countdown, heart rate from the watch's sensor, and Log set / +30 s, and to the **Garmin watch app** (Connect IQ, `garmin/`, through `GarminLink` on both phones) ([Watch apps](docs/decisions/watch-apps.md)). The **set timer** for holds, carries and cardio rides along as wall-clock phases (`timer`), so the notification, Live Activity and watches count it down on their own ([Set timer](docs/decisions/set-timer.md)).
- Native code registered by the app: Android `MainActivity.registerPlugin`, iOS `MainViewController.capacitorDidLoad` (Capacitor 8 with SPM doesn't auto-register app-target plugins). `InstallInfo` (device and install source for analytics) is registered on both.
- Native apps open straight into the app (`server.appStartPath: /app/index.html`); the landing page is for the website.

## Features page (rule, Melvin, 2026-11-12)

- **The website's `/features/` lists every feature, a compatibility table of every connection and the newest features, and stays current** (Melvin, 2026-11-12: "keep it up to date with all new features"). It comes from one file, `src/content/features.ts`, and is in all six site languages (the other languages' words in `src/locales/site/features/<lang>.ts`, same ids). A change that adds, removes or renames a feature a lifter would notice, moves one between Free, Pro and Labs, or adds a connection, device or platform updates that file in the same change (a new feature with today's `added` day, which puts it under Newest, and its words in all six languages). ## Product rules (apply to every screen)

### Action over stats (rule, Melvin, 2026-11-09)
- **We don't show stats for the sake of stats or pretty graphs. We prioritise action-oriented recommendations.** Every screen should answer "what should I do?" before "what happened?". A new chart or number needs a reason the lifter would act on it; if it has none, leave it out or turn it into a recommendation.
- **Every recommendation says why, in a short line.** Each recommended workout, exercise, set count, rep target and weight carries a plain-words reason built from the same data that produced it: readiness low or high (and the signals behind it), a deload, a plateau, missed or hit reps, feedback, the lifter's own settings, recovery and weekly sets left. Code: `src/lib/why.ts` (`itemWhy` for each planned exercise on Today, `workoutWhy` under the target during a set, `callWhy` for the push / as planned / easy call) and the notes on targets in `progression.ts`. A new recommendation lands with its reason in the same change. Reasons are shown, never behind a tap, and never add a tap during a set.
- **Proactive insights ("Coach's notes").** `src/lib/insights.ts` looks for things worth acting on and says what we saw, the numbers behind it, and one thing to do, ideally a one-tap action: fatigue building (missed reps three workouts running, offer a deload), stalled lifts (no new best in 3+ weeks; several at once offers a deload), a big muscle short of its weekly sets for two weeks (offer to make it a priority), body fat creeping up (advice for the goal), weight dropping faster than 1% a week, the weekly goal at risk (offer a 30-minute workout), the last hard week of a block, what's working (a lift up 5%+ in six weeks), and food from a food app through Health Connect or Apple Health (protein short three logged days running, eating too little to build muscle, a very big deficit; no food logging in the app, see [Food from Health](docs/decisions/food-from-health.md)). Lifters in a Pro trial get its notes first: halfway, the last two days and two weeks after it lapses, each with what Pro did for them (adaptive workouts, weights raised, days adjusted; `trialNotes.ts`, [Money](docs/decisions/money.md) "The first two weeks"). Lifters in Friends also get up to two friend notes (a friend challenge slipping away, a friend pulling ahead while they're short of their weekly goal, a friend gone quiet; `friendNotes.ts`, [Friends](docs/decisions/friends.md)). They show on Today (top two) and at the top of Progress ("What to do next"). Nothing is shown when nothing needs doing. "Got it" hides a note on the device until the finding changes (its id changes). Derived from events every time, never stored.
- **Actions:** `store.startDeload()` makes the current week the deload (the next block starts after it), priorities go through Settings' `togglePriority`, and minutes through `setProfile`.
- **Body fat** is an optional field on body weight events (`bodyFat`, %). Weigh-ins and body fat come in from Health Connect and Apple Health on launch and on return to the app at most every 15 minutes (`healthRefresh.ts`; `readBody` in `health.ts`, one per day, ids `health-bw-<day>` so a re-import is a no-op; HealthKit's fraction is turned into a percentage), which covers smart scales and the Hume Body Pod. Past weigh-ins, body fat and tape measurements can also come from another app's export through Settings › Data's import (`importBody.ts`, [Borrowed from Gradelings](docs/decisions/borrowed-from-gradelings.md) under CSV import). **Manual entry** (Melvin, 2026-11-10): an optional body fat box (`BodyFatField`, a `BumpField` in 0.1 steps from the last reading or 20%, 3 to 60%, with the `bodyFat` glossary "i") sits under the weigh-in on Progress and on Body and photos, and is saved on the same weigh-in; body fat on its own is logged with the last weight. **Tape measurements** (nine sites, `measure` events, cm or inches; 2026-11-11) sit on Body and photos, and a growing or shrinking waist becomes a coach's note when there's no body fat data. Details in [Health twin](docs/decisions/health-twin.md). **Shape the figure like me** (a switch on Body › Health, off by default; 2026-11-12) reshapes Health's 3D figure from height, weight, body fat and tape measurements (`src/lib/bodyShape.ts`), and a client who turns on Share body data for a coach shows that coach the same shaped figure with their numbers ([Trainer mode](docs/decisions/trainer-mode.md)). **Fitness tests** (dead hang, one-leg stand, 30-second chair stand; `fitTest` events; 2026-11-11) sit on Body › Health under Fitness age, each with a timer, a typical range from a published study where one exists, what helps and a goal; [Fitness tests](docs/decisions/fitness-tests.md).
- **Labs** (Melvin, 2026-11-10: "a labs section for experimental features … Labs should be a pro only feature. It's where we put experimental features that aren't quite ready for prime time"). **Settings › Labs** lists experiments, each behind its own feature flag with a switch (`LABS` in `src/lib/labs.ts`, text in `lab.*`). Labs is Pro: `labOn(flag)` is false without Pro whatever the flag says, and free lifters see the Labs row marked Pro (it opens Pro). A switch sets the flag on the device; the admin panel can still turn a lab on for everyone (still Pro only). A lab may need another (`needs`), and shows only once that one is on. Experiments today: camera rep counting (`labRepCount`), phone motion counting (`repMotion`), camera bar speed (`labBarSpeed`, needs camera counting), the heart-rate rest timer (`labHrRest`: rest ends early once the heart rate is back down, never below 60% of the planned rest, [Heart rate and health](docs/decisions/heart-rate-and-health.md)), camera form check (`labFormCheck`, needs camera counting), voice set logging (`labVoiceLog`: say "100 for 8" or "too easy" to log a set, recognized on the device; [Voice set logging](docs/decisions/voice-set-logging.md)), today's max from warm-ups (`labSpeedMax`, needs bar speed: warm-up speeds estimate today's max and nudge the first working weight, against each lifter's own end-of-set speed once three sets to failure have taught it), bar path replay (`labBarPath`, needs camera counting: after a counted squat, hinge or overhead press, the rep worth seeing replays from the pose landmarks with the bar's path and one cue on where it drifted; landmarks only, in memory until the next set), watch rep counting (`labWatchReps`: the Wear OS or Apple Watch app streams wrist motion during a set and the phone counts it, [Watch apps](docs/decisions/watch-apps.md)), hands-free sets (`labHandsFree`: while any rep counter is counting, the set logs itself a few seconds after the last rep, [Camera rep counting](docs/decisions/camera-rep-counting.md)), the tempo coach (`labTempo`: on tempo and paused lifts, Count tempo above Log set counts each rep's lowering, hold and lift in sound and haptics, [Tempo coach](docs/decisions/tempo-coach.md)), the Bluetooth smart scale (`labScale`: a scale sharing the standard Weight Scale or Body Composition Service fills in weight and body fat on the weigh-in for the lifter to log; [Connected apps](docs/decisions/connected-apps.md)), the volume button (`labVolumeLog`, phones only: volume up on the phone or Bluetooth earbuds logs the set and the volume goes back, while the workout is on screen; [Volume button logs a set](docs/decisions/volume-button-logging.md)) and Bluetooth gym machines (`labGymMachines`: bikes, rowers, treadmills and cross trainers sharing the Fitness Machine Service fill in a cardio set's time, distance and average power; native Bluetooth on both phones, Chrome on the web, [Gym machines](docs/decisions/gym-machines.md)) and Sonos (`labSonos`: play, pause, skip and change the volume of a Sonos speaker from the workout screen, and let the music follow the workout, set volume for sets, rest volume for rest, a favourite at the start and a pause at the end; Sonos's cloud Control API through our server, so it needs an account; [Sonos](docs/decisions/sonos.md)). New experimental features land as a lab, and leave Labs (flag and entry removed) when they're ready: trainer mode left on 2026-11-12 and is now the Pro feature `coaching` ([Trainer mode](docs/decisions/trainer-mode.md)). A lab marked `native` shows only in the Android and iOS apps. Pure web code, so Android, iOS and the web app get it together (watch rep counting adds native code on both watches).
- **Free vs Pro** (Melvin, 2026-11-12, after an audit against Fitbod, Hevy, Strong and StrongLifts): every Pro feature is in `PRO_FEATURES` (`entitlements.ts`) and on the paywall. Free keeps the logger, every fixed program (the one a free lifter gets fits their gym, `freeProgramFor`), one adaptive workout a week (`freeAdaptive.ts`), "Short on time", Health Connect and Apple Health, coach's notes and reasons; Pro adds daily adaptive plans and splits, the recovery map, advanced stats, health signals moving the call, working around taken equipment, the cloud connections (Strava, Oura, WHOOP, Withings, Polar, Concept2), Labs, coaching clients (trainer mode; being a client is free), the plateau detective and the goal planner. Details in [Money](docs/decisions/money.md).
- Insights and reasons are free; they explain the plan rather than add to it. Pro features add notes through the same list: a single stalled lift goes to the **plateau detective** (Pro), whose note gives the likely cause and a one-tap three-week fix (`fixPlateau`), then says the fix is running and, after it ends, whether it worked. Without Pro the plain stall note shows instead. Several lifts stalling at once stays a deload note, because that's fatigue. There is one place for stalls: coach's notes (the separate plateau card on Progress was removed).
- The wording lives in the language catalogues (`src/locales`: `why.*`, `ins.*`, `sig.*` for readiness signals, `note.*` for the notes on targets, `fix.*` and `cause.*` for the plateau detective, `explain.*` for the "Why?" sheet), so it follows the app's language. Engine code builds sentences from whole catalogue lines with placeholders, never by gluing English fragments, and never matches on a note's wording (compare against `t("note.push")` and friends).

### Positioning
- **An original app.** It borrows ideas from Fitbod (daily adaptive workouts, equipment matching, recovery map, variability setting) and Gymverse (periodized blocks with RIR and deloads, exercise swaps, lock-screen timer). It never uses their names in the UI, their art, screenshots, exercise videos or exact look. Exercise names, setup text and cues are our own.
- **Focus on the workout, not the app.** One tap logs a set as planned. The next set is always pre-filled. The rest timer starts itself. Anything optional (feedback, swaps, info) appears between sets and never adds a tap during a set.
- **One control, one destination** (Melvin, 2026-11-09: "two buttons doing the same thing is not correct"; keep the app as simple and streamlined as possible). On any one screen, a sheet, page or dialog has exactly one control that opens it. Before adding a button, check nothing on the screen (the tab bar included) already goes there; if a bigger area should be tappable, make that area the one button rather than adding a second. A glossary `Info` "i" never sits beside a button or sheet that explains the same thing. Cleaned up on 2026-11-09: the workout screen's info icon and the separate demo tap (the demo card is now the one "How to ›" button), Settings' "Achievements and locker" button (the Awards tab is always on screen there), and the "i" next to fitness age (its "How is this worked out?" sheet explains it). Links from one screen to another screen (Progress › All tools and Settings › Tools, say) are fine: they're different screens.
- **Explain every label that isn't obvious** (Melvin, 2026-11-09). Jargon and training terms (deload, build weeks, RIR, readiness, today's call, volume, estimated one-rep max, sets per muscle, exercise variety, recovery, warm-ups) get the one shared `Info` button (`src/components/Info.tsx`): a small "i" with a 44 px tap target that opens a short plain-language dialog. The text lives in the language catalogues (`gloss.<term>.title` and `gloss.<term>.body`, one paragraph per line); `src/lib/glossary.ts` lists the terms and reads them. `Section` takes an `info` term. Any new label a lifter might not understand gets a glossary entry in the same change.
- **Dark, trustworthy, professional.** Deep navy-black background, one blue brand accent (`#4c8dff`, one CSS variable so cosmetics can recolour it), green, amber and red reserved for status (recovery bands, warnings). Large touch targets, tabular numbers, system font (Roboto on Android).
- **Light mode** (Melvin, 2026-11-09). **Settings › Look and feel › Appearance: Dark (default), Light, or Match system.** It sets `data-theme` on `<html>` (`src/lib/theme.ts`), saved on the profile and in localStorage so the next launch paints the right theme before the profile loads; it also sets the browser bar colour and the native status bar style. **Every colour is a token** in `globals.css` with one dark and one light value, including badge tiers, crate rarities and heart rate zones (`--tier-*`, `--rarity-*`, `--hr-*`); never hard-code a hex in a component. The light accent is a darker blue (`#1d4fc4`) so text passes contrast, and an equipped accent cosmetic is darkened on light screens (`applyAccent`). The design pass's effects (primary gradient and its ink, screen glow, card sheen and shadow) are variables too (`--grad-*`, `--btn-ink`, `--glow-*`, `--sheen*`, `--shadow`); the light primary button is a deeper blue-to-violet with white ink. Earned themes (`themes.ts`) are dark palettes: on a light screen only their accent carries over, darkened, and the light surfaces stay. Order: Appearance, then the earned theme, then an equipped cosmetic accent. `src/lib/appearance.ts` is Appearance; `src/lib/themes.ts` is earned themes. The axe run checks the main screens in both themes. The share image stays dark.

### Visual design system (Melvin, 2026-11-09: "liven it up, but keep it simple and professional")
- **Tokens live in `src/app/globals.css`.** Brand blue plus four supporting hues used only as tints for marks, chips and card glows, never for body text: violet `#a78bfa` (levels, Pro, quotes), cyan `#38d6e8` (rest, time), ember `#ff8a3d` (streaks, challenges), mint `#34d399` (done). Status colours keep their meaning. Named roles are in `src/components/app/theme.ts`: muscle families (push blue, pull cyan, legs violet, core ember) and the readiness call, like a traffic light, with its own tokens (`--call-*`, `--feel-*`): Go easy and Low amber, As planned and Okay blue, Push and Great green, Sore red, Unwell violet ([Today screen](docs/decisions/today-screen.md)).
- **The primary action is a blue-to-violet gradient with dark ink** (`.btn-primary`, 7:1+ contrast). One primary per screen. Cards are raised glass (`.card`, hairline border and a faint top light); `.card-tint` with `--tint` gives a card a hue for the hero card on each screen. A soft light sits at the top of every screen (`.aurora`).
- **Type:** big numbers use `.display` (tabular, 800). **Titles look the same on every screen** (Melvin, 2026-11-11: "ensure titles are styled nicely and uniformly"; the Progress title is the model). The classes live in one place, `src/components/titles.ts`: `SCREEN_TITLE` (1.75rem, extra-bold, tight), `SECTION_LABEL` (small caps in the muted ink, with an optional icon), `SHEET_TITLE` and `CARD_TITLE`. Every screen's h1 goes through **`ScreenHeader`** (`ui.tsx`: optional "‹ Back" link, optional kicker line, the title and an optional glossary "i"), section labels through `Section`, and sheet titles through `Sheet`. Never write a heading's size and weight by hand; the setup wizard and the in-workout exercise name use `SCREEN_TITLE` directly. Only the welcome splash and the end-of-workout headline are bigger, on purpose.
- **Icons:** one hand-drawn stroke set (`src/components/app/icons.tsx`, 24-unit grid, 2 px). No emoji in app chrome.
- **Empty states** use `EmptyState` (icon in a tinted tile, a title, one line of help, and an action when there's an obvious next step). No bare "nothing here" lines.
- **Mascot** (Melvin asked for "juicier", 2026-11-09): an original, friendly kettlebell (`Mascot.tsx`), drawn in the brand gradient so it follows the theme and light mode, with four moods (happy, sleepy, cheer, curious), a slow bob and a blink. It appears only where the app is otherwise quiet: the first setup step, a few empty states (`EmptyState mascot=`: rest day, no workout running, no workouts yet, no routines), the end of a workout, and Today once the day's workout is done. Never on the workout screen during a set, always `aria-hidden`, and still in Lean mode.
- **Motion:** short and purposeful (`rise`, `pop`, `fade`, `nudge` on a changed number, `burst` from Log set, `beat` on the live heart rate, `spring-in` for empty states, `stagger` for Today's exercise list). **Springs:** `--ease-bounce` is a real spring (CSS `linear()`, overshoot then settle) with a back-ease fallback. `.press` squashes instantly (70 ms) and springs back on release; the primary button squashes and stretches (`scale(1.02, 0.9)`), cards dip less. iOS shows `:active` only with a touch listener, so `App.tsx` adds one. **Bursts** (`burst.ts`): particles in the token colours plus an optional checkmark, from what the lifter touched (Log set, a crate), under a second, never blocking a tap. Nothing moves during a set except what the lifter touched. `prefers-reduced-motion` and **Lean mode** (`profile.lean`, Settings) both cut motion, bursts and confetti (`.calm` on `<html>`, `calm()` in `juice.ts`).
- **Sound set:** every sound is one synthesized voice (a soft glassy mallet) in A major pentatonic (`juice.ts`), so sounds never clash: a near-silent tick for steppers, chips and the length slider, a soft rising or falling pair for a switch on or off, a rising pair for Log set, a phrase for Start, a three-note chime for rest over, a falling pair for discard, a bright run for a goal or quest done, a low soft pair for an error, and a longer phrase for the end of a workout. No sound on navigation. One **Sounds** switch (`profile.restSounds`) covers them all.
- **Haptics** go through `@capacitor/haptics` on both Android and iOS, falling back to `navigator.vibrate` on the web. The vocabulary (`HapticKind`): `select` (light tick) for steppers, sliders, chips and tabs; `tick` for buttons; `toggle` (medium) for switches; `tap` (medium) for Log set; `thud` (heavy) at rest end; `double` (a crisp double tap) and `celebrate` (double tap then success) for PRs, level-ups and achievements; `success`, `warning` and `error` notifications. `oops()` pairs the error haptic with the error sound for any failure. **Vibration** can be turned off in Settings (`profile.haptics`).
- **On/off settings are switches** (`Switch`, `SwitchRow` in `ui.tsx`, `role="switch"`), not On/Off chip pairs or checkboxes: one tap, one thumb. Inside a card or sheet, `InlineSwitch` (words, then the switch). A checkbox is only for agreeing to something ("I understand the risks"). The knob springs across and stretches while pressed.
- **Safe areas and the tab bar** (Melvin, 2026-11-10: "the bottom navigation cuts off the main content"). Android 15+ draws edge to edge and iOS always does, so the status bar and the phone's gesture or three-button bar sit over the page. The tab bar (`TabBar` in `App.tsx`) measures its own height, safe area included, into `--nav-h`; `main` pads by it (`.clear-nav`) and Today's Start button sits at `bottom: var(--nav-h)`, so screens don't add their own bottom padding for the bar. `StatusScrim` (`.status-scrim`) covers the status bar so scrolled content doesn't run under the clock. Shared web code, so Android, iOS and the web get it together; `e2e-devices.mjs` checks the end of each tab and Start workout clear the bar with a 48 px bottom safe area.
- **The tab bar has five tabs** (Melvin, 2026-11-12): Today, Body, Progress, Friends, Awards (`TABS` in `App.tsx`). Friends moved there from a small button on Today's header, and **Gyms moved out to Settings › Gyms and equipment** (still one tap away from Today's gym chip), because it's set up once and rarely revisited. Friends shows a dot when something is waiting and hides when the `social` flag is off. Keep it at five: a new tab means demoting one ([Friends](docs/decisions/friends.md)). Shared web code, so Android, iOS and the web get it together.
- **Desktop layout on the web** (Melvin, 2026-11-12: like Hevy's website). On a wide window with a mouse, the web app swaps the tab bar for a sidebar with the same tabs, widens pages and opens sheets as centred dialogs; the workout stays a focused phone-width panel. Phones, tablets and the Android and iOS apps keep the phone layout. Style for it with the `desk:` variant (`data-layout="desktop"`, `src/lib/layout.ts`), never by checking the width; a screen with a layout of its own goes on `WIDE` in `App.tsx`, and `.desk-cols` flows a screen's cards into two columns in the phone's order. On desktop the workout takes keyboard shortcuts (L logs the set), and the routine builder is a wide dialog with the exercise browser open and rows that drag (`Sheet wide`). A new screen should look right at both ([Desktop layout](docs/decisions/desktop-layout.md)).
- **Loading** shows `TodaySkeleton`, shaped like Today, instead of a spinner; `Skeleton` makes any other shape.
- Before/after screenshots: `node scripts/shots.mjs [base-url] [out-dir]` (after `npm run build:static`).
- **App icon and favicon** (Melvin asked, 2026-11-09: "follow the app's theme"). The mark is an **anvil with a loaded barbell resting on it** ("smith" plus "lift"), an original drawing, in the primary gradient (`--grad-a` to `--grad-c`) on the navy background (`--color-bg`) with the same soft top glow as the screens. It's a solid silhouette so it reads at 16 px and works as a one-colour shape. **One script draws every file** from that one mark, so the platforms can't drift: `node scripts/make-icons.mjs` (Playwright's Chromium, ImageMagick for the `.ico`; set `PW_CHROMIUM=/opt/pw-browsers/chromium` in cloud sessions). It writes:
  - *Web:* `public/icon.svg` (favicon), `favicon.ico` (16/32/48), `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`, `icon-maskable-512.png` (mark inside the 40% safe circle) and `icon-mono.svg`, all listed in `manifest.ts` and `layout.tsx`.

### Accessibility (Melvin, 2026-11-09: "accessibility checks, WCAG guidelines, colour blind support")
- **Target: WCAG 2.2 AA everywhere**, checked in CI. `scripts/e2e-a11y.mjs` runs axe on every screen in dark and light, again with colour-blind safe colours and more contrast, once under forced colours, then a **keyboard-only run** at the **largest text on a 360 px phone**: every Tab stop shows a focus ring, a workout starts and a set logs without a pointer, sheets take focus, keep Tab inside and close on Escape with focus returned, and no screen scrolls sideways. `src/lib/a11y.test.ts` checks the colour tokens: status colours 4.5:1 as text, recovery colours 3:1 against cards, and both colour sets simulated for protanopia, deuteranopia and tritanopia (Machado 2009) so they stay apart. Lint runs the full strict `jsx-a11y` rule set.
- **Settings › Look and feel › Accessibility** (`src/lib/a11y.ts`, saved as `profile.a11y` and in localStorage so the first paint is right):
  - *Text size:* Match my phone (default), Default, Large, Larger, Largest (100 to 150%). It scales the root font size; **every font size is in rem** (no `text-[Npx]`), so all text follows. On Android and iOS, Match my phone reads the phone's own size (font scale, Dynamic Type) through `@capacitor/text-zoom` and pins the WebView's own zoom at 100%, one path on both platforms. Layouts wrap rather than scroll sideways at the largest size.

Status and recovery colours are tokens with `-std` and `-cvd` values per theme (`--band-*`, `--good-*`, `--warn-*`, `--bad-*`), picked by `data-cvd` on `<html>`. Heart rate zone colours already pass the simulation and stay as they are.

  - Motion: Lean mode (a switch in the same section) and the phone's reduce motion setting.
- **Colour is never the only cue (WCAG 1.4.1):** the recovery map and its legend add dots (Recovering) and stripes (Fatigued); picked chips show a tick; every band also has a label and a percentage.
- **Sheets always show how to close them** (Melvin, 2026-11-09): every `Sheet` (`ui.tsx`) has a ✕ Close button in its header (44 px) and closes when swiped down (from the handle, or anywhere while scrolled to the top; 96 px, or a quick flick of 40 px+) or dragged down with a mouse or pen from the handle or the title row (content stays selectable; Melvin, 2026-11-11: "cursor or finger"), as well as by tapping outside and Escape. The whole sheet follows the finger while dragged and the backdrop lightens with it (the sheet's rise-in animation is cleared first, because a filling animation overrides an inline transform; 2026-11-10). A short pull springs back. Drags that start on a 3D figure, a slider or `[data-no-swipe]` belong to that control, and sideways or upward drags are left alone. Pure web code, so Android, iOS and the web get it together.
- **Back always goes back** (Melvin, 2026-11-10: "pressing the back button on your phone should navigate back to the previous screen"). One rule for the whole app, in `src/lib/back.ts`: back closes the open sheet or dialog first (the newest one), then goes to the previous screen, goes to Today from a screen with nothing behind it (a shortcut or notification), and only on Today leaves the app (Android sends it to the background, so a workout keeps running). Android wires it to the system back button and gesture through `@capacitor/app`; iOS gets a swipe in from the left edge (`allowsBackForwardNavigationGestures` in `MainViewController`); the web uses the browser's back. Every app history entry records how many screens are behind it and which one (`router.ts`), and `go()` to the screen just left steps back instead of pushing, so a screen's own "‹ Settings" link and the phone's back agree. Anything new that should close on back (a sheet, a dialog, a wizard step) calls `useBack(open, close)`; `Sheet`, `Info` and the setup wizard already do. Screens need nothing, so new Settings sub-screens get it for free. **Next.js stays out of these steps** (2026-11-10): a back or forward step that changes only the hash is stopped before Next's own popstate listener (`guardTraversals` in `router.ts`), because Next treats each one as a traversal of its own page and may refetch it, which the Android app's local server can't answer. Steps to another path still go to Next. (The "This page couldn't load" after Today during a workout turned out to be something else: see native listeners under Architecture decisions.) And a screen that fails to draw shows an in-app message with Reload (`ScreenBoundary`, the error goes into feedback diagnostics) instead of Next's dead-end page, with the tab bar still there.
- **Screen readers:** the rest timer is a `timer`; a polite live region says when rest starts, at ten seconds left and when rest is over (not every second). Sheets are modal dialogs labelled by their title.
- **Forced colours** (Windows High Contrast): cards and buttons keep an edge, the focus ring uses `Highlight`, and the recovery map keeps its colours (`.keep-colours`).
- **Quick, one-handed input (Melvin, 2026-11-09: "the less manual typing the better"):** every screen should be fast to adjust in the gym. Prefer steppers with bump buttons, sliders, toggles and chips over text fields, and offer typing only as a fallback. Design for one hand, and respect left- or right-handed use.
  - **Hold to repeat** (Melvin, 2026-11-11: "hold it down for a bit before this happens to avoid accidental touches … speed should start slow and ramp up … haptic and sounds adjusting accordingly"). Every − / + is the one `Bump` in `ui.tsx` (`useHoldRepeat`, timing in `src/lib/holdRepeat.ts`); never hand-roll a − / + button. A tap steps once when the finger lifts, so a scroll that starts on a bump never steps. Held still for 450 ms it starts repeating, slow (200 ms apart) and faster each step down to 60 ms, reached in about two seconds; boxes whose number can jump (`BumpField`, the 1RM inputs) then move 2 steps at a time after 20 repeats and 5 after 40, while the workout's weight and rep bumps stay one plate or rep per step. The tick sound and the `select` haptic come from the bump itself, every step while slow and thinned out at speed (at most every 85 ms and 110 ms), with a `tick` haptic when the step size grows; both follow the Sounds and Vibration switches. A step that changes nothing (a limit) returns `false` and the hold stops. Sliding off (12 px), pointer cancel (a scroll), leaving the button or losing focus stops it. Enter or Space held from the keyboard repeats the same way; a screen reader's click steps once. Used by the workout steppers, every `BumpField`, gym plate counts, the 1RM inputs and routine set counts. Pure web code, so Android, iOS and the web get it together.
  - Numbers a lifter would type use **`BumpField`** (− box +, typing still works): body weight in setup, Settings and the weigh-in on Progress and Body and photos (with body fat under it), age and known lifts in setup, and bar weights in Gyms. An empty box bumps from a sensible start (the last weigh-in, 30 years, a common bar). New number inputs use it too.
  - **One-handed controls** (Settings › Workout, first on the page: Off, Right hand, Left hand; `profile.a11y.hand`): during a workout the weight and rep bumps move down into a dock beside Log set, with Log set under that hand's thumb; the big numbers stay on the set card. Off by default.

## Security (audit, 2026-11-09)

- **Security headers on every website response** (`src/lib/securityHeaders.ts`, added in `next.config.ts` for the server build only; the native shells load files from the device): HSTS (2 years), `nosniff`, `X-Frame-Options: SAMEORIGIN`, `strict-origin-when-cross-origin`, a Permissions-Policy that keeps only the camera (rep counting) and Web Bluetooth (heart rate), and a CSP of `frame-ancestors 'self'; object-src 'none'; base-uri 'self'; form-action 'self'`. Routes with their own stricter policy (the inbox email view) keep it. The one exception is `/embed/<slug>/` (free calculators other sites put on their pages, [Public pages and SEO](docs/decisions/public-pages-and-seo.md)): same headers without `X-Frame-Options`, with `frame-ancestors https: 'self'` (`EMBED_HEADERS`), because they hold no account state or action worth a tricked click. **Script policy** (2026-11-10): the account session token is in localStorage, so injected script must not run. Next writes different inline scripts into every page, so after `npm run build` the `postbuild` step (`scripts/csp.mjs`) hashes each prerendered page's own inline scripts and adds `<meta http-equiv="Content-Security-Policy" content="script-src 'self' 'wasm-unsafe-eval' https://accounts.google.com https://appleid.cdn-apple.com 'sha256-…'">` right after its charset; no `'unsafe-inline'`, no `'unsafe-eval'` (`'wasm-unsafe-eval'` is for rep counting, the two hosts for Sign in with Google and Apple). Pages rendered per request have none, so keep pages static (the one exception is the public share link page, `/w/<id>/`, which is plain HTML with no scripts and its own `default-src 'none'` policy; see [Sharing](docs/decisions/sharing.md)). New inline scripts need nothing extra (they're hashed), but a script from another host must be added to `SCRIPT_SOURCES`. `src/lib/csp.test.ts` checks the script. **The native apps don't carry it** (Platform deltas): on Android WebViews without document-start scripts, Capacitor puts its bridge into the page as an inline script whose hash we can't know, so a policy could stop the app from starting, and the apps only ever load their own files.
- **Creator commission counts only store-verified events** (`source = 'store'`, from the RevenueCat webhook). The app's own `trial_start` and `purchase` events reach `/api/collect/` without authentication, so they may stand in for revenue on the admin panel until the webhook is set, but never for money owed to a creator (`loadCreators`).
- **Rate limits are one atomic statement** (`rateLimit` in `db.ts`: an upsert with `RETURNING count`), so a burst of parallel requests can't all read the same count. **Email sign-in codes count each try before comparing** and are used up with a conditional update, so parallel guesses can't pass the five-try limit. Both have tests that fail on the old read-then-write code.
- Every public route that writes or sends rate-limits through the database, never only in memory (serverless instances don't share memory): feedback per address, `/api/collect/` per install and per address. Secrets in headers (cron, RevenueCat) are compared in constant time (`authorized` in `revenuecat.ts`).
- Rate limits key on the first `x-forwarded-for` address, which Vercel sets itself.
- **This repo is public** (audit, 2026-11-11). Never commit a real code that unlocks anything (a lifetime Pro code, the store review code, a promo code meant to stay private): not in docs, tests, comments or commit messages. Test fixtures use made-up codes. **Lifetime Pro codes are 10+ characters** (`LIFETIME_MIN`, checked by the admin form), because the public code lookup answers without an account. **Admin sign-in links are used up in one statement** (`UPDATE … WHERE used_at IS NULL RETURNING`), so two requests racing with one link can't both get a session.
- **Code and models come from our own origin, never a CDN.** Camera rep counting's MediaPipe runtime and pose model are our own copies under `public/mediapipe/` (runtime copied from the lockfile-pinned package by `scripts/mediapipe.mjs`; model committed and hash-checked by `mediapipe.test.ts`). The only outside scripts are Google's and Apple's sign-in libraries on the website (`accounts.google.com`, `appleid.cdn-apple.com`, loaded only when the lifter taps that sign-in button), because their makers serve them only from there. A new library or model is bundled or self-hosted.
- **The web view's storage stays out of phone backups** (Melvin, 2026-11-10). It holds workouts, health readings, injuries, cycle logs, progress photos and the account session token. Android keeps `allowBackup` on but excludes `app_webview/` (and the WebView's prefs) from Google's cloud backup and from phone-to-phone transfer (`res/xml/data_extraction_rules.xml` for Android 12+, `full_backup_content.xml` for older); iOS marks `Library/WebKit` as excluded from iCloud and computer backups at launch (`AppDelegate.swift`). Signing in and sync, or a backup file, carry the data to a new phone instead. `storePolicy.test.ts` checks both. Anything new the app stores natively that holds personal data gets the same exclusion.

## Architecture decisions

- **Stack copied from Gradelings** (`mjparinas/gradelings`): Next.js 16 static export, React 19, TypeScript, Tailwind 4, Zustand, Vitest.
- **Capacitor, not Bubblewrap (Melvin chose it, 2026-11-09).** A TWA can't run a foreground service, show a live lock-screen countdown, read Health Connect, keep Bluetooth heart rate going with the screen off, or use StoreKit (it has no iOS app). Capacitor wraps the same static export and adds those through native plugins; it also builds the iOS app. The cost is a store release for each app change.
- **Offline-first, like Gradelings.** Everything the lifter does is an event with a unique id (set, session start and end, feedback, swap), appended to IndexedDB first (`localdb.ts`). Stats, PRs, recovery, streaks, XP and progression are recomputed from events, never stored (`derive.ts`), so merging devices is order-independent and duplicate-safe. Profile and gyms are last-write-wins on `updatedAt`.
- **Two builds** (`next.config.ts`): `npm run build` is the Vercel server build with API routes named `route.api.ts`; `npm run build:static` (`STATIC_EXPORT=1`) is the static export for the native shells and CI, and it leaves those routes out. Native apps call the API on `SITE_URL`. **The apps carry only the app, not the website** (2026-11-11): after every `cap copy` or `cap sync`, `scripts/native-web.mjs` deletes everything in the shell's copy of `out/` except `app/`, `_next/`, `mediapipe/`, the icons and the manifest (`KEEP`), which took both apps from about 387 MB of web files to 27 MB. Something new that app screens load by a root path goes on `KEEP` ([App size](docs/decisions/app-size.md)).
- **Sync (built, 2026-11-09):** `POST /api/sync/` (`src/server/sync.ts`, client `src/lib/sync.ts`) pushes this device's new events and deletes and pulls the account's other devices' by cursor, on open, on return to the foreground, when back online, and 4 s after a change. The outbox (`src/lib/syncOutbox.ts`, localStorage) is filled by `localdb.ts` itself, so anything that writes there (the store, a restored backup) is queued; writes that came from sync pass `{ remote: true }` and aren't sent back. Signing in queues every event once. Server: `sync_events` (one row per account and event id, `seq` is the cursor; a delete becomes a tombstone with a new seq that is never undone; a device never gets back what its own session wrote) and `sync_records` (`profile` and `gym:<id>`, last write wins on `updatedAt`; a removed gym is a null record). **On a device's first sync the account's profile wins** over the device's, so signing in on a freshly set-up phone brings the lifter's own settings back; gyms are merged. 500 events per page, 1,000 per push, 3.5 MB per request, 600 syncs an hour per account. **Storage quota per account** (`QUOTA` in `sync.ts`, 2026-11-10): 200,000 events (tombstones included), 50 MB of event bodies and 200 records; a push that would pass it is refused whole with 413 `full`, nothing from it is stored, and the device keeps its data and shows "sync storage is full" (`account.syncFull`). A lifter training five days a week writes about 10,000 events a year, so only abuse reaches it. Everything in the event log syncs, health readings, injuries and cycle logs included (the user's own account only); progress photos never do. A 401 signs the device out and keeps its data.
- **The schema check on a server's first query is one read** (`migrate` in `db.ts`, 2026-11-12): it lists what the database already has and makes only what's missing, in one batch. Each statement is a network hop to Turso, and running all of them one by one made every cold start take about four seconds. Add tables and indexes to `SCHEMA` and columns to `COLUMNS` as before ([Friends](docs/decisions/friends.md) "Loading fast").
- **One static page for the app** with hash routes (`#/today`, `#/workout`, …), so it works offline from one cached page.
- **The active workout** is also kept in `localStorage`, so killing the app mid-set loses nothing.
- **Seeded randomness only** in the generator (`random.ts`), never `Math.random`, so plans are reproducible and testable.
- **Build stamp** (Melvin, 2026-11-11: "a short commit hash somewhere in the app so i know what code has been released"). `next.config.ts` stamps the commit into every build (`NEXT_PUBLIC_COMMIT_SHA`: `COMMIT_SHA`, else Vercel's `VERCEL_GIT_COMMIT_SHA`, else GitHub's `GITHUB_SHA`, else `git rev-parse HEAD`); `src/lib/build.ts` reads it. The Android and iOS apps bundle the web build made in `release.yml`, so they carry that commit with no native code, one path on both. Shown as "Version 0.1.0 (8) · build 3336dee" at the bottom of Settings (the store build number comes from `InstallInfo` on the phones, none on the web), as plain "Build 3336dee" (no link to GitHub, Melvin 2026-11-11) in the site footer and the admin header (`BuildStamp`), and in feedback diagnostics.
- **Native listeners unsubscribe through `unlisten()`** (`src/lib/nativeListen.ts`, 2026-11-11). Our own plugins are reached through `window.Capacitor.Plugins`, where Android's `addListener` returns the handle itself and iOS a promise of it; calling `.then` on Android's handle threw when the workout screen closed, so Today failed to draw after a workout ("This page couldn't load"). Never call `.then` on an `addListener` result directly.
- **Native code** lives in the Android project as small Capacitor plugins (WorkoutSession foreground service; Health Connect; HealthWorkout, the one Kotlin plugin, because Health Connect's client is Kotlin-first), called from `src/lib/sessionNotify.ts` and friends, which fall back to web APIs when not native.

## Code conventions (Melvin asked, 2026-11-09: "easier to maintain and change")
- **Strict TypeScript plus** `noImplicitReturns` and `noFallthroughCasesInSwitch` (`tsconfig.json`). No `any`.
- **The training engine also has `noUncheckedIndexedAccess`** (`tsconfig.engine.json`, `npm run typecheck:engine`, a CI step): reading `list[i]` or `record[key]` there is typed as possibly missing, so an index that can run off the end shows up at compile time. Handle the missing case, or add `!` only where the index is in range by construction (a loop bound, the first item of a group that can't be empty). A new engine file goes in that config's `include` list.
- **Prettier formats every code file** (`prettier.config.mjs`: width 140, imports sorted and grouped: Node, packages, `@/`, relative). Run `npm run format` before committing; CI's Formatting step fails on unformatted code. Docs and data files are left as written (`.prettierignore`). Formatting-only commits go in `.git-blame-ignore-revs`.
- **App state is one Zustand store in slices** (`useApp` from `src/lib/store.ts`, the only import path). Each area's state and actions live in `src/lib/store/<slice>.ts`: `workout` (the workout in progress), `plan` (profile, gyms and Today's plan), `injuries`, `health` (cycle, weigh-ins, Health imports, TDEE), `routines` and `history` (editing, deleting, naming and repeating finished workouts); `store.ts` keeps loading, sync, backup and erase. A slice gets `set`, `get`, `commit` and `gym` through `Ctx` (`store/shared.ts`). New actions go in the slice they belong to, with their type in its `…Slice` interface.
- **Six languages, every change** (Melvin, 2026-11-10: all G7 countries): English, Spanish, French, German, Italian and Japanese (`LANGS` in `src/lib/i18n.ts`). New text goes into its catalogue file (`src/locales/text/<prefix>.ts`) in all six in the same change, and native text into every `values-<l>` and `<l>.lproj` file; `i18n.test.ts` and `nativeStrings.test.ts` fail otherwise. The app loads one language at a time (`scripts/locales.mjs`, `src/locales/load/`), so app code never imports a catalogue (`@/locales/en` and friends) at run time; use `t()` or `english()` ([Speed](docs/decisions/speed.md)). Splice a label into a sentence with `inSentence()`, never `toLowerCase()` (German capitalises nouns), and give Japanese plurals only `other`. Register, fixed terms and the Japanese and German layout rules are in [Borrowed from Gradelings](docs/decisions/borrowed-from-gradelings.md) under Languages.
- **English is Canadian English** (Melvin, 2026-11-11: "ensure it uses Canadian spellings"). Every piece of English a person reads (the `en` catalogues, hard-coded UI text, the website, blog posts and guides, emails, notifications, the Android, Wear OS, iOS, watch and Garmin text, the store listing, the admin panel) uses Canadian spelling: *-our* (colour, favourite, behaviour, endeavour), *-re* (centre, metre, litre, fibre), doubled *l* (levelled, cancelled, travelled, labelled), catalogue, defence, grey, cheque, "practice" as the noun and "practise" as the verb, but **-ize and -yze** (organize, prioritize, realize, stabilize, analyze), "program" (not "programme"), "math" (not "maths"), tire, curb and aluminum. Code identifiers, CSS (`color`, `center`), API fields, analytics names, URLs and slugs stay as they are, because changing them breaks code, saved data or search links. Proper names keep their own spelling (Labor Day, the Whole Earth Catalog).
- **Type-aware lint on `src/`** (`eslint.config.mjs`): `no-floating-promises` (a promise nobody waits for loses its error; await it, or mark a deliberate fire-and-forget with `void`), `no-misused-promises` (no async function where a plain callback is expected; JSX handlers may be async), and `switch-exhaustiveness-check` (a `switch` over a union covers every case or has a `default`).

## Testing (Melvin asked, 2026-11-09: like Gradelings)

- **Test data comes from `src/test/factories.ts`** (`makeSet`, `makeSets`, `makeWorkout`, `makeSessionStart`, `makeSessionEnd`, `makeProfile`, `makeTestGym`, fixed `NOW` and `DAY`): plain readable defaults plus overrides for what the test is about, so a new required field is added in one place. Ids count up; nothing is random.
- **Property tests** (`fast-check`, `src/lib/properties.test.ts`) for rules that must hold for every input: the plate solver only uses plates owned and its totals add up, recovery stays within 0 to 100% and moves the right way, units round-trip, remix links round-trip, and remix links, share links and CSV imports never crash on junk. Runs are seeded (`SEED`), so a failure repeats, and fast-check shrinks it to the smallest failing input. Add a property when a rule is "always" or "never". **No Faker** (Melvin asked, 2026-11-09): random names and strings don't find bugs in training math, and readable hand-picked numbers make failures easier to read.
- **Unit tests** (`src/lib/*.test.ts`, node) for every engine rule: plates, recovery, blocks, progression, generator, stats, game.
- **Component and integration tests** (`*.test.tsx`, `// @vitest-environment jsdom`, Testing Library, fake-indexeddb): the whole app from first run to a saved workout through the real store and IndexedDB, steppers, swaps, a bodyweight gym, and a workout surviving a reload.
- **Browser tests** (Playwright, `scripts/e2e*.mjs`): playthrough, offline, a device layout sweep (no sideways scroll, Log set fully on screen and 48 px+, controls 44 px+), and axe WCAG 2.2 AA with no serious or critical problems. Any console error fails a run.
- **Device coverage** (Melvin asked, 2026-11-09: "comprehensive but not too many"). One list in `scripts/devices.mjs`, 13 devices, each adding a screen size the others don't: iPhone SE (3rd gen), iPhone 16, iPhone 17 Pro Max, iPad Mini, iPad Pro 11 landscape; Galaxy S9+ (320 wide, the narrowest), Galaxy S24 (360, the most common Android width), Pixel 7, Galaxy A55, Pixel 7 landscape, Galaxy Z Fold 7 opened, Galaxy Tab S9 portrait and landscape. iOS devices run in **WebKit** (the iOS app is a WKWebView) and Android ones in Chromium. Every device gets the layout sweep plus a logged and saved set (about 2 s each); the full playthrough runs on Pixel 7 and again on iPhone 16 in WebKit. Offline and accessibility runs stay on Pixel 7. Add a device only when it brings a new size or engine, and drop one when another covers it. Cloud sessions have only Chromium, so WebKit devices skip locally and run in CI, where a missing engine fails the run.
- **Mutation tests** (Stryker, `stryker.config.mjs`, Gradelings' Vitest 5 runner in `scripts/stryker-vitest5.mjs`) on the engine, run by hand (not in CI); the run fails below the `break` score. Mutants are checked against the engine's own tests under `src/lib` (`vitest.mutation.config.mts`): with the screen, site and server tests too a run needed about five hours, so the hour-limited runs on 2026-11-11 and 2026-11-12 were cancelled at 20% with no report. A full run now takes about 45 minutes (limit 120) and the incremental cache is saved even when it fails. It is a ratchet: 34% at first, 67.5% on 2026-11-13 after tests for readiness, loads, progression and the generator, so `break` is 60; raise it as engine tests land (Gradelings aims for 85). Weakest now: `game.ts`, `recovery.ts` and `generator.ts` (about 55%).
- A bug fix comes with a test that fails without it. Flaky tests are fixed at the cause, never retried.
- Colour tokens must pass contrast: `--color-faint` was raised to `#808c9d` because axe failed `#5b6777`.

## CI/CD (Melvin asked, 2026-11-09: like Gradelings)

- `.github/workflows/ci.yml` on every pull request and push to `main` and `staging`: types, lint (no warnings), dependency audit, unit and integration tests with coverage, build, then browser tests in three parallel jobs. **"CI passed"** is the one required check.
- `mutation.yml`: **on demand only** (Actions › Mutation tests › Run workflow). Mutation runs are long and expensive, so they never run on pull requests or merges and never gate a merge (Melvin, 2026-11-09). Run one after a batch of engine work and raise `break` when the score rises.
- `promote-staging.yml` (Melvin confirmed the Gradelings model, 2026-11-09): `main` is production and every pull request targets `staging`. At 09:00 UTC each night it opens a staging → main pull request and merges it when "CI passed" is green on staging's latest commit, then merges `main` back into `staging`. Run it by hand from the Actions tab to ship sooner. Scheduled workflows only run from the default branch, so the file must be on `main` before the nightly run starts. It needs "Allow GitHub Actions to create and approve pull requests" on, and `PROMOTE_TOKEN` if `main` requires reviews.
- `ci.yml` also builds an Android debug APK (uploaded as an artifact to install and try) and an unsigned iOS simulator build. Both are part of "CI passed".
- **CI speed (Melvin asked, 2026-11-09 and 2026-11-10: "find other ways to reduce CI runs").** The `changes` job decides what a run does, and "CI passed" counts a skipped job as passed, so the required check still reports:
  - *Already tested:* when "CI passed" succeeds it records the tree it tested as a commit status (`CI passed tree`, on the pull request's head commit or the pushed commit). A run whose tree already passed (on a parent, on the pull request a squash commit came from, or on the same commit) skips every job. That covers the staging push after a merge when staging didn't move meanwhile, the nightly promotion pull request, the push to `main` and the merge back into `staging`, which used to run the whole suite four more times for code that had already passed.
  - *Markdown only:* when every changed file is `.md` (docs, `AGENTS.md`, READMEs) and the commit before passed, the tests and builds are skipped. `docs/PLAY_LISTING.md` still runs everything, because `playListing.test.ts` checks it. **Locale text (`src/locales/`) is not treated as copy**: it's app code, the tests check every key in every language, and longer text can break layouts at large text sizes, so it runs the full web suite (but not the native builds).
  - *Native builds* run only when the diff touches `android/`, `ios/`, `capacitor.config.*`, `package.json`, `package-lock.json`, `ci.yml` or `.github/actions/`, on pull requests and on pushes alike (pushes used to build both every time; `release.yml` still builds both on every promotion). Add a path to that filter whenever something new can affect native builds.
  - Runs on the same branch or pull request cancel the one in progress. The device sweep runs as two jobs (`DEVICES=ios` and `DEVICES=android`) and the iPhone playthrough is in the playthrough job. Gradle uses its build cache (cached across runs) and `--parallel`. The iOS simulator build compiles arm64 only, with no index store, and uses a placeholder `out/` so it starts without waiting for the web build.
- `release.yml`: on every promotion to `main` (nightly or by hand; `promote-staging.yml` starts it with a workflow dispatch, because a merge made with the default `GITHUB_TOKEN` doesn't fire its `push` trigger; with `PROMOTE_TOKEN` set the push fires it and the dispatch is skipped; Melvin, 2026-11-10) and on demand, builds a signed Android App Bundle and uploads it to the Play **internal** track, and archives iOS and uploads it to **TestFlight**. Version name comes from `package.json`, build number from the run number. Each platform skips itself with a notice until its secrets exist. Promoting past internal testing stays a human step in the store consoles.
