# Liftsmith: guide for agents

Liftsmith is an Android-first adaptive strength training app. It plans each workout from the lifter's equipment, recovery and training block, then gets out of the way while they lift. This file records every product and technical decision made so far, and why. Follow them. If a task seems to need one changed, raise it with the owner (Melvin) first, and when a decision changes, update this file in the same change.

The full plan with stages lives in the plan doc: https://claude.ai/artifact/S24kx43ZkQ8g3gGtGew34n

## Commands

```bash
npm run dev                  # http://localhost:3000 (public site), http://localhost:3000/app/ (the app)
npm test                     # unit + integration tests (Vitest; engine in node, screens in jsdom)
npm run test:coverage
npm run test:mutation        # Stryker on the engine; report in reports/mutation/
npm run lint && npx tsc --noEmit
npm run build                # server build (Vercel): pages plus API routes (route.api.ts)
npm run build:static         # static export to out/ (native shells, browser tests)
node scripts/e2e.mjs         # full playthrough (serves out/ itself, or pass a base URL)
node scripts/e2e-offline.mjs # real offline after one visit
node scripts/e2e-devices.mjs # layout on 13 phones and tablets (DEVICES=ios|android|full|names)
DEVICE='iPhone 16' node scripts/e2e.mjs  # the playthrough on another device
node scripts/e2e-a11y.mjs    # axe WCAG 2.2 AA on every screen
node scripts/site-screenshots.mjs # real app screenshots for the home page (public/screens/)
node scripts/play-capture.mjs && node scripts/play-compose.mjs && node scripts/play-video.mjs # Google Play art (docs/PLAY_LISTING.md)
npx cap sync                 # copy out/ into the Android and iOS shells (after npm run build:static)
```

There is no Android SDK in cloud sessions; APKs and AABs build in GitHub Actions (`.github/workflows/android.yml`).

## Platform parity (rule, Melvin, 2026-11-09)

- **Every feature goes in both apps, plus the web app wherever it makes sense** (Melvin, 2026-11-09). Each feature lands on Android and iOS in the same change: native Android code (Java or Kotlin in `android/`) and native iOS code (Swift in `ios/`) for anything the web layer can't do. The web app (`/app/`) gets it too when the browser can do it (for example, `.ics` files instead of calendar access, and manifest shortcuts instead of widgets).
- **One-platform features are allowed when they're very useful** (Melvin, 2026-11-09). If a feature is very useful on one platform but the other ecosystem can't support it, build it anyway. Record the gap under "Platform deltas" below, and in the pull request description, say what each platform does instead.
- Platform equivalents: Health Connect ↔ HealthKit (Apple Health); foreground-service notification ↔ Live Activity (lock screen and Dynamic Island); Play Billing ↔ StoreKit; Sign in with Google ↔ Sign in with Apple (both offered on iOS); Wear OS ↔ Apple Watch.
- CI builds both apps together (`android` and `ios` jobs in `ci.yml`): on every pull request that touches native code, Capacitor or dependencies, and on every push to `staging` and `main`. Both always run or skip together.
- **Live workout notification today:** Android runs a foreground service (`WorkoutService.java`) with an ongoing notification: lock-screen rest countdown (chronometer), next set and plates, heart rate, and Log set / +30 s buttons, plus a rest-over alert. iOS (`WorkoutSessionPlugin.swift`) runs a **Live Activity** (lock screen and Dynamic Island: rest countdown, next set and plates, heart rate, Log set / +30 s links; drawn by the `LiftsmithWidgets` extension) and schedules a time-sensitive rest-over notification with the same two buttons. Heart-rate-only changes reach the Live Activity at most every 15 s, because iOS budgets updates. Both are driven by the same `WorkoutSession` calls in `src/lib/sessionNotify.ts`.
- Native code registered by the app: Android `MainActivity.registerPlugin`, iOS `MainViewController.capacitorDidLoad` (Capacitor 8 with SPM doesn't auto-register app-target plugins). `InstallInfo` (device and install source for analytics) is registered on both.
- Native apps open straight into the app (`server.appStartPath: /app/index.html`); the landing page is for the website.

## Product decisions

### Action over stats (rule, Melvin, 2026-11-09)
- **We don't show stats for the sake of stats or pretty graphs. We prioritise action-oriented recommendations.** Every screen should answer "what should I do?" before "what happened?". A new chart or number needs a reason the lifter would act on it; if it has none, leave it out or turn it into a recommendation.
- **Every recommendation says why, in a short line.** Each recommended workout, exercise, set count, rep target and weight carries a plain-words reason built from the same data that produced it: readiness low or high (and the signals behind it), a deload, a plateau, missed or hit reps, feedback, the lifter's own settings, recovery and weekly sets left. Code: `src/lib/why.ts` (`itemWhy` for each planned exercise on Today, `workoutWhy` under the target during a set, `callWhy` for the push / as planned / easy call) and the notes on targets in `progression.ts`. A new recommendation lands with its reason in the same change. Reasons are shown, never behind a tap, and never add a tap during a set.
- **Proactive insights ("Coach's notes").** `src/lib/insights.ts` looks for things worth acting on and says what we saw, the numbers behind it, and one thing to do, ideally a one-tap action: fatigue building (missed reps three workouts running, offer a deload), stalled lifts (no new best in 3+ weeks; several at once offers a deload), a big muscle short of its weekly sets for two weeks (offer to make it a priority), body fat creeping up (advice for the goal), weight dropping faster than 1% a week, the weekly goal at risk (offer a 30-minute workout), the last hard week of a block, and what's working (a lift up 5%+ in six weeks). They show on Today (top two) and at the top of Progress ("What to do next"). Nothing is shown when nothing needs doing. "Got it" hides a note on the device until the finding changes (its id changes). Derived from events every time, never stored.
- **Actions:** `store.startDeload()` makes the current week the deload (the next block starts after it), priorities go through Settings' `togglePriority`, and minutes through `setProfile`.
- **Body fat** is an optional field on body weight events (`bodyFat`, %). Weigh-ins and body fat come in from Health Connect and Apple Health on launch (`readBody` in `health.ts`, one per day, ids `health-bw-<day>` so a re-import is a no-op; HealthKit's fraction is turned into a percentage), which covers smart scales and the Hume Body Pod. A manual body fat entry is still to do.
- Insights and reasons are free; they explain the plan rather than add to it. Pro features add notes through the same list: a single stalled lift goes to the **plateau detective** (Pro), whose note gives the likely cause and a one-tap three-week fix (`fixPlateau`), then says the fix is running and, after it ends, whether it worked. Without Pro the plain stall note shows instead. Several lifts stalling at once stays a deload note, because that's fatigue. There is one place for stalls: coach's notes (the separate plateau card on Progress was removed).
- The wording lives in the language catalogues (`src/locales`: `why.*`, `ins.*`, `sig.*` for readiness signals, `note.*` for the notes on targets, `fix.*` and `cause.*` for the plateau detective, `explain.*` for the "Why?" sheet), so it follows the app's language. Engine code builds sentences from whole catalogue lines with placeholders, never by gluing English fragments, and never matches on a note's wording (compare against `t("note.push")` and friends).

### Positioning
- **An original app.** It borrows ideas from Fitbod (daily adaptive workouts, equipment matching, recovery map, variability setting) and Gymverse (periodized blocks with RIR and deloads, exercise swaps, lock-screen timer). It never uses their names in the UI, their art, screenshots, exercise videos or exact look. Exercise names, setup text and cues are our own.
- **Focus on the workout, not the app.** One tap logs a set as planned. The next set is always pre-filled. The rest timer starts itself. Anything optional (feedback, swaps, info) appears between sets and never adds a tap during a set.
- **One control, one destination** (Melvin, 2026-11-09: "two buttons doing the same thing is not correct"; keep the app as simple and streamlined as possible). On any one screen, a sheet, page or dialog has exactly one control that opens it. Before adding a button, check nothing on the screen (the tab bar included) already goes there; if a bigger area should be tappable, make that area the one button rather than adding a second. A glossary `Info` "i" never sits beside a button or sheet that explains the same thing. Cleaned up on 2026-11-09: the workout screen's info icon and the separate demo tap (the demo card is now the one "How to ›" button), Settings' "Achievements and locker" button (the Awards tab is always on screen there), and the "i" next to fitness age (its "How is this worked out?" sheet explains it). Links from one screen to another screen (Progress › All tools and Settings › Tools, say) are fine: they're different screens.
- **Explain every label that isn't obvious** (Melvin, 2026-11-09). Jargon and training terms (deload, build weeks, RIR, readiness, today's call, volume, estimated one-rep max, sets per muscle, exercise variety, recovery, warm-ups) get the one shared `Info` button (`src/components/Info.tsx`): a small "i" with a 44 px tap target that opens a short plain-language dialog. The text lives in the language catalogues (`gloss.<term>.title` and `gloss.<term>.body`, one paragraph per line); `src/lib/glossary.ts` lists the terms and reads them. `Section` (app) and `Panel` (web dashboard) take an `info` term. Any new label a lifter might not understand gets a glossary entry in the same change.
- **Dark, trustworthy, professional.** Deep navy-black background, one blue brand accent (`#4c8dff`, one CSS variable so cosmetics can recolour it), green, amber and red reserved for status (recovery bands, warnings). Large touch targets, tabular numbers, system font (Roboto on Android).
- **Light mode** (Melvin, 2026-11-09). **Settings › Appearance: Dark (default), Light, or Match system.** It sets `data-theme` on `<html>` (`src/lib/theme.ts`), saved on the profile and in localStorage so the next launch paints the right theme before the profile loads; it also sets the browser bar colour and the native status bar style, and the web dashboard follows it. **Every colour is a token** in `globals.css` with one dark and one light value, including badge tiers, crate rarities and heart rate zones (`--tier-*`, `--rarity-*`, `--hr-*`); never hard-code a hex in a component. The light accent is a darker blue (`#1d4fc4`) so text passes contrast, and an equipped accent cosmetic is darkened on light screens (`applyAccent`). The design pass's effects (primary gradient and its ink, screen glow, card sheen and shadow) are variables too (`--grad-*`, `--btn-ink`, `--glow-*`, `--sheen*`, `--shadow`); the light primary button is a deeper blue-to-violet with white ink. Earned themes (`themes.ts`) are dark palettes: on a light screen only their accent carries over, darkened, and the light surfaces stay. Order: Appearance, then the earned theme, then an equipped cosmetic accent. `src/lib/appearance.ts` is Appearance; `src/lib/themes.ts` is earned themes. The axe run checks the main screens in both themes. The share image stays dark.

### Visual design system (Melvin, 2026-11-09: "liven it up, but keep it simple and professional")
- **Tokens live in `src/app/globals.css`.** Brand blue plus four supporting hues used only as tints for marks, chips and card glows, never for body text: violet `#a78bfa` (levels, Pro, quotes), cyan `#38d6e8` (rest, time, easy days), ember `#ff8a3d` (streaks, push days, challenges), mint `#34d399` (done). Status colours keep their meaning. Named roles are in `src/components/app/theme.ts`: muscle families (push blue, pull cyan, legs violet, core ember) and the readiness call (push ember, normal blue, easy cyan).
- **The primary action is a blue-to-violet gradient with dark ink** (`.btn-primary`, 7:1+ contrast). One primary per screen. Cards are raised glass (`.card`, hairline border and a faint top light); `.card-tint` with `--tint` gives a card a hue for the hero card on each screen. A soft light sits at the top of every screen (`.aurora`).
- **Type:** 28–30 px extra-bold screen titles, tight tracking; big numbers use `.display` (tabular, 800). Section labels are small caps with an icon.
- **Icons:** one hand-drawn stroke set (`src/components/app/icons.tsx`, 24-unit grid, 2 px). No emoji in app chrome.
- **Empty states** use `EmptyState` (icon in a tinted tile, a title, one line of help, and an action when there's an obvious next step). No bare "nothing here" lines.
- **Mascot** (Melvin asked for "juicier", 2026-11-09): an original, friendly kettlebell (`Mascot.tsx`), drawn in the brand gradient so it follows the theme and light mode, with four moods (happy, sleepy, cheer, curious), a slow bob and a blink. It appears only where the app is otherwise quiet: the first setup step, a few empty states (`EmptyState mascot=`: rest day, no workout running, no workouts yet, no routines), and the end of a workout. Never on the workout screen during a set, always `aria-hidden`, and still in Lean mode.
- **Motion:** short and purposeful (`rise`, `pop`, `fade`, `nudge` on a changed number, `burst` from Log set, `beat` on the live heart rate, `spring-in` for empty states, `stagger` for Today's exercise list). **Springs:** `--ease-bounce` is a real spring (CSS `linear()`, overshoot then settle) with a back-ease fallback. `.press` squashes instantly (70 ms) and springs back on release; the primary button squashes and stretches (`scale(1.02, 0.9)`), cards dip less. iOS shows `:active` only with a touch listener, so `App.tsx` adds one. **Bursts** (`burst.ts`): particles in the token colours plus an optional checkmark, from what the lifter touched (Log set, a crate), under a second, never blocking a tap. Nothing moves during a set except what the lifter touched. `prefers-reduced-motion` and **Lean mode** (`profile.lean`, Settings) both cut motion, bursts and confetti (`.calm` on `<html>`, `calm()` in `juice.ts`).
- **Sound set:** every sound is one synthesized voice (a soft glassy mallet) in A major pentatonic (`juice.ts`), so sounds never clash: a near-silent tick for steppers, chips and the length slider, a soft rising or falling pair for a switch on or off, a rising pair for Log set, a phrase for Start, a three-note chime for rest over, a falling pair for discard, a bright run for a goal or quest done, a low soft pair for an error, and a longer phrase for the end of a workout. No sound on navigation. One **Sounds** switch (`profile.restSounds`) covers them all.
- **Haptics** go through `@capacitor/haptics` on both Android and iOS, falling back to `navigator.vibrate` on the web. The vocabulary (`HapticKind`): `select` (light tick) for steppers, sliders, chips and tabs; `tick` for buttons; `toggle` (medium) for switches; `tap` (medium) for Log set; `thud` (heavy) at rest end; `double` (a crisp double tap) and `celebrate` (double tap then success) for PRs, level-ups and achievements; `success`, `warning` and `error` notifications. `oops()` pairs the error haptic with the error sound for any failure. **Vibration** can be turned off in Settings (`profile.haptics`).
- **On/off settings are switches** (`Switch`, `SwitchRow` in `ui.tsx`, `role="switch"`), not On/Off chip pairs: one tap, one thumb. The knob springs across and stretches while pressed.
- **Loading** shows `TodaySkeleton`, shaped like Today, instead of a spinner; `Skeleton` makes any other shape.
- Before/after screenshots: `node scripts/shots.mjs [base-url] [out-dir]` (after `npm run build:static`).
- **App icon and favicon** (Melvin asked, 2026-11-09: "follow the app's theme"). The mark is an **anvil with a loaded barbell resting on it** ("smith" plus "lift"), an original drawing, in the primary gradient (`--grad-a` to `--grad-c`) on the navy background (`--color-bg`) with the same soft top glow as the screens. It's a solid silhouette so it reads at 16 px and works as a one-colour shape. **One script draws every file** from that one mark, so the platforms can't drift: `node scripts/make-icons.mjs` (Playwright's Chromium, ImageMagick for the `.ico`; set `PW_CHROMIUM=/opt/pw-browsers/chromium` in cloud sessions). It writes:
  - *Web:* `public/icon.svg` (favicon), `favicon.ico` (16/32/48), `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`, `icon-maskable-512.png` (mark inside the 40% safe circle) and `icon-mono.svg`, all listed in `manifest.ts` and `layout.tsx`.
  - *Android:* an adaptive icon (vector background with the glow, foreground PNGs with the mark inside the 66 dp safe circle) plus a **monochrome layer for Android 13+ themed icons**, legacy square and round PNGs for Android 7, and the splash screens.
  - *iOS:* `AppIcon` with **light, dark and tinted** images (iOS 18 appearances; dark and tinted are transparent so iOS draws its own background), and the splash.
  - *Earned theme icons* (forge, glacier, aurora, royal) come from the same mark in each theme's colours, with the same monochrome, dark and tinted variants. Change a theme's colours in `PALETTES` in the script.
  It replaced Capacitor's placeholder icons and splash, and `scripts/make-theme-icons.py`.

### Accessibility (Melvin, 2026-11-09: "accessibility checks, WCAG guidelines, colour blind support")
- **Target: WCAG 2.2 AA everywhere**, checked in CI. `scripts/e2e-a11y.mjs` runs axe on every screen in dark and light, again with colour-blind safe colours and more contrast, once under forced colours, then a **keyboard-only run** at the **largest text on a 360 px phone**: every Tab stop shows a focus ring, a workout starts and a set logs without a pointer, sheets take focus, keep Tab inside and close on Escape with focus returned, and no screen scrolls sideways. `src/lib/a11y.test.ts` checks the colour tokens: status colours 4.5:1 as text, recovery colours 3:1 against cards, and both colour sets simulated for protanopia, deuteranopia and tritanopia (Machado 2009) so they stay apart. Lint runs the full strict `jsx-a11y` rule set.
- **Settings › Accessibility** (`src/lib/a11y.ts`, saved as `profile.a11y` and in localStorage so the first paint is right):
  - *Text size:* Match my phone (default), Default, Large, Larger, Largest (100 to 150%). It scales the root font size; **every font size is in rem** (no `text-[Npx]`), so all text follows. On Android and iOS, Match my phone reads the phone's own size (font scale, Dynamic Type) through `@capacitor/text-zoom` and pins the WebView's own zoom at 100%, one path on both platforms. Layouts wrap rather than scroll sideways at the largest size.
  - *Colours:* Standard or **Colour-blind safe** (blue, light blue, orange and pink for recovery; blue, orange and pink for good, warn and bad). Status and recovery colours are tokens with `-std` and `-cvd` values per theme (`--band-*`, `--good-*`, `--warn-*`, `--bad-*`), picked by `data-cvd` on `<html>`. Heart rate zone colours already pass the simulation and stay as they are.
  - *Contrast:* Match my phone (follows `prefers-contrast: more`), Standard, or More (secondary text and borders mixed toward the ink colour; glows, sheen and gradient text removed). Built from each theme's own ink and background, so it works in dark and light.
  - Motion: Lean mode and the phone's reduce motion setting (unchanged).
- **Colour is never the only cue (WCAG 1.4.1):** the recovery map and its legend add dots (Recovering) and stripes (Fatigued); picked chips show a tick; every band also has a label and a percentage.
- **Sheets always show how to close them** (Melvin, 2026-11-09): every `Sheet` (`ui.tsx`) has a ✕ Close button in its header (44 px) and closes when swiped down (from the handle, or anywhere while scrolled to the top; 96 px, or a quick flick of 40 px+), as well as by tapping outside and Escape. A short pull springs back. Drags that start on a 3D figure, a slider or `[data-no-swipe]` belong to that control, and sideways or upward drags are left alone. Pure web code, so Android, iOS and the web get it together.
- **Screen readers:** the rest timer is a `timer`; a polite live region says when rest starts, at ten seconds left and when rest is over (not every second). Sheets are modal dialogs labelled by their title.
- **Forced colours** (Windows High Contrast): cards and buttons keep an edge, the focus ring uses `Highlight`, and the recovery map keeps its colours (`.keep-colours`).
- **Quick, one-handed input (Melvin, 2026-11-09: "the less manual typing the better"):** every screen should be fast to adjust in the gym. Prefer steppers with bump buttons, sliders, toggles and chips over text fields, and offer typing only as a fallback. Design for one hand, and respect left- or right-handed use.
  - Every − / + bump (`Bump` in `ui.tsx`) **repeats while held**, faster the longer it's held; a keyboard or screen reader click steps once.
  - Numbers a lifter would type use **`BumpField`** (− box +, typing still works): body weight in setup, Settings and the weigh-in on Progress and Body and photos, age and known lifts in setup, and bar weights in Gyms. An empty box bumps from a sensible start (the last weigh-in, 30 years, a common bar). New number inputs use it too.
  - **One-handed controls** (Settings › Accessibility: Off, Right hand, Left hand; `profile.a11y.hand`): during a workout the weight and rep bumps move down into a dock beside Log set, with Log set under that hand's thumb; the big numbers stay on the set card. Off by default.
- Every new screen gets an axe scan in the a11y run, and every new colour is a token that passes `a11y.test.ts`.

### Today screen (Melvin, 2026-11-09)
- The greeting uses the lifter's first name when one is set ("Good evening, Melvin"). Setup's first step asks for it (optional), and Settings can change it.
- **Daily quote:** one quote a day on Today about effort, health, hard work and discipline, from `src/lib/quotes.ts` (380 quotes, at least 365 so none repeats within a year; bundled, so it works offline). A fixed seeded shuffle picks the day's quote, so every device shows the same one and it changes at local midnight. Every quote has its author and, where known, its source; only documented quotes, with common misattributions left out (a test checks a few). Settings › Daily quote turns it off (`profile.quotes`).

### Name
- **Liftsmith** (Melvin chose it, 2026-11-09; the working name before was Setwise). The name is set in `src/lib/brand.ts`.
- **App id: `com.getliftsmith.app`** for the Android package and the iOS bundle id, with the widget extension at `com.getliftsmith.app.widgets` (Melvin, 2026-11-09). It can never change after the first Play and App Store upload.
- **Domain: `getliftsmith.com`** (Melvin chose it and bought it on Cloudflare, 2026-11-09; attached to Vercel, which makes production public because custom domains skip Vercel Authentication). **Every URL uses `https://www.getliftsmith.com`** (Melvin, 2026-11-09): the bare domain redirects to www, so canonical links, `metadataBase`, the sitemap, robots, Open Graph tags, email links, store listings and native config all use the www host, never the bare one. Email addresses stay on the bare domain (`hello@getliftsmith.com`). It's the default `SITE_URL` (`src/lib/site.ts`, overridable with `NEXT_PUBLIC_SITE_URL`, which must also include www). When App Links and Universal Links land, serve `assetlinks.json` and `apple-app-site-association` on www and list both hosts in the app's intent filters and associated domains, so old bare links still open the app.

### Training engine (src/lib)
- **Equipment and gym profiles.** Each gym has its own equipment list, bars, the exact plates owned (with counts), dumbbells, kettlebells and machine step. The generator uses only exercises whose every needed item is at the active gym (`available` in `exercises.ts`).
- **Bodyweight exercises** cover every major muscle, so a "Bodyweight" gym (hotel, park) gets full workouts. A test checks this.
- **Workout length.** A slider from 15 to 90 minutes. The plan is seeded by day and gym, so moving the slider adds or drops exercises at the end instead of reshuffling (`generator.ts`). **Every length counts warm-up sets and rest** (Melvin, 2026-11-09): an exercise is setup (60 s), its warm-ups with 60 s rest after each, its working sets, and the rest between them, and the rest before each exercise counts too (`itemSeconds`, `planSeconds`). Today shows each exercise's minutes and warm-up count. If the final order's warm-ups push the plan past the time asked for, sets come off the end.
- **Warm-up sets** (Melvin, 2026-11-09; `warmup.ts`). The first loaded lift for a muscle ramps up on weights the gym can make: the empty bar ×10 for barbells, then about 55%×5 and 80%×2 (or 50/70/85% for 100 kg and up). Machines and dumbbells get 50%×8 and 75%×4. A later barbell lift for muscles that are already warm gets one feeler set (70%×3). A first isolation exercise gets one light set, and bodyweight and timed exercises get none. Warm-ups are their own `warmup` event, so stats, recovery, progression, PRs and XP never count them. The workout screen shows "Warm-up 1 of N", with a 60 s rest and a Skip warm-up link.
- **Recovery.** Each set adds fatigue to its primary muscles (full) and secondary muscles (half), less when far from failure. Fatigue fades so 90% is gone after about 48 h for small muscles and 72 h for large ones. Bands: Fresh 90%+, Ready 70%+, Recovering 40%+, Fatigued under 40% (`recovery.ts`). The generator only targets muscles at 55%+ and avoids exercises whose primary muscles are under 40%.
- **Periodization.** Blocks of 3 to 6 build weeks (default 4) then a deload week. RIR steps down across the build weeks (3, 2, 1, 0 for four weeks); the deload is RIR 4 at half the sets. Weekly sets per muscle rise from 8–12 to 12–20 by experience (`block.ts`).
- **Progression.** Double progression on top of the RIR target: hit every set's target and the next session adds a rep; at the top of the rep range, the weight goes up one loadable step and reps go back to the bottom; a miss by 2+ reps drops a step. Post-exercise feedback (too easy, too hard) shifts it one more step (`progression.ts`).
- **Starting lighter after a break** (competitor audit, Melvin 2026-11-09; `src/lib/layoff.ts`). When the muscles an exercise trains (any exercise sharing a primary muscle) haven't been worked for 10+ days, the first session back is about 10% lighter for each whole week away, at most 30%, from the heaviest working weight of that exercise's last session before the break. On adaptive plans the next two sessions close the gap a third at a time (70 → 80 → 90 after three weeks off), unless normal progression is already past it or the last session was a miss or "too hard"; after three sessions back the break is over. The note on the target says why ("Back after 3 weeks off: starting 30% lighter", `note.comeback`, `note.rampBack`). **Fixed programs** get the same first-session cut (the planned sets carry `comeback`, and so do the logged ones), then rebuild with their own jumps from the lighter weight, as the well-known 5×5 apps do. Deload weeks, bodyweight exercises and sets done lighter for an injury are left alone. Derived from events, never stored.
- **One dumbbell or a pair, one side at a time** (competitor audit, Melvin 2026-11-09: Hevy's most-raised request, which it calls "genuinely tricky" to add under logged history; `src/lib/sides.ts`). A set's `weight` is the load of **one** dumbbell or kettlebell, and the whole load for barbells and machines. Each set records `implements` (1 or 2, from `implementsFor`) when it's logged, so a later change to the exercise list never rewrites history; older and imported sets without it fall back to the exercise (dumbbell exercises use a pair unless listed in `ONE_DUMBBELL`, kettlebell exercises use one bell). Per-side exercises (`PER_SIDE`: one-arm rows, split squats, lunges, single-leg calf raises) log reps for each side: both the same is the one-tap default, and an optional "Sides differ?" link under the reps adds a stepper for the right side (`Active.repsR`), so a set can carry `repsL` and `repsR`, with `reps` as the weaker side for progression. **Volume** everywhere (`setVolume`: sessions, totals, recaps, seasonal challenges, tonnage) is weight × implements × reps on every side, so two 20 kg dumbbells for 10 count 400 kg; volume figures from before this change went up for dumbbell work (no real users yet). The weight label says "each" only for pairs. e1RM, PRs and plate math stay per implement. Strong and Hevy log a dumbbell's own weight, which is what the importer assumes.
- **First-session starting weights** (Melvin, 2026-11-09, after a 145 lb "experienced" lifter was offered a 175 lb squat). Each exercise's `start` is a share of body weight for about 10 reps. That gives an estimated one-rep max, scaled by experience (new 0.55, some 0.8, experienced 1.0, because self-reported experience runs high), sex (women 0.6 upper body and 0.75 lower; unknown sits between), and age (from 40, 0.92 down to 0.65 at 70+). The first session then aims 2 reps further from failure than the block asks (`FIRST_RIR`). Known numbers entered in setup (squat, bench, deadlift, overhead press as weight × reps) replace the estimate for that lift, and scale to close relatives at 85%. **Quick calibration:** if the first session shows the start was light ("too easy", 2+ reps over target, or the lifter raised the weight), the next session jumps to what the logged sets show, capped at +25%, instead of one step at a time. That 145 lb lifter now gets 120 lb × 6 (135 lb if they say male).
- **Variability.** Consistent keeps an exercise for a muscle about 75% of the time, Balanced 50%, Variable 25%.
- **Swaps.** Alternatives share primary muscles and must be doable at the gym, ranked by muscle overlap and movement pattern. A swap marked "not available here" keeps that exercise out of plans at that gym for 14 days.
- **Plates.** Every suggested barbell weight is one the lifter's plates can make. The plate solver is a bounded knapsack (a greedy fill misses some combinations), prefers fewest plates, then heaviest first, and works in the gym's unit so 45 lb plates stay exact (`plates.ts`). Plate colours follow the common competition convention.
- **Units.** Weights are stored in kilograms; a gym's plates, bars and dumbbells are stored in the gym's unit and converted at the edges (`units.ts`).

### Workout screen
- Big target weight and reps with steppers, the barbell plate graphic for every barbell set, a big Log set button, an automatic rest timer with +30 s and Skip, and the next set's plates shown during rest so the lifter can load while resting.
- **Live workout notification and lock-screen rest timer.** On Android, a foreground service shows an ongoing notification with a live countdown, the next set and plates, heart rate, and Log set and +30 s buttons; it sounds and vibrates when rest ends. On iOS the same content is a Live Activity on the lock screen and in the Dynamic Island. The web build falls back to a service-worker notification and an alert at rest end (`sessionNotify.ts`).
- The screen stays on during a workout (wake lock), unless the lifter turns it off in Workout preferences.
- **Workout preferences** (Melvin, 2026-11-09; Settings › Workout preferences, `#/training`, `TrainingSettings.tsx`, `src/lib/training.ts`, stored on `profile.training`). Every field is optional and missing means the automatic choice, so older profiles behave exactly as before. Everything is chips and taps (no typing), so it works one-handed in the gym.
  - *Rest between sets:* a default for big lifts and one for smaller lifts, plus a per-exercise time. Order: the exercise's own, then compound/isolation, then by goal (`restFor`).
  - *Rep ranges:* one for compound and one for isolation lifts, plus a per-exercise range (`repRange`). Type ranges apply to loaded exercises only (bodyweight work keeps adding reps); holds stay in seconds. Double progression runs inside the chosen range.
  - *Sets per exercise:* Auto (3, 4 on the first big lifts, a filler set when time allows) or a fixed 2–6, plus a per-exercise count. A chosen count gets no filler sets; deload weeks and easy days still use fewer.
  - *Effort scale:* RIR or RPE (RPE = 10 − RIR, RIR 4+ shows as RPE ≤6). Stored as RIR either way; only the labels change (Today's week chip, the aim under the numbers, the optional set-effort row).
  - *Rest timer:* auto-start on (default) or off. Off leaves a **Start rest** button after Log set; the rest still counts from Log set. Rest-over alert: follow Sounds and Vibration (default), both, sound only, vibration only, or silent; it drives the in-app chime and buzz, the native alert and the web notification. Keep screen on (default on).
  - *Favourites:* a star in the exercise's How to sheet, or picked by muscle in Workout preferences. The generator weights a favourite 6× and prefers it over keeping last time's exercise when both fit; it still needs the gym's equipment, recovery and the day's muscles.
  - *Muscle priorities:* up to three. They aim for a third more weekly sets (`PRIORITY_VOLUME`), rank higher when recovered, and get leftover-time sets first. Recovery rules are unchanged, so a fatigued priority muscle still waits.
  - *Default workout length:* the Today slider goes back to it on the first open of each day (`minutesForToday`, `profile.minutesDay`); "Last used" keeps the old behaviour.
  - *Week starts on:* Monday (default) or Sunday, for streaks, freezes, quests, recaps, weekly stats and the web dashboard's calendars. `derive.ts` holds it as module state set from the profile (`setWeekStart`, `weekOf`, which replaced `mondayOf`). Training blocks keep their own 7-day weeks from `blockStart`.
  - *kg or lb:* Settings › Units is the display unit. Each gym also switches its plates between kg and lb (Gym › "This gym's plates are in"), which swaps the kit for a standard set in the new unit, because plates don't convert. When the gym's unit differs from the display unit, the workout shows the weight in both.
  - Per-exercise rest, reps and sets are also editable from the How to sheet during a workout; they apply from the next plan.
- **Supersets** (table stakes, Melvin, 2026-11-09; `src/lib/superset.ts`). A chain button between two exercises links them, on Today's plan and in the workout's "Coming up" list; tapping it again splits them, and three or more can be chained. Linked exercises share `PlanItem.group` and alternate: one set of each with a 15 s switch (`SWITCH_REST`), then the longest of their rests before the next round; when one runs out of sets the other carries on with its own rest. Warm-ups run the first time each exercise comes up. Plan length counts one rest per round, so linking shortens the estimate. Each set event records its `superset`, so "Same as last time" brings the pairing back. Links made on Today survive a rebuild of the plan (length, call) while both exercises are still neighbours, and so does splitting a pair the plan linked itself (a routine or "Same as last time"): the store keeps `a>b` for a link and `!a>b` for a split (`applyLinks`). **Pairing has to show** (Melvin, 2026-11-09: "the pairing of supersets doesn't do anything"; the link worked underneath but was easy to miss): on Today the link button sits on the line between the two exercises it joins (filled blue when linked), linked rows share a tint, a dashed join and one accent bracket down the left, each says "Superset A · 1 of 2", and the hint under the list says they alternate and how many minutes it saves. During the workout the superset chip has a "Then <exercise>" line naming where the next set goes. The generator never pairs exercises by itself yet. Pure web code, so Android, iOS and the web get it together.
- **Saved routines** (table stakes, Melvin, 2026-11-09; `src/lib/routines.ts`, `Routines.tsx`). The lifter's own list of exercises, set counts and supersets, used instead of the adaptive plan for a day. Today's **Routines** chip opens the list: Use today (the chip then shows the routine's name, and "Back to today's adaptive plan" undoes it), edit, delete, **Save today's plan as a routine**, or **Build a new routine** from the exercise library (search by name or muscle; what the gym can do comes first). The summary has **Save as a routine**, which takes what was actually done, swaps and supersets included. Weights and reps still come from progression and warm-ups from `warmup.ts`, so a routine keeps moving forward; exercises the gym can't do are left out for that day. Custom exercises can go in a routine (the lifter chose them, unlike the generator). Routines live on the profile (`profile.routines`, newest first, at most 50 of 20 exercises each), so they're in the backup and will sync with the profile; `sessionStart.routine` records which one a workout came from. Free, like the logger. The length slider doesn't change a routine. When the programs work (`Profile.planSource`) lands, a routine becomes `{ kind: "routine", id }` there. Pure web code, so Android, iOS and the web get it together.
- **Notes, set effort and custom exercises** (table stakes, Melvin, 2026-11-09). Each is its own event (`note`, `effort`, `customExercise`), so it syncs and exports like everything else.
  - *Notes:* written in the exercise's info sheet (500 characters at most). The latest note on an exercise shows under its name every time it comes up, in any workout.
  - *Set effort:* during rest, an optional "Reps left in the tank on that set?" row (0 to 4+) for the set just logged; it never adds a tap during a set and disappears once answered. In `progression.ts` (`effortSignal`), sets that had 2+ more reps left than planned count like "too easy", and sets closer to failure than planned count like "too hard". Explicit post-exercise feedback wins when both exist.
  - *Custom exercises:* "+ Add your own exercise" at the bottom of the swap sheet (name, main muscle, equipment, whether it's a big lift), then it's used straight away. They're registered into the library on load (`registerCustom` in `exercises.ts`), get starting weights, progression, recovery and stats like any other lift, but **the generator never plans them**, because we can't know their movement well enough to programme them.

### Workout data and coaching (Melvin, 2026-11-09: "win on data")
- **Capture everything, automatically, with no extra taps.** Every set stores weight, reps, the planned weight, reps and RIR, when the work started, its duration, the rest actually taken before it, and heart rate during the set (average, peak, and the value at Log set). Every session stores its length, time under load, total rest, average, max and min heart rate, and the call it was built with (push / normal / easy, readiness score, whether the lifter overrode it). The **full heart rate stream** (one sample a second) is saved as an `hrSeries` event at the end, and the in-progress stream is checkpointed to localStorage every 15 samples.
- **Set duration** runs from the end of the rest (timer ran out or Skip) to Log set. When the lifter logs before the rest ends, or the gap is far longer than a set could take, the duration is left out rather than guessed. A watch or HR-based set detector can refine this later.
- **Forgotten workouts end themselves** 3 hours after the last activity (`AUTO_END_MS`), checked on open, every minute, and when the app comes back to the foreground. The end time is set to where the lifter stopped (last activity plus a minute), not when it was noticed, and the session is marked `auto`.
- **The data drives the next workout** (`src/lib/readiness.ts`). A daily readiness score (50 baseline) from big-muscle recovery, days since the last workout and back-to-back days, target reps hit in the last two workouts, how sets felt, rep speed against the lifter's own history for the same exercises, and session heart rate against their usual. Sleep, HRV, resting HR and the pre-workout check-in plug into the same score when connected (integrations roadmap, step 2).
  - 65 or more is a **push day**: the first compound lift goes one rep closer to failure. 35 or less is an **easy day**: one set fewer per exercise (minimum 2), a step lighter, one more rep in reserve, and no extra filler sets. A deload week is never a push day.
  - **Challenges:** on about 30% of push days, at most one a week and never in a deload, the first compound's last set is as many good reps as possible. Challenge sets are flagged, so they don't skew the missed-reps signal.
  - Today shows the call, the score, the top three reasons, and Go easy / As planned / Push buttons. **The lifter can always override**, and overrides are recorded.
  - Weights and reps for the next session keep coming from `progression.ts` (double progression plus feedback), now on richer data.

### Camera rep counting (Melvin asked, 2026-11-09: "rep counter by camera or watch motion", then "use the camera for workouts… a toggle during that exercise to auto count", after trying the lab)
- **On the workout screen, for exercises the camera can read** (`profileFor` in `profiles.ts` has a profile; holds, carries, shrugs and wrist curls don't). A **Count reps** button at the bottom left of the exercise demo turns it on, and **Stop counting** on the counting stage turns it off (`AutoCount.tsx`). It's optional and never adds a tap during a set: the reps counted fill in the reps box, so Log set stays one tap, and the lifter can still bump the number. Each logged set (or warm-up) starts a fresh count; nothing is counted during rest. If the tracker ends a set on its own after 8 s still, the next reps add to the same count.
- **While it's on, the 3D figure follows the lifter** (`LiftDemo follow`, side view) with the live count in the corner and a small camera preview at the bottom right for lining up (mirrored for the front camera, a dot that turns green when the whole body is in view). **Front camera by default**, with a flip button on the preview. On or off, the camera side and the source are remembered on the device (localStorage `liftsmith.autoCount`), so it stays on across exercises and workouts until switched off.
- **Pro** (`can("autoCount")`; everyone has it until billing is live). The lab screen (`#/lab`, the `repLab` flag) was removed once this landed.
- **Phone motion** counting was unreliable in Melvin's tests, so it's behind the `repMotion` flag (off). When the flag is on, the stage offers "Use phone motion". Five quick taps on the Settings title switch the flag on this device, for testing.
- Nothing about counting is saved yet beyond the reps the lifter logs. Self-host the MediaPipe runtime and model before a store release (Open items).
- **One rep engine for every source** (`src/lib/reps/tracker.ts`): follows the excursion from the rest position (5-sample median, then a One Euro filter), counts an attempt each time the lifter leaves rest and comes back, and grades it when the set ends: **full**, **partial** (under 80% of the set's deepest rep or under the profile's minimum range), **failed** (didn't come back within 6 s, tracking lost for 1.5 s mid-rep, or sank back to the bottom after getting partway up). **Grinders** are full reps 50%+ slower than the set's fastest, or with a stall (under 15% of the rep's peak speed for 250 ms+). **Set length** runs from the first movement to the end of the last attempt; the set ends itself after 8 s idle. **Bar speed** is mean concentric velocity: m/s when the scale is known (camera: lifter's height and leg or arm length; motion: integrated), otherwise degrees a second. **Reps in reserve** is a rough estimate from velocity loss (after Sánchez-Medina and González-Badillo 2011).
- **Camera:** MediaPipe Pose Landmarker Lite (33 points, Apache 2.0) in the web view, GPU delegate with a CPU fallback, loaded on first use (runtime from jsDelivr pinned to the npm version, model from Google's bucket; self-host both, see Open items). Joint angles per exercise come from `profiles.ts` (knee for squats, hip for hinges, elbow for presses, rows and curls, shoulder for raises); a side view is the setup we ask for. Frames are read in memory and dropped: **video never leaves the device and is never recorded.**
- **Motion:** `imu.ts` prefers the platform's fused data (vertical linear acceleration plus rotation rate; DeviceMotionEvent now, CMDeviceMotion on watchOS and Wear OS linear-acceleration sensors later) and falls back to raw |a| - g. Zero-velocity resets at still moments and a snap back to rest at lockout keep double-integration drift from building up. Lifts where the hands don't move (pull-ups, dips, push-ups) get no motion profile.
- **Accuracy is measured on simulated sets** (`simulate.ts`, `evaluate.ts`; pass marks in `reps.test.ts`; full report with `REP_ACCURACY=1 npx vitest run src/lib/reps`). Real recordings with hand-counted truth must replace them before this ships.

### Heart rate and health
- **Live heart rate comes over Bluetooth**, not Health Connect, because Health Connect gets Fitbit data in batches, often minutes late. Any standard heart rate broadcaster works (Heart Rate Service 0x180D): Fitbit Charge 6 and Pixel Watch "share heart rate", Polar, Garmin, Wahoo straps (`heartRate.ts`).
- **Health Connect** (Android) and **Apple Health** (iOS) go through one plugin, `@capgo/capacitor-health` (`src/lib/health.ts`). Reads (weight, height, body fat, resting HR, plus sleep, HRV, steps, VO2 max and respiratory rate for the health twin; nothing else, see "Google Play review" below) prefill the wizard's body weight step ("Fill in from Health Connect / Apple Health"). Finished workouts are written as active calories (about 5 METs) and average HR, because the plugin can't write workout sessions yet. The Android Health Connect privacy rationale is `public/privacypolicy.html`.
- **Connecting never fails silently or hangs** (Melvin, 2026-11-09, after a Fitbit Air showed in Chrome's picker and then nothing happened). `connectHeartRate` times out each step (10 s connect, 8 s service, 30 s for a pairing prompt), retries the GATT connect up to three times (Chrome's first connect to a watch often fails or never answers), and throws an `HrError` whose `problem` is `cancelled`, `bluetoothOff`, `blocked`, `unreachable` (in use by another app or machine, or out of range), `noService` (no standard 0x180D service), `pairing` or `failed`. The workout's Connect button and the setup tile show "Connecting…" and then `hrMessage`'s plain-words reason (a closed picker shows nothing); for a Fitbit or Pixel Watch the message adds how to turn sharing on (Fitbit Air, Edge, Charge 6: Google Health app › Connections › the device › Share heart rate › Get started; Pixel Watch: Connected Fitness in quick settings). If notifications fail on Android and the device isn't bonded, the app asks Android to pair (`createBond`) and tries again; iOS and browsers show their own pairing prompt when the watch asks. Same code on Android, iOS and the web.
- Native heart rate uses `@capacitor-community/bluetooth-le` on both platforms (keeps reading with the screen off; iOS has the `bluetooth-central` background mode). The web build keeps Web Bluetooth.

### Google Play review (Melvin, 2026-11-09; audit: https://claude.ai/artifact/5YAP14XHLSZUfXbcEWD4hS)
- **Ask only for health data a feature uses today.** Play's Health Connect review rejects any permission the app doesn't visibly use. `READ` and `WRITE` in `health.ts` are the list (reads: weight, height, body fat, resting heart rate, and for the health twin sleep, HRV, steps, VO2 max and respiratory rate; writes: active calories, heart rate), and the manifest strips every other permission the health plugin adds (`tools:node="remove"`). The same list drives HealthKit, and the iOS usage strings match it. Sleep, HRV, steps, VO2 max and respiratory rate came back with the health twin (2026-11-09), each visibly used there, and declared in `health.ts`, the manifest, both privacy pages, `docs/PRIVACY_LABELS.md` and the iOS strings. A new type goes in all of them in the same change, with a screen that uses it. `storePolicy.test.ts` fails when the manifest and `health.ts` disagree.
- **Precise location stops at Android 11** (`maxSdkVersion="30"`), where scanning for a Bluetooth heart rate monitor still needs it; Android 12+ scans with `BLUETOOTH_SCAN` (`neverForLocation`) and the app asks only for approximate location.
- **The privacy pages carry the Health Connect Limited Use statement and a contact address** (`CONTACT_EMAIL` in `site.ts`, hello@getliftsmith.com). The policy URL for the store listing and the Health Connect form is https://www.getliftsmith.com/privacy/. `public/privacypolicy.html` is also the in-app Health Connect rationale (loaded from the app's assets), so its links are absolute.
- Melvin's developer account doesn't need Play's 12-tester closed test.

### Integrations roadmap (Melvin agreed, 2026-11-09; research: https://claude.ai/artifact/UoDvYPVgFxt8wwPuJJS7KH)

The reply-to is the sender's email, so the owner can answer straight from the inbox. CORS allows only the native shells' origins.

### Cycle-aware readiness (Melvin, 2026-11-09; built)
- **Opt-in, with its own consent sheet** (Settings › Cycle-aware readiness › Set up). The sheet says what is logged, that it stays on the phone (only the user's own backup/sync moves it), that it is never used for analytics or ads or included in feedback reports, that it isn't medical advice, contraception or a fertility tool, and that turning it off deletes it. `profile.cycle.consentAt` records the agreement.
- The lifter logs the first day of a period with one tap ("Period started today" / "Started yesterday"), stored as `cycle` events. `src/lib/cycle.ts` estimates the cycle day and phase from their own median cycle length (gaps of 21 to 45 days, default 28), and says nothing if nothing was logged in the last two cycles.
- It feeds `readiness.ts` as a small nudge the lifter can override: period days −5 ("go by feel"), late luteal −4, follicular +3, otherwise 0. The effect is small on purpose, because the evidence is mixed and individual.

### Injury mode (Melvin, 2026-11-09; built)
- The lifter logs an injury by body part (15 parts: neck, shoulder, elbow, wrist or hand, chest, upper back, lower back, abs or core, hip, groin, front of thigh, hamstring, knee, calf, ankle or foot) from Today ("Something hurts?"), Settings, or the swap sheet mid-workout. Screen: `#/injuries` (`src/components/app/Injuries.tsx`); rules: `src/lib/injury.ts`.
- **Matching is deliberately broad** (better to skip one exercise too many): an exercise is affected when the part's muscles are primary (or, for some parts, secondary), its movement pattern loads the joint (knee: squats and lunges; lower back: hinges; shoulder: vertical presses and pulls), or it is listed by id. Each affected exercise can be marked "Doesn't hurt".
- **Default is skip** until the lifter taps "I'm fully healed". Instead they can keep one exercise, or all of them, **lighter at 50, 60, 70, 80 or 90%** of the usual load (default 70). Lighter means the load rounded down to one the gym can make (reps for bodyweight and timed work), at least 3 reps in reserve, no filler sets, never the push-day exercise or a challenge, and it isn't lightened again on an easy day.
- **Every move from skipping to training** (lighter or "doesn't hurt") shows a risk warning that needs "I understand the risks" ticked; the acknowledgment is stored on the event (`ack`). Changing the share while already lighter doesn't warn again.
- **Wording is neutral and never diagnoses.** Every injury screen says Liftsmith isn't a medical app, this isn't medical advice, and a doctor or physiotherapist can say what's safe, and lists the stop signs (sharp pain, pain that builds, swelling, numbness, tingling, a joint giving way).
- **Swaps:** skipped exercises never appear in swap lists, and ones that avoid the injured area are listed first. The injury card shows two that avoid it for each skipped exercise. Logging or changing an injury mid-workout swaps (or drops) the exercises not started yet and re-targets lighter ones.
- **Progression** ignores sessions done lighter (`SetEvent.injuryPct`), so after healing the plan picks up from before the injury. The healed sheet tells the lifter to ease back in and use "Too hard" feedback.
- Stored as `injury`, `injuryRule` and `injuryHealed` events, derived in time order so devices merge cleanly. Injury data is health data: it stays on the device (and the user's own sync) and is never sent to analytics or feedback reports.
- **Programs and routines honour it too** (`injuryPass` in `generator.ts`): on a fixed program day or a saved routine, a skipped lift is swapped for the closest exercise that isn't skipped, keeping the program's sets, reps and lift slot (or dropped if nothing fits), and a lighter lift is scaled set by set with no AMRAP. Split programs plan through the generator, so they get it there. Sets done lighter never move a program lift (`programSessions` ignores them).
- **Free, not Pro**, because it's a safety feature. Pure web layer, so it is identical on Android, iOS and the web (parity).
- **Pain ratings (0–10)** (folded in from the coaching-features thread's "pain-aware training", Melvin picked it 2026-11-09): asked right after logging an injury (skippable), any day on the injury card ("How does it feel today?"), once per exercise per workout during the rest after a set of an exercise trained despite the injury (lighter, marked fine, or in a graded return), and on the summary after a workout. Never during a set. Stored as `pain` events (with the session and exercise when there is one). The card shows a sparkline of the last 14 ratings with a dashed line at 2, the latest score and the change.
- **Graded return** (`gradedReturn`, `returnReady` in `injury.ts`): offered once pain has stayed at 2 or below for about a week (low ratings going back 6+ days, the latest within 4 days). Starting it shows the same risk warning and needs the tick (`injuryReturn` event with `ack`). Skipped exercises then come back lighter: 50%, then 70%, then 90%. Each step lasts at least a week and needs a rating of 2 or less in it to move on; a 3 or 4 restarts the week; 5 or more stops the return and the exercises are skipped again until pain settles and the lifter starts it again. After a week at 90% with low pain the card suggests marking it healed, which stays the lifter's call. Exercises the lifter set to lighter or "doesn't hurt" keep their own choice.

### Reminders and lifecycle messages (Melvin, 2026-11-09; built)
- **What:** workout reminders, a missed-day nudge, streak alerts, comebacks, milestones and Pro offers, by phone notification and by email, to keep people training and help conversion. One pure planner (`src/lib/messages.ts`) decides what goes out and when for both channels; the phone (`src/lib/reminders.ts`) and the server (`src/server/reminders.ts`) only deliver.
- **Kinds** (each has its own switch in **Settings › Reminders**, separately for push and email, `MessageSettings.tsx`):
  - *Workout reminders:* push on each training day at the workout time (Settings › Calendar's days and time; defaults spread the days-a-week goal at 18:00), skipped once there's a workout that day. The first one before any workout reads "Your first workout is ready". By email, one Monday 08:00 note with the week's days and last week's count, not one a day.
  - *Missed workouts:* once per lapse, the morning after the first missed training day (by email, the second), and only if that morning isn't a training day itself (its reminder says it). Then a check-in after 7, 14 and 30 quiet days (counted from setup if there's no workout yet), and nothing more.
  - *Streak alerts:* when the week's goal needs a workout on every day left and there's a streak of at least one week to keep. On a training day it's folded into that day's reminder. Streaks count weeks (game.ts `goalStreak`), so nothing asks anyone to train on a rest day.
  - *Milestones:* email only (the app already celebrates in the moment): the first workout, sent right away when the phone reports it, and streaks of 4, 8, 12, 26 and 52 weeks.
  - *Pro trial and offers:* two days before a trial ends ("or do nothing and stay on the free plan"), then four offers about what Pro adds, 3, 17, 31 and 59 days after the trial ends or is declined, then none. **Off by default on both channels** (Apple 4.5.4 needs explicit opt-in for promotional pushes; GDPR and CASL need it for marketing email). **None go out until billing is live** (`billingLive()` in `billing.ts`), because until then everyone has Pro and an offer would be misleading. Once it is, trial and Pro state come from the store entitlement (`storePro`).
  - *Welcome:* the email after confirming, always sent (it's the confirmation of the sign-up).
- **Caps and quiet hours:** at most one message a day per channel; nothing between 21:00 and 08:00 except the reminder at the time the lifter picked (06:00 to 21:00). Email also caps at three a rolling week and one Pro email a fortnight (`CAPS`). Priority on a busy day: reminder, streak, missed, Pro.
- **Push is local, not FCM/APNs.** Every message can be worked out on the phone from its own data, so the phone schedules the next 14 days with `@capacitor/local-notifications` (Android and iOS) when the app opens, comes back to the foreground, a workout ends or a setting changes. It works offline and needs no account, server, Firebase project or APNs key. Android uses its own "Reminders" channel (mutable on its own) and inexact alarms, so the lifter is never sent to the "Alarms & reminders" screen. On iOS, `WorkoutSessionPlugin.swift` owns the notification delegate and passes everything that isn't the workout's own notification to Capacitor's router, so reminder taps open the app on the right screen. Remote push (FCM/APNs) waits for a message the phone can't compute (friends, coach sharing); it will need a Firebase project and an APNs key.
- **The web app has email only** (Platform deltas).
- **Email is double opt-in.** Settings asks for the address and a consent tick (offers stay off), then `POST /api/reminders/` stores the subscription as pending and sends a confirmation email. Only the button on the confirmation page (a POST, so mail scanners that open links can't sign anyone up) confirms it and sends the welcome. Three confirmation emails a day at most per subscription, and the routes rate-limit per address. Changing the address or turning email back on after unsubscribing asks again.
- **What the server keeps** (`reminder_subs` and `reminder_sends`, `src/server/remindersDb.ts`, in the same database as analytics): the address, which kinds are on, when the lifter agreed, and the planner's numbers only: training days and time, time zone, days a week, setup time, last and first workout times, days trained this week, streak weeks and Pro state. **No workouts, weights, heart rate or health data.** The device keeps a random subscription id and secret in localStorage; the server stores only hashes of it and of the confirmation token. `account_id` is nullable so accounts can claim the subscription later and send the same fields from sync.
- **Scheduling:** a Vercel cron (`vercel.json`, once a day at 00:05 UTC, which works on every Vercel plan) runs `GET /api/cron/reminders/` (`CRON_SECRET`), plans each confirmed subscriber's next 26 hours in their own time zone and hands each email to Resend with `scheduled_at` and an idempotency key. When the phone reports a change (say, a workout that makes a missed-day nudge wrong), the server cancels the scheduled emails that no longer apply and schedules any new ones. If the phone is offline after a workout, a scheduled nudge can still go out; that's accepted.
- **Every email** carries a one-click unsubscribe link (an HMAC of the subscription id, so the token is never stored) and the `List-Unsubscribe` and `List-Unsubscribe-Post` headers (RFC 8058, required by Gmail and Yahoo for bulk senders), says why it was sent and where to change it, and includes the postal address (CAN-SPAM, CASL). The routes refuse to send without `MAIL_POSTAL_ADDRESS`. Unsubscribing stops everything and cancels what's scheduled; the app's syncs can't quietly resubscribe. **Stop all email and delete my address** in Settings, and **Erase this device**, delete the row and its history from the server.
- **Server environment:** `RESEND_API_KEY`, `MAIL_FROM` (a sender on a domain verified in Resend, e.g. `Liftsmith <coach@getliftsmith.com>`), `MAIL_POSTAL_ADDRESS`, `REMINDER_SECRET` (a long random string for unsubscribe links), `CRON_SECRET`, and the database. Without them `/api/reminders/` answers 503 and the app says it couldn't reach the server.
- **Later:** switch the streak alert to the gamification thread's `goalStreak` `atRisk` flag and freezes once that lands; a weekly-quest "almost done" nudge; win-back and receipts by email once accounts and billing exist.

### Coaching features (Melvin picked them, 2026-11-09; built)
From a ranked list of features Fitbod, Hevy, Strong and StrongLifts don't have. All run in the shared web layer, so Android, iOS and the web app get them in the same change; only remix links differ (see Platform deltas).
- **Why this weight** (free, `src/lib/explain.ts`, `CoachExtras.tsx`). Tapping "Why?" under the target opens the reasons in plain words: why this exercise today and any change to the set count (taken from `why.ts`'s `itemWhy`, the same words as Today's plan), last session's sets, the double-progression rule that applied, feedback, the block week's RIR, today's push or easy call, and how the plates round it. It reads the same data as `progression.ts` and never changes the plan. Fitbod's most common complaint is that it's a black box.
- **Change the plan mid-workout** (Pro, `can("replan")`, `src/lib/replan.ts`). The ⏱ button: "N min left" trims sets from the least important exercises first (core and isolation, then later ones; never below 2, never under what's done on the current one), then drops whole exercises from the end; the current exercise is never removed. "Bench or rack taken?" moves the exercise after the next one (only before its first set) or swaps it for one that needs other equipment, through the normal swap (so swap events and injury rules still apply). Bars, bands and small gear don't count as "taken".
- **Plateau detective** (Pro, `can("plateauDetective")`, `src/lib/plateau.ts`, shown as coach's notes on Today and Progress through `insights.ts`). A weighted lift is stalled when its estimated one-rep max hasn't come within 1% of its best for 3 weeks, with 5+ sessions overall and 2+ recently, outside a deload. Causes come from the lifter's own data, strongest first: missed reps (30%+ of sets), "too hard" feedback, weekly sets for the muscle under 70% of the block target, rest under 75% of plan, readiness averaging under 42, or the same rep range for 4+ sessions. Each maps to a three-week fix: reset (about 10% lighter once, then rebuild), a different rep range, one extra set, a minute more rest, or a close variation. Fixes live on `profile.plateauFixes` and are applied to the plan after `generate()` (`applyFixes`, called from `store.replan`), so the generator stays one thing. After a fix ends, a coach's note says whether it worked. A lift isn't re-diagnosed while a fix runs or for a week after.
- **Goal-date planner** (Pro, `can("goalPlanner")`, `src/lib/goals.ts`). Melvin: "it should be realistic". Goals are one-rep maxes by a date (`profile.goals`). The forecast blends typical monthly gains by experience (new 4%, intermediate 1.5%, advanced 0.6%; slowing each month, nothing added in deload weeks) half and half with the lifter's own 12-week trend, which is capped at twice the typical rate so one good month can't promise too much. It shows a range (half to one and a half times the rate) and says "very likely", "on track", "a stretch" or "not realistic", and when it isn't, the likely date and what's realistic by the date. In the last two weeks it gives taper advice and three loadable attempts (90% and 96% of the expected max, then the goal only if the forecast supports it).
- **Workout remix links** (free, `src/lib/remix.ts`, `Remix.tsx`, route `#/remix/<code>`). "Share this workout" on the Done screen makes a link holding only exercise ids, sets, reps and rest (format `1~id.sets.reps.rest~…`, at most 20 items; no weights or anything personal). Opening it rebuilds the workout for the opener's gym (swaps to the closest available exercise, or leaves it out) at their own weights: their history's estimated max at the shared reps. Unknown exercises and bad numbers are dropped.
- **What to buy next** (free, `src/lib/buying.ts`, `BuyNext.tsx`, Gyms screen, home gyms only: under 15 equipment items). Plate pairs ranked by running out of plates first, then a smaller jump (aiming for a 2.5 kg or 5 lb total jump), then more loadable weights up to 25% past the heaviest recent barbell set; and equipment that unlocks the most exercises and first loaded work for a muscle (big machines left out). "I got them" / "I have it" adds it to the gym. Advice only: no shop links or sponsored picks (no ads, ever).
- **Machine settings memory** (free, `src/lib/machineSettings.ts`). "Save setup" under the exercise name: up to 4 labelled values per exercise per gym (seat, pads, foot position, pulley height, J-hooks, bench angle…), offered from the equipment the exercise needs, stored on `gym.settings` (last-write-wins with the gym) and shown as "Seat 4 · Back pad 2" before the first set.
- **Pain-aware training** was picked too; the injury mode thread owns it (pain rating, trend and graded return on top of injury mode).

Tapping one opens its last 30 days against the lifter's **own normal** (the 30 days before today, mean ± one SD, needs 7 readings), never against other people. - **TDEE:** with 5+ of the last 7 days of steps, the activity level comes from steps and training together (`withSteps` in `tdee.ts`: the higher of the two, one up when 7,500+ steps and 3+ training days; source `steps`).
- Glossary entries: health twin, HRV, resting HR, breathing rate, VO2 max, lean mass, BMI, rest drop. Not medical advice, said on the screen and every sheet.

### Fitness age (Melvin asked, 2026-11-09: "estimate how healthy somebody is or their biological aging" without becoming a medical device; Melvin picked VO₂-max fitness age, 2026-11-09; built)
- **Decision doc: `docs/FITNESS_AGE.md`** (options, evidence, FDA and Health Canada framing, sources). Melvin picked option 1. **No composite "health age" or "biological age"** from resting HR, HRV, sleep and steps: no validated formula combines consumer-wearable readings, and HRV differs between Android (RMSSD) and iOS (SDNN).
- **What it is:** the age at which a typical healthy person of the lifter's sex has their VO₂ max (`src/lib/fitnessAge.ts`, pure and tested). Reference: the HUNT 3 Fitness Study's treadmill VO₂ max means by sex and ten-year group (Loe et al., PLoS ONE 2013, Table 2: 3,816 healthy adults), placed at each group's middle (70+ at 75) and joined with straight lines; answers stay within 20 to 80 ("20 or younger", "80 or older"). The VO₂ max used is the median of the newest five readings from the last 120 days. Shown as "About N" with a range for a reading 8% higher or lower (`READING_SPREAD`; watch estimates are typically 5 to 15% off a lab test), and a chip: fitter than typical (3+ years younger, the good token), about typical, or "Room to build" (never a warning colour). Needs a VO₂ max reading, a birth year and a sex; otherwise it says what's missing (age and sex link to the TDEE tool, where they're edited).
- **Where:** a card on Body › Health (`FitnessAgeCard` in `HealthTwin.tsx`), between the figure and the metric groups, with what moves it (hard cardio twice a week), this week's strength-training days and minutes against the guideline of 2+ days a week (`strengthWeek`), the strength score, a "How is this worked out?" sheet and the general-wellness note. Free, like the rest of the twin. Glossary term `fitnessAge`; text in `fit.*` in all three catalogues. The a11y run scans the sheet.
- **Wellness rules (keep them in any change):** FDA General Wellness guidance (6 January 2026) and Health Canada's software-as-a-medical-device guidance. Call it "Fitness age", never biological, health, heart or real age; no disease names, mortality or "live longer" claims anywhere (app, glossary, store listing, marketing); no "abnormal", "at risk", clinical thresholds or red or amber states; never a notification; always a range, its source and how it's worked out; always paired with what to do; a standing line that it's a general wellness estimate, not medical advice, and that a doctor may be helpful with health concerns (never triggered by a value). `FitnessAge.test.tsx` fails on disease or warning words in the card. It stays on the device like all health data. **Before its first store release, a regulatory lawyer reads the card and sheet text** (Open items).
- VO₂ max already comes through `health.ts` on both platforms, so Android and iOS get it from one build with no native code; the web app says to open Liftsmith on the phone, like the other health-store metrics (Platform deltas: Health twin).

### Stats and recovery map
- **The recovery map is the exercise demos' 3D figure** (Melvin, 2026-11-09: "use the same 3d models with the muscles highlighted, fall back to 2d if the device doesn't support it"). `RecoveryMap.tsx` (Recovery screen and Today's "Why these muscles") shows the standing hologram figure (the body from Settings' sex, male when unset) with every muscle drawn **inside a glass body as a glowing volume** in its recovery band's colour (Melvin picked this "glow" style from four samples, 2026-11-09), Front / Back buttons, and drag to turn. It uses the demo engine (`engine.ts` `paint`, `hatch`, `selected`, `calm`; `scene3d.ts`), with these changes for a map: each muscle's patch of skin is pulled in toward its limb's core with a belly shape, and triangles that cross between two muscles are left out so each muscle stands apart; a hidden depth-only core inside the muscles so the far side never shows through; the skin turns to a faint neutral wireframe (so Fresh green and the colour-blind blue can't be mistaken for the hologram's cyan); and the band colours taken from the **dark** theme's tokens (`STAGE_BANDS` in `colours.ts`, kept equal to `globals.css` by `a11y.test.ts`) because the stage is always dark; Settings › Accessibility › Colour-blind safe switches it to the `-cvd` set. **Fatigued muscles also get stripes**, and the legend shows that mark, so colour is never the only cue; the canvas's label lists every band's muscles in words. Turns snap instead of easing in Lean mode or with reduced motion, and nothing else moves. Same WebGL check as the demos (`detectMode`); **without WebGL (or if the 3D scene fails) it falls back to the 2D map** (`src/components/BodyMap.tsx`, front and back with dots and stripes).
- **Tap a muscle to see what to do** (action over stats; `src/lib/muscleAdvice.ts`): on the figure (the engine picks the painted muscle nearest the camera under the finger), in the Recovery screen's muscle list, or in the band list under the map. It says the call and why from the same model the generator plans with: rest it or go light, with when it's back to Ready (70%, found by searching the recovery curve), or how many sets are left of this week's goal, or that the week's sets are done; plus when it was last worked. A recovered muscle with half or more of its weekly sets left offers **Make it a priority** (`togglePriority`). The 3D map, picking and advice are pure web code, so Android, iOS and the web get them together. The recovery map is Pro (see Money); the billing work adds the gate.
- Stats: weekly sets per muscle against the target, estimated one-rep max trends, PRs, volume, session history, streaks and trophies.
- **One-rep max calculator** (Melvin, 2026-11-09: "use the latest research and algorithms, use as much existing data as possible"; `src/lib/onerm.ts`, `OneRepMax.tsx`). Every exercise with data is on Progress; tapping one opens its estimate, likely range and confidence, the set it leans on, a reps-to-weight table and a "try a set" calculator with every formula's answer.
  - Reps to failure = reps + RIR. The RIR is the lifter's reported effort, else 0 for AMRAP, challenge and missed sets, else the plan's RIR less any extra reps, else 2 for web-logged and imported sets (counted for less).
  - Formula by rep range: up to 10 reps to failure, the mean of Brzycki, Epley and Marzagao's 2026 weight-dependent equation (arXiv 2603.17495, fitted on 303,494 near-failure sets); above 10, Mayhew, Wathan and Marzagao. Sets past 20 reps to failure are ignored; high-rep, far-from-failure and guessed-RIR sets count for less.
  - Each session's best set is one point. Today's max is the quality- and recency-weighted mean (6-week half-life) of the best three points from the last 6 months, after a detraining mark-down (none for 3 weeks, then about 1% a month). The setup max is used only until a lift has logged sets.
  - The strength score and strength twins use the same estimate (`strength.ts` calls `oneRm`), so the cards on Progress agree. PRs and XP stay on plain Epley (`derive.ts`, `game.ts`) because they are recomputed from all history and a new formula would quietly add or remove earned PRs, XP and badges (Melvin agreed, 2026-11-09).
- **DOTS score** (Melvin, 2026-11-09) from the estimated back squat, bench press and deadlift maxes and the latest weigh-in, with the published DOTS coefficients (men's or women's). When the profile has a sex set (setup or Settings), the card uses it and hides the formula picker; the Men's / Women's chips show only when sex isn't set (Melvin, 2026-11-09). Needs all three lifts; the lifter can bump any number with steppers to see "what if". Rough bands: 200 novice, 300 intermediate, 400 advanced, 500 elite.
- **Calculators take no typing** (Melvin, 2026-11-09): steppers with − and + buttons, chips for reps in reserve, a picker for the exercise.

### Tools: TDEE calculator (Melvin, 2026-11-09)
- **Tools** (`#/tools`, from Progress and Settings) holds calculators that use what the app already knows. First is **TDEE** (`#/tools/tdee`, `src/lib/tdee.ts`, `src/components/app/Tools.tsx`). The same engine powers a public page, `/tools/tdee-calculator/` (with `/tools/` as the index), for search.
- **Formulas:** Mifflin-St Jeor for BMR, or Katch-McArdle when a body fat reading is known (lean mass suits lifters). TDEE = BMR × the standard activity factor (1.2, 1.375, 1.55, 1.725, 1.9). Results also show BMI, a cut (TDEE − 500, never below BMR), a lean bulk (+250), protein at 1.6 to 2.2 g/kg, and the TDEE at every activity level.
- **Automatic, as far as possible.** Weight is the latest weigh-in; age comes from the birth year; height and body fat are new profile fields (`heightCm`, `bodyFat`). On native, weight, height and body fat are read from Health Connect / Apple Health on every open (`readBody` in `health.ts`; same plugin on both platforms, so no native code). A newer health weight becomes a weigh-in whose id is its measurement time, so repeated reads never duplicate it.
- **Activity level from real training:** training days a week (distinct days, so doubles don't inflate it) over the last 4 weeks: 0 sedentary, 1–2 light, 3–5 moderate, 6–7 heavy, 10+ sessions a week athlete. Until there are two weeks of history it uses the days-a-week goal. The lifter can pick a level by hand; Auto goes back.
- **Tracked over time:** a `tdee` event is recorded whenever weight (0.5 kg+), age, height, sex, body fat or activity level changes, with what changed. `App.tsx` checks 2 s after any change to events or profile. The screen charts one point a day (step line to today) and lists every change. The current value is always computed fresh; the events are the history.
- **Minimal typing (Melvin's rule):** sex, activity and body fat on/off are chips; numbers use the shared `BumpField` (hold to repeat), in the app and on the public page. An empty box starts from a typical value (30 years, 177 cm for men, 163 cm for women). Weight saves one weigh-in 1.5 s after the last change, so holding + doesn't log dozens.
- Not yet: adaptive TDEE from weight trend plus logged food (needs calorie intake), and steps from Health as an activity input.

### Engagement and juice (owner request, 2026-11-09)

- **The line we hold:** no tricks in billing (plain prices, cancel in two taps, no fake countdowns or pre-ticked upgrades), no notifications that pretend to be something else, and no reward for training a muscle marked Fatigued. Juice goes around and between sets, never adds taps during one. All motion respects `prefers-reduced-motion`.

- **Built (2026-11-09, gamification thread):**

Friend leaderboards wait for accounts and sync.

  - **Lean mode** (`profile.lean`, runtime `juice.lean`, Settings › Celebrations): no confetti, celebration sounds, count-ups or pop-up motion. Rest-timer sounds and haptics stay. XP, streaks and badges keep counting.

### Programs (Melvin, 2026-11-09; built)
- Settings › Program (`#/programs`) picks how Today is planned: **Adaptive** (the default), a **fixed program**, or a **split**. The engine is `src/lib/programs.ts`; the choice is `Profile.planSource` (`adaptive` / `program`; a `routine` kind is reserved for a routine followed as the standing plan). A saved routine picked for today (`routines.ts`) replaces that day's plan, adaptive or program, and doesn't count as a program day, so the program's next day stays next.
- **Fixed programs follow their own published rules**, not readiness or RIR blocks: no length slider and no push/easy call on Today. Classic 5×5 (A/B, +2.5 kg a session, +5 kg deadlift, −10% after three misses in a row), Novice 3×5 (squat every session, +5 kg squat and deadlift, power cleans 5×3 replace the B-day deadlift after six sessions), 5×5 plus arms (5×5 plus 3×8 accessories), Ramping 5×5 (heavy / light / top-set days ramping 12.5% a set, a triple 2.5% over the top set that becomes next week's top, miss and repeat the week), Tiered progression (T1 5×3+ → 6×2+ → 10×1+ → restart at 85%; T2 3×10 → 3×8 → 3×6 → 3×10 at the last 3×10 weight + 7.5 kg / 15 lb; T3 3×15+, add weight at 25), Training max waves (TM 90% of e1RM, 65/75/85, 70/80/90, 75/85/95 and a deload, 5×10 at 50% plus one assistance lift, TM +2.5/+5 kg a cycle or −10% after a short last set) and Bodyweight skills (ladders for pull-up, squat, dip, hinge, row, push-up and core; 3×5–8, step up after 3×8; holds 20–60 s).
- **Splits** (push/pull/legs, upper/lower) pass each day's muscles to the adaptive generator (`GenerateInput.muscles`): only exercises whose main muscles are all in the day, muscles at 40%+ recovery, and they keep RIR blocks, deloads, readiness and the length slider.
- **Progress is derived, never stored.** The starting weights are frozen when a program is picked (`planSource.start`, from the lifter's own logged sets, else `startE1rm`), and the current weights come from replaying the program's sessions (`sessionStart.program`). Each set records the program lift it counts for (`SetEvent.slot`), so swaps and stand-in exercises keep the lift's progress, and `amrap` marks "as many as you can" sets. When the lifter lifted what was planned, the next weight builds on the exact planned weight, so small jumps the plates can't make yet still add up; when they changed it, on what they lifted.
- **After a break** the first session of a fixed program starts lighter (see "Starting lighter after a break" under Training engine), then the program rebuilds from there.
- Per-set targets (`PlanItem.setTargets`) drive ramps and percentages: the workout screen loads each set's weight and shows a banner on AMRAP sets. Programs run through `withWarmups`; ramped lifts keep only the empty-bar warm-up, since their first sets are the warm-up.
- A lift the gym can't do is swapped for the closest exercise it can, at a weight scaled by the two exercises' usual loads, with a note on Today. Ladder steps the gym can't do are skipped. Ladder-only steps (`LADDER_ONLY` in `exercises.ts`) stay out of adaptive plans.
- **Names (trademark check, 2026-11-09):** STARTING STRENGTH, JIM WENDLER 5/3/1 and STRONGLIFTS are registered US trademarks; no registrations found for Madcow, Ice Cream Fitness or GZCLP. Every program has a plain descriptive name, credits the original in its info text ("Based on Starting Strength by Mark Rippetoe"), and the picker says the names belong to their owners. Never use a trademarked name as a program's name (a test checks this).
- The picker shows each program's steps, credit, level, days a week, tier, a typical week of hard sets per muscle, and any kit the active gym lacks.
- Web-layer only: no native code, so both apps get it from the same build.

Small things that make the app a pleasure, all derived from events (never stored), all between sets or optional (never an extra tap during a set), and quiet in lean mode. The badges for tonnage and comebacks belong to the gamification work (`achievements.ts`); these files only celebrate.
- **Lifetime tonnage** (`moments.ts`): a running total on Progress and "you've lifted a ..." milestones (grand piano 500 kg up to the Eiffel Tower's iron 7,300 t), each labelled "about".
- **Anniversaries and comebacks** (`moments.ts`): "1 year since your first workout" on Today (29 February is celebrated on the 28th), a warm welcome back after 14+ days away (readiness already eases the plan after 10), and "comeback complete", workout-count and tonnage moments on the summary.
- **Monthly recap and year in lifting** (`recap.ts`, `#/recap`): workouts, volume, sets and reps, PRs, top lift and muscle, favourite day and time of day, heaviest bar, change against the period before, average heart rate. Last month is offered in a month's first week; the year from 26 December to 7 January. Shared as text for now; it moves to the gamification share card (`shareImage.ts`) once that lands.
- **PR replay** (`PrReplay.tsx`): on the summary, each new best replays rep by rep: the 3D figure (`LiftDemo`) performs the lift that many times, with the lifter's own bar and plates underneath and a rep counter. Reduced motion shows a still pose.
- **Smart plate memory** (`plateMemory.ts`): what's on the bar is the last set or warm-up of the exercise this session; plates go on heaviest first, so the shared inside run stays and only the outside changes ("Take off 2.5, then add 5 kg each side").
- **Ghost mode** (`ghost.ts`): the last session of the exercise races along on the rest card: its weight, reps and rest for this set, and how far ahead or behind the lifter is. On by default.
- **Same as last time** (`ghost.ts`): one tap on Today repeats the last workout's exercises and set counts (weights still come from progression, exercises the gym can't do are dropped); on the set card, one optional tap uses last time's numbers.
- **Voice coach** (`voice.ts`, `VoiceCoachPlugin` on both platforms): off by default. Says the next set ("Set two of four. 100 kilos for 8. two in reserve."), the last set, ten seconds left, a new exercise, a new best and the end of the workout. Music is ducked while it talks. See Platform deltas.
- **Rest extras** (`WorkoutExtras.tsx`): a breathing guide (in 4 s, out 6 s, to bring heart rate down) or a plate-math mini-game built from the gym's own plates. Off by default; picked on the rest card or in Settings.
- **General warm-up** (`warmupRoutine.ts`): "Warm up first" on Today builds about five minutes of movement prep (a pulse raiser, then drills for today's muscles, only what the gym's equipment allows), seeded by day. It complements the per-exercise warm-up sets in `warmup.ts`.
- **Strength score and strength twins** (`strength.ts`): each lift's best estimated max from the last 6 months against a typical intermediate of the same body weight (`Exercise.start`), optionally adjusted for age (masters-style coefficients, on by default when a birth year is known) and sex. 50 is typical, 75 twice as strong. Twins shows "stronger than about N%" on the big lifts. **It's an estimate from standards, not a ranking of real users**, and the app says so; real rankings need accounts.
- **Earned themes and app icons** (`themes.ts`): full palettes unlocked by milestones (Forge at 12 t, Glacier at 25 workouts, Volt at 10 PRs, Aurora at 8 goal weeks, Rose at 50 workouts, Abyss at 150 t, Royal at the first liftiversary), plus seasonal Pumpkin (October) and Frost (December) open to everyone. A cosmetic accent from the gamification work wins over a theme's accent. Four themes come with an app icon (Forge, Glacier, Aurora, Royal), drawn by `scripts/make-icons.mjs` with the main icon (see "App icon and favicon"): Android launcher aliases (`AppIconPlugin.java`, `.Icon*` in the manifest; static shortcuts sit on every alias) and iOS alternate icons (`AppIcon-*` sets, `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES`). A test checks every theme's text contrast (WCAG AA).
- **Body weight and progress photos** (`photos.ts`, `#/photos`): weigh-ins are `bodyweight` events (synced like other data) and update the profile. **Photos never leave the phone**: their own IndexedDB database, outside the event log, so sync, backups, analytics and feedback never see them; shrunk to 1440 px JPEG, which drops location data; erased with "Erase this device". Front, side and back, with a before/after slider. iOS asks for the camera with `NSCameraUsageDescription`.
- **Gym buddy check-ins** (`buddy.ts`): buddy names only (no contacts), one tap records a `checkin` event and opens the share sheet with a short message. When accounts and sync arrive, the server turns the same event into a push nudge on each buddy's phone.
- **Holiday and seasonal challenges** (`seasonal.ts`): dated windows in local time (fresh start week, spring, solstice, back to it, Halloween "6.66 t", twelve days of lifting, last rep of the year), counted from workouts, sets, days or tonnage, never per muscle. Shown on Today in the window; no XP or badges here (the gamification code may add XP from `seasonalChallenges()`; its own date badges cover 1 Jan, 29 Feb, 14 Mar and 31 Oct).
- Settings: Voice coach, Ghost mode, Smart plate memory, While you rest, Themes, App icon (native). All live in `profile.delight`.

### Accounts and sign-in (built, 2026-11-09; Melvin chose to build them after "it's not clear how to save my information" on mobile web)
- **Accounts are optional.** The app works fully offline with no account; signing in turns on backup and sync. Everything stays on the device either way: signing out keeps the device's data and only stops syncing.
- **Where:** Settings' first row, **Account and sync** (`#/account`, `Account.tsx`), and "Already use Liftsmith? Sign in" on setup's first step (a sheet with the same `AccountPanel`). Signing in on a new device during setup pulls the account's profile, which ends setup.
- **Methods:** Sign in with Google, Sign in with Apple, and a six-digit code emailed through Resend (works everywhere, so nobody is stuck). Per platform (Platform deltas): Android has Google and email; iOS has Apple, Google and email (Apple requires Sign in with Apple whenever Google is offered, so they ship together); the web has Google, Apple and email. A Google or Apple button shows only when the build has its public client id (`AUTH` in `src/lib/auth.ts`, from `NEXT_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `NEXT_PUBLIC_GOOGLE_IOS_CLIENT_ID`, `NEXT_PUBLIC_APPLE_SERVICES_ID`; client ids aren't secrets, so they can be committed once created). Apple on iOS needs no id.
- **Native code is ours, not a social-login plugin** (`AccountSignIn`: `AccountSignInPlugin.java`, `AccountSignInPlugin.swift`). The common Capacitor social-login plugin links the Facebook SDK on iOS through Swift Package Manager whether or not it's used, which doesn't fit "no tracking SDKs". Android uses Credential Manager's Sign in with Google sheet (`androidx.credentials`, `googleid`); iOS uses `ASAuthorizationController` for Apple and Google's OAuth code flow with PKCE in an `ASWebAuthenticationSession` (iOS client id, no Google SDK). The web loads Google Identity Services and Sign in with Apple JS only on the account screen. iOS has the `com.apple.developer.applesignin` entitlement.
- **Tokens:** every method ends with the provider's ID token (or the emailed code) checked on the server (`src/server/idToken.ts`): RS256 signature against Google's or Apple's published keys, issuer, audience (our client ids, `GOOGLE_CLIENT_IDS` / `APPLE_CLIENT_IDS` plus the public ones and the bundle id), expiry, and a nonce (the app makes a random value, gives the provider its SHA-256, and sends the raw value to the server). Identities with the same **verified** email join one account. The server returns a random session token (365 days, sliding); only its SHA-256 is stored, and the device keeps it in localStorage (`liftsmith.account`), sent as a Bearer header (no cookies, so the native shells work cross-origin).
- **Email codes:** 10 minutes, one use, 5 wrong tries, 5 codes a day per address, plus per-address-IP rate limits on every route. The answer is the same whether or not the address has an account.
- **Delete my account** (`DELETE /api/account/`) deletes the account, its identities, sessions and the whole synced copy at once (App Store 5.1.1(v), Play's account deletion rule; the web link for Play's form is `https://www.getliftsmith.com/app/#/account`). With `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY` set, Apple sign-ins swap their authorization code for a refresh token at sign-in and deleting revokes it, as Apple requires. "Erase this device" signs the device out and leaves the account.
- **Not yet:** Pro on the account (entitlements stay per install; the server's `entitlements` table can join accounts later), friends and a shared feed, and moving the email reminder subscription onto the account (`account_id` is ready).

## Architecture decisions

- **Stack copied from Gradelings** (`mjparinas/gradelings`): Next.js 16 static export, React 19, TypeScript, Tailwind 4, Zustand, Vitest.
- **Capacitor, not Bubblewrap (Melvin chose it, 2026-11-09).** A TWA can't run a foreground service, show a live lock-screen countdown, read Health Connect, keep Bluetooth heart rate going with the screen off, or use StoreKit (it has no iOS app). Capacitor wraps the same static export and adds those through native plugins; it also builds the iOS app. The cost is a store release for each app change.
- **Offline-first, like Gradelings.** Everything the lifter does is an event with a unique id (set, session start and end, feedback, swap), appended to IndexedDB first (`localdb.ts`). Stats, PRs, recovery, streaks, XP and progression are recomputed from events, never stored (`derive.ts`), so merging devices is order-independent and duplicate-safe. Profile and gyms are last-write-wins on `updatedAt`.
- **Two builds** (`next.config.ts`): `npm run build` is the Vercel server build with API routes named `route.api.ts`; `npm run build:static` (`STATIC_EXPORT=1`) is the static export for the native shells and CI, and it leaves those routes out. Native apps call the API on `SITE_URL`.
- **Sync (built, 2026-11-09):** `POST /api/sync/` (`src/server/sync.ts`, client `src/lib/sync.ts`) pushes this device's new events and deletes and pulls the account's other devices' by cursor, on open, on return to the foreground, when back online, and 4 s after a change. The outbox (`src/lib/syncOutbox.ts`, localStorage) is filled by `localdb.ts` itself, so anything that writes there (the store, the dashboard's past-workout log, a restored backup) is queued; writes that came from sync pass `{ remote: true }` and aren't sent back. Signing in queues every event once. Server: `sync_events` (one row per account and event id, `seq` is the cursor; a delete becomes a tombstone with a new seq that is never undone; a device never gets back what its own session wrote) and `sync_records` (`profile` and `gym:<id>`, last write wins on `updatedAt`; a removed gym is a null record). **On a device's first sync the account's profile wins** over the device's, so signing in on a freshly set-up phone brings the lifter's own settings back; gyms are merged. 500 events per page, 1,000 per push, 3.5 MB per request, 600 syncs an hour per account. Everything in the event log syncs, health readings, injuries and cycle logs included (the user's own account only); progress photos never do. A 401 signs the device out and keeps its data.
- **One static page for the app** with hash routes (`#/today`, `#/workout`, …), so it works offline from one cached page.
- **The active workout** is also kept in `localStorage`, so killing the app mid-set loses nothing.
- **Seeded randomness only** in the generator (`random.ts`), never `Math.random`, so plans are reproducible and testable.
- **Native code** lives in the Android project as small Capacitor plugins (WorkoutSession foreground service; Health Connect), called from `src/lib/sessionNotify.ts` and friends, which fall back to web APIs when not native.

## Code conventions (Melvin asked, 2026-11-09: "easier to maintain and change")
- **Strict TypeScript plus** `noImplicitReturns` and `noFallthroughCasesInSwitch` (`tsconfig.json`). No `any`.
- **Type-aware lint on `src/`** (`eslint.config.mjs`): `no-floating-promises` (a promise nobody waits for loses its error; await it, or mark a deliberate fire-and-forget with `void`), `no-misused-promises` (no async function where a plain callback is expected; JSX handlers may be async), and `switch-exhaustiveness-check` (a `switch` over a union covers every case or has a `default`).

## CI/CD (Melvin asked, 2026-11-09: like Gradelings)

- `.github/workflows/ci.yml` on every pull request and push to `main` and `staging`: types, lint (no warnings), dependency audit, unit and integration tests with coverage, build, then browser tests in three parallel jobs. **"CI passed"** is the one required check.
- `mutation.yml`: **on demand only** (Actions › Mutation tests › Run workflow). Mutation runs are long and expensive, so they never run on pull requests or merges and never gate a merge (Melvin, 2026-11-09). Run one after a batch of engine work and raise `break` when the score rises.
- `promote-staging.yml` (Melvin confirmed the Gradelings model, 2026-11-09): `main` is production and every pull request targets `staging`. At 09:00 UTC each night it opens a staging → main pull request and merges it when "CI passed" is green on staging's latest commit, then merges `main` back into `staging`. Run it by hand from the Actions tab to ship sooner. Scheduled workflows only run from the default branch, so the file must be on `main` before the nightly run starts. It needs "Allow GitHub Actions to create and approve pull requests" on, and `PROMOTE_TOKEN` if `main` requires reviews.
- `ci.yml` also builds an Android debug APK (uploaded as an artifact to install and try) and an unsigned iOS simulator build. Both are part of "CI passed".
- **CI speed (Melvin asked, 2026-11-09).** A `changes` job skips both native builds on a pull request that touches none of `android/`, `ios/`, `capacitor.config.*`, `package.json`, `package-lock.json`, `ci.yml` or `.github/actions/`, since the native compile can't change otherwise; pushes to `staging` and `main` always build both, so a break still shows before the nightly promotion. "CI passed" counts a skipped job as passed. The device sweep runs as two jobs (`DEVICES=ios` and `DEVICES=android`) and the iPhone playthrough moved into the playthrough job. Gradle uses its build cache (cached across runs) and `--parallel`. The iOS simulator build compiles arm64 only, with no index store, and uses a placeholder `out/` so it starts without waiting for the web build. Add a path to the `changes` filter whenever something new can affect native builds.
- `release.yml`: on every promotion to `main` and on demand, builds a signed Android App Bundle and uploads it to the Play **internal** track, and archives iOS and uploads it to **TestFlight**. Version name comes from `package.json`, build number from the run number. Each platform skips itself with a notice until its secrets exist. Promoting past internal testing stays a human step in the store consoles.
