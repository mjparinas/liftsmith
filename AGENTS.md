
# Liftsmith: guide for agents

Liftsmith is an Android-first adaptive strength training app. It plans each workout from the lifter's equipment, recovery and training block, then gets out of the way while they lift. This file holds the rules that apply to every change. The decisions about each feature, and why, are in one file per topic under `docs/decisions/` (listed under "Decision record" below), so threads working on different features don't edit the same file (Melvin, 2026-11-09). Follow them. Before working on a feature, read its topic file. If a task seems to need a decision changed, raise it with the owner (Melvin) first, and when a decision changes, update its file in the same change. A new topic gets a new file and one line in the list below.

The full plan with stages lives in the plan doc: https://claude.ai/artifact/S24kx43ZkQ8g3gGtGew34n

## Commands

```bash

npm test                     # unit + integration tests (Vitest; engine in node, screens in jsdom)
npm run test:coverage
npm run test:mutation        # Stryker on the engine; report in reports/mutation/
npm run lint && npx tsc --noEmit && npm run format:check
npm run build                # server build (Vercel): pages plus API routes (route.api.ts)
npm run build:static         # static export to out/ (native shells, browser tests)
node scripts/e2e.mjs         # full playthrough (serves out/ itself, or pass a base URL)
node scripts/e2e-offline.mjs # real offline after one visit
node scripts/e2e-devices.mjs # layout on 13 phones and tablets (DEVICES=ios|android|full|names)
DEVICE='iPhone 16' node scripts/e2e.mjs  # the playthrough on another device
node scripts/e2e-a11y.mjs    # axe WCAG 2.2 AA on every screen
node scripts/e2e-gaps.mjs    # no two cards touch, on every app screen and each kind of site page; no button stretches on desktop
node scripts/site-screenshots.mjs # real app screenshots for the home page (public/screens/)
STILLS=1 npm run build:static && node scripts/og-images.mjs --missing # preview cards (public/og/) and exercise stills (public/stills/) for new pages
node scripts/play-capture.mjs && node scripts/play-compose.mjs && node scripts/play-video.mjs # Google Play art (docs/PLAY_LISTING.md)
npx cap sync                 # copy out/ into the Android and iOS shells (after npm run build:static); the website is left out (docs/decisions/app-size.md)
```

There is no Android SDK in cloud sessions; APKs and AABs build in GitHub Actions (`.github/workflows/android.yml`).

## Platform parity (rule, Melvin, 2026-11-09)

- **Every feature goes in both apps, plus the web app wherever it makes sense** (Melvin, 2026-11-09). Each feature lands on Android and iOS in the same change: native Android code (Java or Kotlin in `android/`) and native iOS code (Swift in `ios/`) for anything the web layer can't do. The web app (`/app/`) gets it too when the browser can do it (for example, `.ics` files instead of calendar access, and manifest shortcuts instead of widgets).
- **One-platform features are allowed when they're very useful** (Melvin, 2026-11-09). If a feature is very useful on one platform but the other ecosystem can't support it, build it anyway. Record the gap in [Platform deltas](docs/decisions/platform-deltas.md), and in the pull request description, say what each platform does instead.
- Platform equivalents: Health Connect ↔ HealthKit (Apple Health); foreground-service notification ↔ Live Activity (lock screen and Dynamic Island); Play Billing ↔ StoreKit; Sign in with Google ↔ Sign in with Apple (both offered on iOS); Wear OS ↔ Apple Watch.
- CI builds both apps together (`android` and `ios` jobs in `ci.yml`) whenever a pull request or a push to `staging` or `main` touches native code, Capacitor or dependencies, and `release.yml` builds both on every promotion. Both always run or skip together.
- **Live workout notification today:** Android runs a foreground service (`WorkoutService.java`) with an ongoing notification: lock-screen rest countdown (redrawn once a second), next set and plates, heart rate, workout progress bar, and Log set / +30 s buttons; when rest ends the same card says "Rest over" (no second notification) while the service sounds and buzzes, and 10 seconds before the end it gives a gentle heads-up buzz (its own switch; the watches too, iOS in the app only; [Workout screen](docs/decisions/workout-screen.md)). On Android 16 it's promoted as a **Live Update** (status bar chip with the rest time left or the set, "2/4"; Samsung's Now Bar on One UI 8); while resting it says the time left in its text and chip and shows a rest bar, redrawn once a second during rest only, details in [Workout screen](docs/decisions/workout-screen.md). iOS (`WorkoutSessionPlugin.swift`) runs a **Live Activity** (lock screen and Dynamic Island: rest countdown or the set, next set and plates, heart rate, a rest bar while resting and the workout progress bar otherwise, Log set / +30 s links; drawn by the `LiftsmithWidgets` extension) and schedules a time-sensitive rest-over notification with the same two buttons. Heart-rate-only changes reach the Live Activity at most every 15 s, because iOS budgets updates. **Log set and +30 s work with the app closed:** the tap is kept with its time and logged when the app opens, and the notification or Live Activity steps through the next sets the app sent ahead (`ahead`, `workout/sessionAhead.ts`; [Workout screen](docs/decisions/workout-screen.md)). Both are driven by the same `WorkoutSession` calls in `src/lib/sessionNotify.ts`, which also send the workout to the **watch apps** (Wear OS module `android/wear`, Apple Watch target `LiftsmithWatch`): set, weight and reps or the rest countdown, heart rate from the watch's sensor, and Log set / +30 s, and to the **Garmin watch app** (Connect IQ, `garmin/`, through `GarminLink` on both phones) ([Watch apps](docs/decisions/watch-apps.md)); the Wear OS app is not standalone, so it finds the phone app by its `liftsmith_phone` capability and offers Start on phone or Install on phone (Play review, 2026-11-20, Watch apps "Finding the phone"). The **set timer** for holds, carries and cardio rides along as wall-clock phases (`timer`), so the notification, Live Activity and watches count it down on their own ([Set timer](docs/decisions/set-timer.md)).
- Native code registered by the app: Android `MainActivity.registerPlugin`, iOS `MainViewController.capacitorDidLoad` (Capacitor 8 with SPM doesn't auto-register app-target plugins). `InstallInfo` (device and install source for analytics) is registered on both.
- Native apps open straight into the app (`server.appStartPath: /app/index.html`); the landing page is for the website.

## Features page (rule, Melvin, 2026-11-12)

- **The website's `/features/` lists every feature, a compatibility table of every connection and the newest features, and stays current** (Melvin, 2026-11-12: "keep it up to date with all new features"). It comes from one file, `src/content/features.ts`, and is in all ten site languages (the other languages' words in `src/locales/site/features/<lang>.ts`, same ids). ## Email (rule, Melvin, 2026-11-14)

- **"Email me" is on by default** for every signed-in adult, existing accounts included, with the account's verified address. Under-18s start with it off. Turning it off syncs (`messages.emailOff`), the sign-in screen says emails come with an account, and every email has one-click unsubscribe and its kind's own switch in Settings › Reminders. **Getting started tips** (the feature tour) send one branded email a day for the first eight days, each with a real app screen in the reader's language (`src/server/tour.ts`, `public/email/`). Lifecycle emails, each with its own switch and on by default: a weekly (Sunday) and monthly (the 1st) recap, new personal bests (at most one a week), friends who trained (Thursday), trial ending, a welcome and first-workout email that names the workout waiting, a win-back after 14 and 21 quiet days, and after Getting started, **Weekly tips** (one a week, below). No promotional email (the tour, Pro offers) goes to under-18s. Details in [Reminders and lifecycle messages](docs/decisions/reminders-and-lifecycle-messages.md).
- **Every brand-new feature goes on the weekly email list** (Melvin, 2026-11-15: "add to this list of email content if a feature is brand new and append it to the list"). [Weekly tips emails](docs/decisions/weekly-emails.md) is the weekly series that follows Getting started (built 2026-11-15: one a week, Tuesday 10:00 or the next free weekday, its own "Weekly tips" switch on by default, never to under-18s, role emails for coaches, physios, school coaches and gyms; `src/server/weekly/`). A change that ships a feature a lifter, coach, physio or gym would notice appends an email for it to the end of `WEEKLY` in `src/server/weekly/list.ts` with `fresh` set to the day it shipped (sent next to everyone already in the series), its words in all six `src/server/weekly/text/<lang>.ts` (title, opening line, three to five points, a "Did you know?" line), its screenshot (`ONLY=<id> node scripts/weekly-email-shots.mjs`) and a short entry at the end of the doc's list marked **New**, in the same change; or adds a point to the email it extends. A small setting goes into a "Did you know" round-up instead. No other app's name, ever. `weekly.test.ts` fails when a language lacks an email or a line, or a screenshot is missing.

## App versions (rule, Melvin, 2026-11-19)

- **Every new feature bumps the version** (Melvin, 2026-11-19: "versions should get bumped on every new feature, right now it's this Version 0.1.0"). A pull request that ships a feature runs `node scripts/bump-version.mjs minor` (0.2.0 → 0.3.0); one that only fixes something a lifter could notice runs `patch` (0.2.0 → 0.2.1); CI, docs, tests and admin-only changes bump nothing. `package.json` is the one source: the web build stamps it (`APP_VERSION`), `release.yml` passes it to Android (`versionName`, phone and Wear OS) and iOS (`MARKETING_VERSION`, app, widgets and watch), the Gradle files read it for local builds and the script keeps the Xcode project equal (`appVersion.test.ts`). Store build numbers stay the Release run number, so they always rise. Each What's new release carries the `version` it ships as, and a minor bump comes with its change in the top release (`appNews.test.ts`); several features before one promotion share that release and move its version up. If staging's version moved while the branch was open, merge staging and bump again from its number. Details in [App versions](docs/decisions/app-versions.md).

## Community (rule, Melvin, 2026-11-17)

- **Lifters shape the app in the Liftsmith community** (Melvin, 2026-11-17: "a community for the app itself. like voting for features that are missing, adding comments, mentioning bugs"). Settings › Help › Community (`#/community`) has Ideas, Bugs and a Roadmap: post (a bug can carry one screenshot only its author and staff see), vote once, comment and @mention by Friends handle (a mention reaches only people already in that post), and follow each post from Under review, Planned, In progress to Shipped or Won't do with a push when it moves. Built in-house on our database and the Friends filter; three reports hide a post or comment and they go to Admin › Reports (kind `feedback`); staff set statuses with notes, merge duplicates, answer as the Liftsmith team and block accounts on Admin › Community. Under-18s show no name and stay off the website. The website has `/community/`, the roadmap, the changelog and a page per post (server-drawn, no scripts). When a feature ships that came from the community, set its post to Shipped with a note so the people who voted for it hear. Details in [Community](docs/decisions/community.md).

## Product rules (apply to every screen)

### Action over stats (rule, Melvin, 2026-11-09)
- **We don't show stats for the sake of stats or pretty graphs. We prioritise action-oriented recommendations.** Every screen should answer "what should I do?" before "what happened?". A new chart or number needs a reason the lifter would act on it; if it has none, leave it out or turn it into a recommendation.
- **Every recommendation says why, in a short line.** Each recommended workout, exercise, set count, rep target and weight carries a plain-words reason built from the same data that produced it: readiness low or high (and the signals behind it), a deload, a plateau, missed or hit reps, feedback, the lifter's own settings, recovery and weekly sets left. Code: `src/lib/why.ts` (`itemWhy` for each planned exercise on Today, `workoutWhy` under the target during a set, `callWhy` for the push / as planned / easy call) and the notes on targets in `progression.ts`. A new recommendation lands with its reason in the same change. Reasons are shown, never behind a tap, and never add a tap during a set. A timed set (holds, carries, intervals) or cardio never gets rep wording such as "reps in the tank": `effortAim` and `noteFor` give it seconds and form instead (Melvin, 2026-11-17, [Workout screen](docs/decisions/workout-screen.md)).
- **Proactive insights ("Coach's notes").** `src/lib/insights.ts` looks for things worth acting on and says what we saw, the numbers behind it, and one thing to do, ideally a one-tap action: fatigue building (missed reps three workouts running, offer a deload), stalled lifts (no new best in 3+ weeks; several at once offers a deload), a big muscle short of its weekly sets for two weeks (offer to make it a priority), body fat creeping up (advice for the goal), weight dropping faster than 1% a week, the weekly goal at risk (offer a 30-minute workout), the last hard week of a block, what's working (a lift up 5%+ in six weeks), and food from a food app through Health Connect or Apple Health (protein short three logged days running, eating too little to build muscle, a very big deficit, all against one set of targets shared with Tools › Macros and a coach's numbers, `foodTargets.ts`; maintenance measured from food and weigh-ins once there's two weeks of both; under-18s get protein only; no food logging in the app, see [Food from Health](docs/decisions/food-from-health.md)). Lifters in a Pro trial get its notes first: halfway, the last two days and two weeks after it lapses, each with what Pro did for them (adaptive workouts, weights raised, days adjusted; `trialNotes.ts`, [Money](docs/decisions/money.md) "The first two weeks"). Lifters in Friends also get up to two friend notes (a friend challenge slipping away, a friend pulling ahead while they're short of their weekly goal, a friend gone quiet; `friendNotes.ts`, [Friends](docs/decisions/friends.md)). They show on Today (top two) and at the top of Progress ("What to do next"). Nothing is shown when nothing needs doing. "Got it" hides a note on the device until the finding changes (its id changes). Derived from events every time, never stored.
- **Actions:** `store.startDeload()` makes the current week the deload (the next block starts after it), priorities go through Settings' `togglePriority`, and minutes through `setProfile`.
- **Body fat** is an optional field on body weight events (`bodyFat`, %). Weigh-ins and body fat come in from Health Connect and Apple Health on launch and on return to the app at most every 15 minutes (`healthRefresh.ts`; `readBody` in `health.ts`, one per day, ids `health-bw-<day>` so a re-import is a no-op; HealthKit's fraction is turned into a percentage), which covers smart scales and the Hume Body Pod. Past weigh-ins, body fat and tape measurements can also come from another app's export through Settings › Data's import (`importBody.ts`, [Borrowed from Gradelings](docs/decisions/borrowed-from-gradelings.md) under CSV import). **Manual entry** (Melvin, 2026-11-10): an optional body fat box (`BodyFatField`, a `BumpField` in 0.1 steps from the last reading or 20%, 3 to 60%, with the `bodyFat` glossary "i") sits under the weigh-in on Progress and on Body and photos, and is saved on the same weigh-in; body fat on its own is logged with the last weight. **Tape measurements** (nine sites, `measure` events, cm or inches; 2026-11-11) sit on Body and photos, and a growing or shrinking waist becomes a coach's note when there's no body fat data. Details in [Health twin](docs/decisions/health-twin.md). **Shape the figure like me** (a switch on Body › Health, off by default; 2026-11-12) reshapes every 3D figure in the app (Health, the recovery map, the exercise demos; `useMyShape` in `myShape.ts`) from height, weight, body fat and tape measurements (`src/lib/bodyShape.ts`), says what's missing with a button to add it, and says what it was shaped from, and a client who turns on Share body data for a coach shows that coach the same shaped figure with their numbers ([Trainer mode](docs/decisions/trainer-mode.md)). **Fitness tests** (dead hang, one-leg stand, 30-second chair stand; `fitTest` events; 2026-11-11) sit on Body › Health under Fitness age, each with a timer, a typical range from a published study where one exists (shown on a coloured number line with a marker at the result, 2026-11-17), what helps and a goal; [Fitness tests](docs/decisions/fitness-tests.md).
- **Labs** (Melvin, 2026-11-10: "a labs section for experimental features … Labs should be a pro only feature. It's where we put experimental features that aren't quite ready for prime time"). **Settings › Labs** lists experiments, each behind its own feature flag with a switch (`LABS` in `src/lib/labs.ts`, text in `lab.*`). Labs is Pro: `labOn(flag)` is false without Pro whatever the flag says, and free lifters see the Labs row marked Pro (it opens Pro). A switch sets the flag on the device; the admin panel can still turn a lab on for everyone (still Pro only). A lab may need another (`needs`), and shows only once that one is on. Experiments today: camera rep counting (`labRepCount`), phone motion counting (`repMotion`), camera bar speed (`labBarSpeed`, needs camera counting), the heart-rate rest timer (`labHrRest`: rest ends early once the heart rate is back down, never below 60% of the planned rest, [Heart rate and health](docs/decisions/heart-rate-and-health.md)), camera form check (`labFormCheck`, needs camera counting), voice set logging (`labVoiceLog`: say "100 for 8" or "too easy" to log a set, recognized on the device; [Voice set logging](docs/decisions/voice-set-logging.md)), today's max from warm-ups (`labSpeedMax`, needs bar speed: warm-up speeds estimate today's max and nudge the first working weight, against each lifter's own end-of-set speed once three sets to failure have taught it), bar path replay (`labBarPath`, needs camera counting: after a counted squat, hinge or overhead press, the rep worth seeing replays from the pose landmarks with the bar's path and one cue on where it drifted; landmarks only, in memory until the next set), watch rep counting (`labWatchReps`: the Wear OS or Apple Watch app streams wrist motion during a set and the phone counts it, [Watch apps](docs/decisions/watch-apps.md)), hands-free sets (`labHandsFree`: while any rep counter is counting, the set logs itself a few seconds after the last rep, [Camera rep counting](docs/decisions/camera-rep-counting.md)), the tempo coach (`labTempo`: on tempo and paused lifts, Count tempo above Log set counts each rep's lowering, hold and lift in sound and haptics, [Tempo coach](docs/decisions/tempo-coach.md)), the Bluetooth smart scale (`labScale`: a scale sharing the standard Weight Scale or Body Composition Service fills in weight and body fat on the weigh-in for the lifter to log; [Connected apps](docs/decisions/connected-apps.md)), the volume button (`labVolumeLog`, phones only: volume up on the phone or Bluetooth earbuds logs the set and the volume goes back, while the workout is on screen; [Volume button logs a set](docs/decisions/volume-button-logging.md)) and Bluetooth gym machines (`labGymMachines`: bikes, rowers, treadmills and cross trainers sharing the Fitness Machine Service fill in a cardio set's time, distance and average power; native Bluetooth on both phones, Chrome on the web, [Gym machines](docs/decisions/gym-machines.md)) and Sonos (`labSonos`: play, pause, skip and change the volume of a Sonos speaker from the workout screen, and let the music follow the workout, set volume for sets, rest volume for rest, a favourite at the start and a pause at the end; line-in, the TV and AirPlay show by name, without skip buttons; Sonos's cloud Control API through our server, so it needs an account; [Sonos](docs/decisions/sonos.md)). New experimental features land as a lab, and leave Labs (flag and entry removed) when they're ready: trainer mode left on 2026-11-12 and is now the Pro feature `coaching` ([Trainer mode](docs/decisions/trainer-mode.md)). A lab marked `native` shows only in the Android and iOS apps. Pure web code, so Android, iOS and the web app get it together (watch rep counting adds native code on both watches).
- **Pregnancy and postpartum mode** (Melvin, 2026-11-19, gap item 10): Settings › Body and units, opt-in with its own consent, weeks on a stepper. Like injury mode it changes the plan: by the week of pregnancy or weeks since birth, loads come down, every set stays 2 to 4 reps short of failure, sets are capped, push days and challenges go, and exercises are left out (lying on the back or belly, jumps and crunch-style core from week 14; jumps, running and crunches for 12 weeks after birth, 14 after a C-section). Every change says why (target notes, a Today chip). Free, pure web code, so Android, iOS and the web get it together. Details in [Pregnancy and postpartum mode](docs/decisions/pregnancy.md).
- **Features unlock as a new lifter trains** (Melvin, 2026-11-18: "slowly unlock things as time goes on, like seasons shouldn't be available right away for new users"). Counted in finished workouts (imported history counts, `UNLOCKS` in `src/lib/unlocks.ts`): XP, level, badges and the Awards tab after 1, weekly quests and the league after 2, Friends and the share cards after 3, training seasons, crates and the locker after 5, and the monthly challenge, Adaptive workout options and Labs after 8. The workout that opens one shows a "New for you" card on Done. Nothing is taken away (`reveal.peak`), accounts from before 2026-11-18 keep everything (only a first setup writes `profile.reveal`), an experienced lifter starts three workouts in, and Settings › Look and feel › Show everything opens it all. Experience, never money: a Pro item that appears keeps its Pro tag, and the paywall lists every Pro feature. Links always open their screen. A new feature that would crowd a new lifter's first days goes behind one of these unlocks (`useUnlocked`). Details in [Features that unlock as you train](docs/decisions/unlocks.md).
- **Training seasons** (Melvin, 2026-11-17: "games like diablo have this concept of a season … different badges, colour schemes, icons, that you can only unlock in there"; "applicable to both serious lifters and casual ones"). Ten-week seasons (8 to 12, scheduled in Admin › Seasons) with a track of 20 tiers. **Season points come from the lifter's own weekly goal, never past it**: 600 a week shared over the goal days, 200 for meeting it (twice after a missed week), 50 per weekly quest, 500 per season challenge, the last week doubled, prestige stars past tier 20, and a 1 in 6 rare drop per new best. Tiers bring season-only badges, an avatar, an accent and a theme with its app icon (native on both phones), earned only during the season and kept after it; **every tier is free and Pro adds a bonus row** (Melvin picked it, 2026-11-17). Derived from events, never stored. Light on screen: one row on Today's This week card, a Seasons card on Awards and the Season screen (`#/season`), with **Settings › Look and feel › Training seasons** to turn it off (Melvin: "consider an opt-out toggle"). A new season needs a new reward set (kit) in an app release. **Planned through 2027** (Melvin, 2026-11-19: "keep them unique, plan it out until end of 2027"): six ten-week seasons back to back, built in (`DEFAULT_SEASONS`) so they start and end on their own: Ember, Tempest, Bloom, Solstice, Maple and Obsidian (to 16 January 2028), each with its own themes, app icons, avatars, accents, rare plates and three challenges of its own (`Kit.challenges`); never reuse a kit, a look or a challenge set, and the admin can move or take off any that hasn't started. Details in [Training seasons](docs/decisions/seasons.md).
- **Pick weights** (Melvin, 2026-11-13): every exercise has a per-lifter chance of being picked by the adaptive plan, drawn in proportion to its weight: popular lifts start high (`STAPLE`), well-known variations lower (`COMMON`), everything else rarely; a star (favourite) makes it a staple ×40, a plain swap lowers it and fades over months ("not available here" swaps don't count), new lifters and a lifter's first four weeks get familiar staples almost every time (`BASE_FRESH`), and Settings › Workout › Plan details › Picked less often resets one. Hard filters (equipment, not available here, injuries, recovery) come first. When a bodyweight compound has a loaded version in the gym (Reverse lunge and Dumbbell reverse lunge), the plan picks the loaded one unless the lifter starred or swapped into the bodyweight move (`preferLoaded`, Melvin 2026-11-17). Derived from the profile and swap events, which already sync; the swaps are cached on the device (`SwapCache`). Details in [Pick weights](docs/decisions/pick-weights.md).
- **Adaptive workout options** (Melvin, 2026-11-17: "create superset automatically. This should be a toggle, we should have options to tweak how adaptive workouts work"). Settings › Training › Adaptive workouts: **Pair exercises into supersets** (`training.supersets`, off by default) makes the adaptive plan pair exercises that don't share muscles (opposite muscles first, then upper with lower, then core), each pair's rest after a round cut by the partner's set and the switch (never under a minute, a lifter's own rest kept, the usual rest back if the pair is split), and more work fitted into the same length; **Keep heavy squats and deadlifts on their own** (on by default, every barbell compound on a strength goal); **Warm-up sets** (on by default; off reaches every plan and mid-workout swaps); and **Exercise variety** (moved here). Every pair says why on Today and under the target. Not Pro-gated: the adaptive plan is, and **basic automatic supersets stay free** (Melvin, 2026-11-17: "keep basic automatic supersets free"), so a free lifter's weekly adaptive workout pairs exercises too. Pure web code (`src/lib/autoSuperset.ts`), so Android, iOS and the web get it together. Details in [Adaptive workout options](docs/decisions/adaptive-options.md).
- **Profiles say a little more** (Melvin, 2026-11-14): a Friends profile has an optional **tagline** (60 characters, through the name filter, reported as "Offensive name, handle or tagline", cleared by staff with Clear tagline or Remove) and an optional **home gym**, always one of the finder's real gyms (a `gym_places` id picked from the lifter's linked gyms), never typed text or a location, shown only to people who see the posts and never for under 18s. Both show in the app and on the public page. Details in [Friends](docs/decisions/friends.md) "Tagline and home gym".
- **Open now in the gym finder** (Melvin, 2026-11-19, an idea borrowed from an open-source sat-nav app; our own code): every real gym with readable hours says "Open now · closes …", "Closes soon", or "Closed · opens …" in the app's finder, a gym's details and the website's `/gyms/` map list, with an **Open now** filter chip. One rule (`openState`/`openNow` in `src/lib/openingHours.ts`), worked out on the viewer's clock for gyms within 300 km only (we don't store a gym's time zone); the website's script sends its time zone and the server answers. Pure web code, so Android, iOS and the web get it together. ### Positioning
- **An original app.** It borrows ideas from Fitbod (daily adaptive workouts, equipment matching, recovery map, variability setting) and Gymverse (periodized blocks with RIR and deloads, exercise swaps, lock-screen timer). It never uses their names in the UI, their art, screenshots, exercise videos or exact look. Exercise names, setup text and cues are our own.
- **Focus on the workout, not the app.** One tap logs a set as planned. The next set is always pre-filled. The rest timer starts itself. Anything optional (feedback, swaps, info) appears between sets and never adds a tap during a set.
- **One control, one destination** (Melvin, 2026-11-09: "two buttons doing the same thing is not correct"; keep the app as simple and streamlined as possible). On any one screen, a sheet, page or dialog has exactly one control that opens it. Before adding a button, check nothing on the screen (the tab bar included) already goes there; if a bigger area should be tappable, make that area the one button rather than adding a second. A glossary `Info` "i" never sits beside a button or sheet that explains the same thing. Cleaned up on 2026-11-09: the workout screen's info icon and the separate demo tap (the demo card is now the one "How to ›" button), Settings' "Achievements and locker" button (the Awards tab is always on screen there), and the "i" next to fitness age (its "How is this worked out?" sheet explains it). Links from one screen to another screen (Progress › All tools and Settings › Tools, say) are fine: they're different screens. **The 3D how-to figure has no tempo or pause controls** (Melvin, 2026-11-17: "too many controls, don't think we need speed or pause"): it always plays at its own pace, the muscles it works sit right under the figure, then the view and overlay toggles (`LiftDemoCore.tsx`); the website's 2D figure keeps a Play button only until it starts. The workout screen's demo keeps moving during rest ([Workout screen](docs/decisions/workout-screen.md), [Speed](docs/decisions/speed.md)).
- **Explain every label that isn't obvious** (Melvin, 2026-11-09). Jargon and training terms (deload, build weeks, RIR, readiness, today's call, volume, estimated one-rep max, sets per muscle, exercise variety, recovery, warm-ups) get the one shared `Info` button (`src/components/Info.tsx`): a small "i" with a 44 px tap target that opens a short plain-language dialog. The text lives in the language catalogues (`gloss.<term>.title` and `gloss.<term>.body`, one paragraph per line); `src/lib/glossary.ts` lists the terms and reads them. `Section` takes an `info` term. Any new label a lifter might not understand gets a glossary entry in the same change.
- **The maker isn't named in public** (Melvin, 2026-11-14: "remove my name from the website"). The website, the apps, the store listing and blog bylines never name the owner: the about page says "made by an independent developer", articles are by Liftsmith (JSON-LD authors are the `Organization`). Code comments and docs in this repo may still credit decisions to him; `infoPages.test.tsx` checks the info pages.
- **Dark, trustworthy, professional.** Deep navy-black background, one blue brand accent (`#4c8dff`, one CSS variable so cosmetics can recolour it), green, amber and red reserved for status (recovery bands, warnings). Large touch targets, tabular numbers, system font (Roboto on Android).
- **Light mode** (Melvin, 2026-11-09). **Settings › Look and feel › Appearance: Dark (default), Light, or Match system.** It sets `data-theme` on `<html>` (`src/lib/theme.ts`), saved on the profile and in localStorage so the next launch paints the right theme before the profile loads; it also sets the browser bar colour and the native status bar style. **Every colour is a token** in `globals.css` with one dark and one light value, including badge tiers, crate rarities and heart rate zones (`--tier-*`, `--rarity-*`, `--hr-*`); never hard-code a hex in a component. The light accent is a darker blue (`#1d4fc4`) so text passes contrast, and an equipped accent cosmetic is darkened on light screens (`applyAccent`). The design pass's effects (primary gradient and its ink, screen glow, card sheen and shadow) are variables too (`--grad-*`, `--btn-ink`, `--glow-*`, `--sheen*`, `--shadow`); the light primary button is a deeper blue-to-violet with white ink. - **Mascot** (Melvin asked for "juicier", 2026-11-09): an original, friendly kettlebell (`Mascot.tsx`), drawn in the brand gradient so it follows the theme and light mode, with four moods (happy, sleepy, cheer, curious), a slow bob and a blink. - **Motion:** short and purposeful (`rise`, `pop`, `fade`, `nudge` on a changed number, `burst` from Log set, `beat` on the live heart rate, `spring-in` for empty states, `stagger` for Today's exercise list). **Springs:** `--ease-bounce` is a real spring (CSS `linear()`, overshoot then settle) with a back-ease fallback. `.press` squashes instantly (70 ms) and springs back on release; the primary button squashes and stretches (`scale(1.02, 0.9)`), cards dip less. iOS shows `:active` only with a touch listener, so `App.tsx` adds one. **Bursts** (`burst.ts`): particles in the token colours plus an optional checkmark, from what the lifter touched (Log set, a crate), under a second, never blocking a tap. - **Sound set:** every sound is one synthesized voice (a soft glassy mallet) in A major pentatonic (`juice.ts`), so sounds never clash: a near-silent tick for steppers, chips and the length slider, a soft rising or falling pair for a switch on or off, a rising pair for Log set, a phrase for Start, a three-note chime for rest over, a falling pair for discard, a bright run for a goal or quest done, a low soft pair for an error, and a longer phrase for the end of a workout. The vocabulary (`HapticKind`): `select` (light tick) for steppers, sliders, chips and tabs; `tick` for buttons; `toggle` (medium) for switches; `tap` (medium) for Log set; `thud` (heavy) at rest end; `double` (a crisp double tap) and `celebrate` (double tap then success) for PRs, level-ups and achievements; `success`, `warning` and `error` notifications. `oops()` pairs the error haptic with the error sound for any failure. **Vibration** can be turned off in Settings (`profile.haptics`).
- **On/off settings are switches** (`Switch`, `SwitchRow` in `ui.tsx`, `role="switch"`), not On/Off chip pairs or checkboxes: one tap, one thumb. Inside a card or sheet, `InlineSwitch` (words, then the switch). A checkbox is only for agreeing to something ("I understand the risks"). The knob springs across and stretches while pressed.

### Accessibility (Melvin, 2026-11-09: "accessibility checks, WCAG guidelines, colour blind support")
- **Target: WCAG 2.2 AA everywhere**, checked in CI. `scripts/e2e-a11y.mjs` runs axe on every screen in dark and light, again with colour-blind safe colours and more contrast, once under forced colours, then a **keyboard-only run** at the **largest text on a 360 px phone**: every Tab stop shows a focus ring, a workout starts and a set logs without a pointer, sheets take focus, keep Tab inside and close on Escape with focus returned, and no screen scrolls sideways. `src/lib/a11y.test.ts` checks the colour tokens: status colours 4.5:1 as text, recovery colours 3:1 against cards, and both colour sets simulated for protanopia, deuteranopia and tritanopia (Machado 2009) so they stay apart. Lint runs the full strict `jsx-a11y` rule set.
- **Settings › Look and feel › Accessibility** (`src/lib/a11y.ts`, saved as `profile.a11y` and in localStorage so the first paint is right):
  - *Text size:* Match my phone (default), Default, Large, Larger, Largest (100 to 150%). It scales the root font size; **every font size is in rem** (no `text-[Npx]`), so all text follows. On Android and iOS, Match my phone reads the phone's own size (font scale, Dynamic Type) through `@capacitor/text-zoom` and pins the WebView's own zoom at 100%, one path on both platforms. Layouts wrap rather than scroll sideways at the largest size.
  - *Colours:* Standard or **Colour-blind safe** (blue, light blue, orange and pink for recovery; blue, orange and pink for good, warn and bad). Status and recovery colours are tokens with `-std` and `-cvd` values per theme (`--band-*`, `--good-*`, `--warn-*`, `--bad-*`), picked by `data-cvd` on `<html>`. Heart rate zone colours already pass the simulation and stay as they are.
  - *Contrast:* Match my phone (follows `prefers-contrast: more`), Standard, or More (secondary text and borders mixed toward the ink colour; glows, sheen and gradient text removed). Built from each theme's own ink and background, so it works in dark and light.
  - Motion: Lean mode (a switch in the same section) and the phone's reduce motion setting.
- **Colour is never the only cue (WCAG 1.4.1):** the recovery map and its legend add dots (Recovering) and stripes (Fatigued); picked chips show a tick; every band also has a label and a percentage.
- **Sheets always show how to close them** (Melvin, 2026-11-09): every `Sheet` (`ui.tsx`) has a ✕ Close button in its header (44 px) and closes when swiped down (from the handle, or anywhere while scrolled to the top; 96 px, or a quick flick of 40 px+) or dragged down with a mouse or pen from the handle or the title row (content stays selectable; Melvin, 2026-11-11: "cursor or finger"), as well as by tapping outside and Escape. The whole sheet follows the finger while dragged and the backdrop lightens with it (the sheet's rise-in animation is cleared first, because a filling animation overrides an inline transform; 2026-11-10). A short pull springs back. Drags that start on a 3D figure, a slider or `[data-no-swipe]` belong to that control, and sideways or upward drags are left alone. Pure web code, so Android, iOS and the web get it together.
- **Back always goes back** (Melvin, 2026-11-10: "pressing the back button on your phone should navigate back to the previous screen"). One rule for the whole app, in `src/lib/back.ts`: back closes the open sheet or dialog first (the newest one), then goes to the previous screen, goes to Today from a screen with nothing behind it (a shortcut or notification), and only on Today leaves the app (Android sends it to the background, so a workout keeps running). Android wires it to the system back button and gesture through `@capacitor/app`; iOS gets a swipe in from the left edge (`allowsBackForwardNavigationGestures` in `MainViewController`); the web uses the browser's back. Every app history entry records how many screens are behind it and which one (`router.ts`), and `go()` to the screen just left steps back instead of pushing, so a screen's own "‹ Settings" link and the phone's back agree. Anything new that should close on back (a sheet, a dialog, a wizard step) calls `useBack(open, close)`; `Sheet`, `Info` and the setup wizard already do. Screens need nothing, so new Settings sub-screens get it for free. **Next.js stays out of these steps** (2026-11-10): a back or forward step that changes only the hash is stopped before Next's own popstate listener (`guardTraversals` in `router.ts`), because Next treats each one as a traversal of its own page and may refetch it, which the Android app's local server can't answer. Steps to another path still go to Next. (The "This page couldn't load" after Today during a workout turned out to be something else: see native listeners under Architecture decisions.) And a screen that fails to draw shows an in-app message with Reload (`ScreenBoundary`, the error goes into feedback diagnostics) instead of Next's dead-end page, with the tab bar still there.
- **Screen readers:** the rest timer is a `timer`; a polite live region says when rest starts, at ten seconds left and when rest is over (not every second). Sheets are modal dialogs labelled by their title.
- **Forced colours** (Windows High Contrast): cards and buttons keep an edge, the focus ring uses `Highlight`, and the recovery map keeps its colours (`.keep-colours`).
- **Quick, one-handed input (Melvin, 2026-11-09: "the less manual typing the better"):** every screen should be fast to adjust in the gym. Prefer steppers with bump buttons, sliders, toggles and chips over text fields, and offer typing only as a fallback. Design for one hand, and respect left- or right-handed use.
  - **Hold to repeat** (Melvin, 2026-11-11: "hold it down for a bit before this happens to avoid accidental touches … speed should start slow and ramp up … haptic and sounds adjusting accordingly"). Every − / + is the one `Bump` in `ui.tsx` (`useHoldRepeat`, timing in `src/lib/holdRepeat.ts`); never hand-roll a − / + button. A tap steps once when the finger lifts, so a scroll that starts on a bump never steps. Held still for 450 ms it starts repeating, slow (200 ms apart) and faster each step down to 60 ms, reached in about two seconds; boxes whose number can jump (`BumpField`, the 1RM inputs) then move 2 steps at a time after 20 repeats and 5 after 40, while the workout's weight and rep bumps stay one plate or rep per step. The tick sound and the `select` haptic come from the bump itself, every step while slow and thinned out at speed (at most every 85 ms and 110 ms), with a `tick` haptic when the step size grows; both follow the Sounds and Vibration switches. A step that changes nothing (a limit) returns `false` and the hold stops. Sliding off (12 px), pointer cancel (a scroll), leaving the button or losing focus stops it. Enter or Space held from the keyboard repeats the same way; a screen reader's click steps once. Used by the workout steppers, every `BumpField`, gym plate counts, the 1RM inputs and routine set counts. Pure web code, so Android, iOS and the web get it together.
  - Numbers a lifter would type use **`BumpField`** (− box +, typing still works): body weight in setup, Settings and the weigh-in on Progress and Body and photos (with body fat under it), age and known lifts in setup, and bar weights in Gyms. An empty box bumps from a sensible start (the last weigh-in, 30 years, a common bar). New number inputs use it too.

Off by default. **Big numbers** (the same page, just under it; `profile.a11y.big`, off by default; Melvin, 2026-11-14, asked for a "quiet mode" for logging mid-set, and Lean mode only cuts celebrations, so this extends one-handed controls instead of adding a second mode): during a set only, the weight and reps get much bigger (capped by the screen's width, so nothing scrolls sideways), Log set is taller, the demo card is shorter, and the music bar, Coming up, Add exercise and Same as last time wait until rest. It works with or without the dock. Pure web code, so Android, iOS and the web get it together.
- Every new screen gets an axe scan in the a11y run, and every new colour is a token that passes `a11y.test.ts`.

## Security (audit, 2026-11-09)

- **Security headers on every website response** (`src/lib/securityHeaders.ts`, added in `next.config.ts` for the server build only; the native shells load files from the device): HSTS (2 years), `nosniff`, `X-Frame-Options: SAMEORIGIN`, `strict-origin-when-cross-origin`, a Permissions-Policy that keeps only the camera (rep counting), Web Bluetooth (heart rate) and the position for our own pages (`geolocation=(self)`: Find gyms near you and the `/gyms/` map, 2026-11-15), and a CSP of `frame-ancestors 'self'; object-src 'none'; base-uri 'self'; form-action 'self'`. Routes with their own stricter policy (the inbox email view) keep it. The one exception is `/embed/<slug>/` (free calculators other sites put on their pages, [Public pages and SEO](docs/decisions/public-pages-and-seo.md)): same headers without `X-Frame-Options`, with `frame-ancestors https: 'self'` (`EMBED_HEADERS`), because they hold no account state or action worth a tricked click. **Script policy** (2026-11-10): the account session token is in localStorage, so injected script must not run. Next writes different inline scripts into every page, so `scripts/csp.mjs` hashes each prerendered page's own inline scripts and adds `<meta http-equiv="Content-Security-Policy" content="script-src 'self' 'wasm-unsafe-eval' https://accounts.google.com https://appleid.cdn-apple.com 'sha256-…'">` right after its charset; no `'unsafe-inline'`, no `'unsafe-eval'` (`'wasm-unsafe-eval'` is for rep counting, the two hosts for Sign in with Google and Apple). Pages rendered per request have none, so keep pages static (the one exception is the public share link page, `/w/<id>/`, which is plain HTML with no scripts and its own `default-src 'none'` policy; see [Sharing](docs/decisions/sharing.md); the server-drawn `/gyms/` page runs only our own files under `GYMS_INDEX_CSP`, `script-src 'self'`, see [Gyms](docs/decisions/gyms.md)). New inline scripts need nothing extra (they're hashed), but a script from another host must be added to `SCRIPT_SOURCES`. It runs in two places: on Vercel inside `next build`, as a deployment adapter (`scripts/csp-adapter.mjs`, set as `adapterPath` only when Vercel sets `NEXT_ADAPTER_PATH`) that adds the policy and then hands over to Vercel's own adapter, because that adapter copies the pages into its output before `postbuild` runs (until 2026-11-20 no live page had the policy: the log said "Script policy added to 0 pages"); and as `postbuild` everywhere else. Never rely on a `postbuild` rewrite of `.next/` reaching production. `src/lib/csp.test.ts` checks the script and the adapter. **The native apps don't carry it** (Platform deltas): on Android WebViews without document-start scripts, Capacitor puts its bridge into the page as an inline script whose hash we can't know, so a policy could stop the app from starting, and the apps only ever load their own files.
- **Creator commission counts only store-verified events** (`source = 'store'`, from the RevenueCat webhook). The app's own `trial_start` and `purchase` events reach `/api/collect/` without authentication, so they may stand in for revenue on the admin panel until the webhook is set, but never for money owed to a creator (`loadCreators`).
- **Rate limits are one atomic statement** (`rateLimit` in `db.ts`: an upsert with `RETURNING count`), so a burst of parallel requests can't all read the same count. **Email sign-in codes count each try before comparing** and are used up with a conditional update, so parallel guesses can't pass the five-try limit. Both have tests that fail on the old read-then-write code.
- Every public route that writes or sends rate-limits through the database, never only in memory (serverless instances don't share memory): feedback per address, `/api/collect/` per install and per address. Secrets in headers (cron, RevenueCat) are compared in constant time (`authorized` in `revenuecat.ts`).
- **Two Stripe webhooks, kept apart** (audit, 2026-11-13): `/api/billing/stripe/webhook/` (Pro on the web, `STRIPE_WEBHOOK_SECRET`) ignores any event carrying `account` (a coach's connected account), and `/api/coach/stripe/` (client payments, `STRIPE_CONNECT_WEBHOOK_SECRET`) only applies events whose `account` is the coach's own Stripe account named in the payment's metadata. A client paying a coach can never become Pro or Liftsmith revenue, even if an endpoint is set to listen to the wrong events.
- **Pro that isn't bought is checked against what can be checked** (audit, 2026-11-13): a phone's store subscription counts only for the account that synced from it last (`LATEST_INSTALL`), and earned Pro (invites, coaching 3+ clients) counts only finished workouts with 3+ logged sets ([Money](docs/decisions/money.md)).
- **Admin AI helpers only suggest** (Melvin, 2026-11-16): every request goes through `askClaude` in `src/server/ai.ts`, behind the `aiHelpers` kill switch and the `aiDailyCap` flag (US dollars a Pacific day, default 2; typed on the Flags tab, from $0.01 to $1,000, and over $50 it asks "Are you sure?" first, Melvin 2026-11-19), with public text wrapped as data and answers held to a schema; staff press the existing button to act ([Admin AI helpers](docs/decisions/admin-ai.md)). The exceptions are the gym import's AI backfill (Melvin, 2026-11-16), which fills only empty fields of unclaimed gyms with answers checked in code (`gymAutoFill.ts`, [Admin AI helpers](docs/decisions/admin-ai.md) "The import's AI backfill"), and the **AI fix-up pass** (Melvin, 2026-11-19: "only run against unclaimed gyms and … only run on them once"), a button on Admin › Gyms › Import that checks each unclaimed gym with a website against its own page once ever (`gym_places.ai_fix_at`) under **strict rules** (Melvin, 2026-11-19: "if we are NOT sure, we need to not change things"): nothing at all unless the page shows the gym's own street address or is a one-location site, only empty fields filled (units kept in front), a filled field never changed (a page that says otherwise is a suggestion staff Apply or Dismiss), formatting never counted as a change; it sends closed or not-a-gym pages to Reports, keeps every change with Undo and pauses at the daily cap until midnight Pacific (`gymAiFix.ts`, [Gyms](docs/decisions/gyms.md) "AI fix-up pass").
- Rate limits key on the first `x-forwarded-for` address, which Vercel sets itself.
- **This repo is public** (audit, 2026-11-11). Never commit a real code that unlocks anything (a lifetime Pro code, the store review code, a promo code meant to stay private): not in docs, tests, comments or commit messages. Test fixtures use made-up codes. **Lifetime Pro codes are 10+ characters** (`LIFETIME_MIN`, checked by the admin form), because the public code lookup answers without an account. **Admin sign-in links are used up in one statement** (`UPDATE … WHERE used_at IS NULL RETURNING`), so two requests racing with one link can't both get a session.
- **Code and models come from our own origin, never a CDN.** Camera rep counting's MediaPipe runtime and pose model are our own copies under `public/mediapipe/` (runtime copied from the lockfile-pinned package by `scripts/mediapipe.mjs`; model committed and hash-checked by `mediapipe.test.ts`). The only outside scripts are Google's and Apple's sign-in libraries on the website (`accounts.google.com`, `appleid.cdn-apple.com`, loaded only when the lifter taps that sign-in button), because their makers serve them only from there. A new library or model is bundled or self-hosted.
- **The web view's storage stays out of phone backups** (Melvin, 2026-11-10). It holds workouts, health readings, injuries, cycle logs, progress photos and the account session token. Android keeps `allowBackup` on but excludes `app_webview/` (and the WebView's prefs) from Google's cloud backup and from phone-to-phone transfer (`res/xml/data_extraction_rules.xml` for Android 12+, `full_backup_content.xml` for older); iOS marks `Library/WebKit` as excluded from iCloud and computer backups at launch (`AppDelegate.swift`). Signing in and sync, or a backup file, carry the data to a new phone instead. `storePolicy.test.ts` checks both. Anything new the app stores natively that holds personal data gets the same exclusion.

## Architecture decisions

- **Stack copied from Gradelings** (`mjparinas/gradelings`): Next.js 16 static export, React 19, TypeScript, Tailwind 4, Zustand, Vitest.
- **Capacitor, not Bubblewrap (Melvin chose it, 2026-11-09).** A TWA can't run a foreground service, show a live lock-screen countdown, read Health Connect, keep Bluetooth heart rate going with the screen off, or use StoreKit (it has no iOS app). Capacitor wraps the same static export and adds those through native plugins; it also builds the iOS app. The cost is a store release for each app change.
- **Offline-first, like Gradelings.** Everything the lifter does is an event with a unique id (set, session start and end, feedback, swap), appended to IndexedDB first (`localdb.ts`). Stats, PRs, recovery, streaks, XP and progression are recomputed from events, never stored (`derive.ts`), so merging devices is order-independent and duplicate-safe. Profile and gyms are last-write-wins on `updatedAt`.
- **Two builds** (`next.config.ts`): `npm run build` is the Vercel server build with API routes named `route.api.ts`; `npm run build:static` (`STATIC_EXPORT=1`) is the static export for the native shells and CI, and it leaves those routes out. Native apps call the API on `SITE_URL`. **The apps carry only the app, not the website** (2026-11-11): after every `cap copy` or `cap sync`, `scripts/native-web.mjs` deletes everything in the shell's copy of `out/` except `app/`, `_next/`, `mediapipe/`, the icons and the manifest (`KEEP`), which took both apps from about 387 MB of web files to 27 MB. Something new that app screens load by a root path goes on `KEEP` ([App size](docs/decisions/app-size.md)).
- **Sync (built, 2026-11-09):** `POST /api/sync/` (`src/server/sync.ts`, client `src/lib/sync.ts`) pushes this device's new events and deletes and pulls the account's other devices' by cursor, on open, on return to the foreground, when back online, and 4 s after a change. The outbox (`src/lib/syncOutbox.ts`, localStorage) is filled by `localdb.ts` itself, so anything that writes there (the store, a restored backup) is queued; writes that came from sync pass `{ remote: true }` and aren't sent back. Signing in queues every event once. Server: `sync_events` (one row per account and event id, `seq` is the cursor; a delete becomes a tombstone with a new seq that is never undone; a device never gets back what its own session wrote) and `sync_records` (`profile` and `gym:<id>`, last write wins on `updatedAt`; a removed gym is a null record). **On a device's first sync the account's profile wins** over the device's, so signing in on a freshly set-up phone brings the lifter's own settings back; gyms are merged. 500 events per page, 1,000 per push, 3.5 MB per request, 600 syncs an hour per account. **Storage quota per account** (`QUOTA` in `sync.ts`, 2026-11-10): 200,000 events (tombstones included), 50 MB of event bodies and 200 records; a push that would pass it is refused whole with 413 `full`, nothing from it is stored, and the device keeps its data and shows "sync storage is full" (`account.syncFull`). A lifter training five days a week writes about 10,000 events a year, so only abuse reaches it. Everything in the event log syncs, health readings, injuries and cycle logs included (the user's own account only); progress photos never do. A 401 with the server's `signedOut` marker signs the device out and wipes it too, unless changes there never reached the account (then it keeps them and offers sign in again, a backup or erase). **Signing out from Settings › Account wipes the device** (Melvin, 2026-11-13): it pushes what's waiting first (and offers Try again, a backup file or Sign out anyway when it can't), then erases the event log, photos, the workout in progress, the widget and every personal `liftsmith.*` / `ls.*` key, and reloads; signing in as a different account than the one whose data is on the device wipes it first, so accounts never mix (`signOutDevice.ts`, `wipe.ts`, [Accounts and sign-in](docs/decisions/accounts-and-sign-in.md)). Anything new that stores personal data under another key prefix must be added to `wipe.ts`.
- **Local first, sync behind** (Melvin, 2026-11-13: "data should always sync in the background … gyms can have bad reception"). No screen waits for the network to show what it already knew: a screen that shows something from our server shows the copy kept on the device at once and refreshes behind it (`liveRead` in `src/lib/liveRead.ts`, per account in `liftsmith.reads`, kept when the server can't be reached), and background requests go through `track` (`src/lib/net.ts`), which shows a small spinning ring at the top centre while they run (`SyncSpinner.tsx`; never during a workout, not drawn when idle). `api()` reports whether the server was reached, so `useNet().offline` is real, and Friends says it's showing the last copy while offline. Details in [Background sync](docs/decisions/background-sync.md).
- **The schema check on a server's first query is one read** (`migrate` in `db.ts`, 2026-11-12): it lists what the database already has and makes only what's missing, in one batch. Each statement is a network hop to Turso, and running all of them one by one made every cold start take about four seconds. Add tables and indexes to `SCHEMA` and columns to `COLUMNS` as before ([Friends](docs/decisions/friends.md) "Loading fast"). **`SCHEMA` holds only `CREATE` statements** (2026-11-16): a data fix there runs on every cold start, and Turso bills every row it reads; a province fix-up that scanned the whole gym table 13 times per start used most of a month's reads. Run one-off fixes once. Public pages that read a whole table keep their answer. **Every new query on a table that grows uses an index** (Melvin, 2026-11-16): events, sync events, posts, comments, likes, follows, profiles, gyms, coaching tables, the email log and the like. Check it with `EXPLAIN QUERY PLAN` (`SEARCH … USING INDEX`, never `SCAN <table>`, except one-off admin work and the daily job), add the index to `SCHEMA` (or `LATE_SCHEMA` for a column added through `COLUMNS`) in the same change, and add the query's shape to `dbIndexes.test.ts`; a partial index is used only when the query repeats its `WHERE` ([Database reads](docs/decisions/database-reads.md)).
- **One static page for the app** with hash routes (`#/today`, `#/workout`, …), so it works offline from one cached page. **The address says what the screen is called** (Melvin, 2026-11-14): `URL_NAMES` in `router.ts` gives a screen its own name where the route's differs (`#/progress`, `#/awards`, `#/coaching`, `#/gyms`, `#/stretching`, `#/workout-preferences`), and Body's two views are `#/muscles` and `#/health` (the route stays `recovery`, the view is its argument, switching swaps the address without a step for back). The old names still open their screen and the address is rewritten to the new one, so old links, bookmarks, notifications and reminders keep working. Links other people open (coach invites, shared routines, gyms, clubs) and server push routes are still made with the old names, so an older app on someone's phone can open them; switch them once every app in use knows the new names.
- **No A/B tests** (Melvin, 2026-11-15: "remove a/b tests in the admin"). The admin A/B Tests tab, `/api/admin/experiments/` and the experiment code are gone; feature flags change only through the admin Flags tab (a value for everyone or a rollout to a share of installs), and `GET /api/flags/` records nothing. Details in [Analytics and the admin panel](docs/decisions/analytics-and-the-admin-panel.md).

## Code conventions (Melvin asked, 2026-11-09: "easier to maintain and change")
- **Strict TypeScript plus** `noImplicitReturns` and `noFallthroughCasesInSwitch` (`tsconfig.json`). No `any`.
- **The training engine also has `noUncheckedIndexedAccess`** (`tsconfig.engine.json`, `npm run typecheck:engine`, a CI step): reading `list[i]` or `record[key]` there is typed as possibly missing, so an index that can run off the end shows up at compile time. Handle the missing case, or add `!` only where the index is in range by construction (a loop bound, the first item of a group that can't be empty). A new engine file goes in that config's `include` list.
- **Prettier formats every code file** (`prettier.config.mjs`: width 140, imports sorted and grouped: Node, packages, `@/`, relative). Run `npm run format` before committing; CI's Formatting step fails on unformatted code. Docs and data files are left as written (`.prettierignore`). Formatting-only commits go in `.git-blame-ignore-revs`.
- **App state is one Zustand store in slices** (`useApp` from `src/lib/store.ts`, the only import path). Each area's state and actions live in `src/lib/store/<slice>.ts`: `workout` (the workout in progress), `plan` (profile, gyms and Today's plan), `injuries`, `health` (cycle, weigh-ins, Health imports, TDEE), `routines` and `history` (editing, deleting, naming and repeating finished workouts); `store.ts` keeps loading, sync, backup and erase. A slice gets `set`, `get`, `commit` and `gym` through `Ctx` (`store/shared.ts`). New actions go in the slice they belong to, with their type in its `…Slice` interface.
- **Ten languages, every change** (Melvin, 2026-11-10: all G7 countries; 2026-11-15: Brazilian Portuguese, Korean, Polish and Turkish): English, Spanish, French, German, Italian, Japanese, Portuguese (Brazil, code `pt`), Korean, Polish and Turkish (`LANGS` in `src/lib/i18n.ts`). New text goes into its catalogue file (`src/locales/text/<prefix>.ts`) in all ten in the same change, and native text into every `values-<l>` and `<l>.lproj` file; `i18n.test.ts` and `nativeStrings.test.ts` fail otherwise. The app loads one language at a time (`scripts/locales.mjs`, `src/locales/load/`), so app code never imports a catalogue (`@/locales/en` and friends) at run time; use `t()` or `english()` ([Speed](docs/decisions/speed.md)). Splice a label into a sentence with `inSentence()`, never `toLowerCase()` (German capitalises nouns), give Japanese and Korean plurals only `other` and Polish `one`, `few`, `many` and `other`. Register, fixed terms and the Japanese, Korean and German layout rules are in [Borrowed from Gradelings](docs/decisions/borrowed-from-gradelings.md) under Languages. **Choosing the language** (Melvin, 2026-11-16: "allow users on the web to change their language"): the app follows the phone (apps) or the browser (web, "Match my browser") until the lifter picks one of the ten, from a language button on the welcome screen (before setup's first question) or Settings › Look and feel › Language, one list in `LanguagePicker.tsx`, saved as `profile.language`, which syncs. Shared web code, so Android, iOS and the web get it together ([Setup wizard](docs/decisions/setup-wizard.md)).
- **English is Canadian English** (Melvin, 2026-11-11: "ensure it uses Canadian spellings"). Every piece of English a person reads (the `en` catalogues, hard-coded UI text, the website, blog posts and guides, emails, notifications, the Android, Wear OS, iOS, watch and Garmin text, the store listing, the admin panel) uses Canadian spelling: *-our* (colour, favourite, behaviour, endeavour), *-re* (centre, metre, litre, fibre), doubled *l* (levelled, cancelled, travelled, labelled), catalogue, defence, grey, cheque, "practice" as the noun and "practise" as the verb, but **-ize and -yze** (organize, prioritize, realize, stabilize, analyze), "program" (not "programme"), "math" (not "maths"), tire, curb and aluminum. Proper names keep their own spelling (Labor Day, the Whole Earth Catalog).
- **Type-aware lint on `src/`** (`eslint.config.mjs`): `no-floating-promises` (a promise nobody waits for loses its error; await it, or mark a deliberate fire-and-forget with `void`), `no-misused-promises` (no async function where a plain callback is expected; JSX handlers may be async), and `switch-exhaustiveness-check` (a `switch` over a union covers every case or has a `default`).

## Testing (Melvin asked, 2026-11-09: like Gradelings)

## CI/CD (Melvin asked, 2026-11-09: like Gradelings)

- `.github/workflows/ci.yml` on every pull request and push to `main` and `staging`: types, lint (no warnings), dependency audit, unit and integration tests with coverage, build, then browser tests in three parallel jobs. **"CI passed"** is the one required check.
- `mutation.yml`: **on demand only** (Actions › Mutation tests › Run workflow). Mutation runs are long and expensive, so they never run on pull requests or merges and never gate a merge (Melvin, 2026-11-09). Run one after a batch of engine work and raise `break` when the score rises.
- `promote-staging.yml` (Melvin confirmed the Gradelings model, 2026-11-09): `main` is production and every pull request targets `staging`. At 09:00 UTC each night it opens a staging → main pull request and merges it when "CI passed" is green on staging's latest commit, then merges `main` back into `staging`. Run it by hand from the Actions tab to ship sooner; run right after a merge, it waits (up to 25 minutes) for CI on staging to finish instead of failing, and still refuses when CI failed (2026-11-16). When staging's only new commit is the "Bring main back into staging" merge (same files as `main`), there is nothing to promote and it says so at once; that merge is pushed with `GITHUB_TOKEN`, which starts no workflows, so it never gets CI of its own, and a run that waited for it used to sit the full 25 minutes. A merge that changed no files counts the CI of the parent with the same files; any other commit with no CI run after two minutes fails with a message saying to merge or push to staging first (2026-11-16). A merge that GitHub answers with 405 "Base branch was modified" right after the pull request opens (it hasn't worked out mergeability yet) is tried again every 10 seconds, up to six times (2026-11-17). Scheduled workflows only run from the default branch, so the file must be on `main` before the nightly run starts. It needs "Allow GitHub Actions to create and approve pull requests" on, and `PROMOTE_TOKEN` if `main` requires reviews.
- `ci.yml` also builds an Android debug APK (uploaded as an artifact to install and try) and an unsigned iOS simulator build. Both are part of "CI passed".
- **CI speed (Melvin asked, 2026-11-09 and 2026-11-10: "find other ways to reduce CI runs").** The `changes` job decides what a run does, and "CI passed" counts a skipped job as passed, so the required check still reports:
  - *Already tested:* when "CI passed" succeeds it records the tree it tested as a commit status (`CI passed tree`, on the pull request's head commit or the pushed commit). A run whose tree already passed (on a parent, on the pull request a squash commit came from, or on the same commit) skips every job. That covers the staging push after a merge when staging didn't move meanwhile, the nightly promotion pull request, the push to `main` and the merge back into `staging`, which used to run the whole suite four more times for code that had already passed.
  - *Markdown only, never CI* (rule, Melvin, 2026-11-17: "we only made md changes, dont run ci if that is the case"): when every changed file is `.md` (docs, `AGENTS.md`, READMEs), the tests and builds are skipped, whatever state the commit before was in, and "CI passed" reports green at once. Markdown can't break the build, and the base branch's own run reports its own failures. `docs/PLAY_LISTING.md` and `docs/PLAY_LISTING_TRANSLATIONS.md` still run everything, because `playListing.test.ts` reads them; a new test that reads a Markdown file adds it to that exception in `ci.yml`. Keep docs-only changes in a pull request of their own, so they don't pull in a full run. **Locale text (`src/locales/`) is not treated as copy**: it's app code, the tests check every key in every language, and longer text can break layouts at large text sizes, so it runs the full web suite (but not the native builds).
  - *Native builds* run only when the diff touches `android/`, `ios/`, `capacitor.config.*`, `package.json`, `package-lock.json`, `ci.yml` or `.github/actions/`, on pull requests and on pushes alike (pushes used to build both every time; `release.yml` still builds both on every promotion). Add a path to that filter whenever something new can affect native builds.
  - Runs on the same branch or pull request cancel the one in progress. The device sweep runs as two jobs (`DEVICES=ios` and `DEVICES=android`) and the iPhone playthrough is in the playthrough job. Gradle uses its build cache (cached across runs) and `--parallel`. The iOS simulator build compiles arm64 only, with no index store, and uses a placeholder `out/` so it starts without waiting for the web build. **Shards without dropping a check** (Melvin, 2026-11-16: "speed up ci without reducing safety"; measured on ten runs: about 9.5 minutes, with the accessibility job alone at 6.5 because it ran both `e2e-a11y.mjs` and `e2e-gaps.mjs`): the unit tests run as two `vitest --shard` jobs whose blob reports the Unit test coverage job merges into the same coverage summary; `e2e-a11y.mjs` runs as `A11Y_PART=app` (every phone app screen in each theme and setting) and `A11Y_PART=more` (the public pages, the keyboard run and the desktop layout), and `e2e-gaps.mjs` as `GAPS_LAYOUT=phone` and `desktop`, each half about two minutes. Unset, each script still runs everything locally. Every test and screen runs exactly once; keep shards balanced when adding screens (a new app screen goes in the `app` part, a new public page in `more`). The longest path is now the build then the slowest browser job, about 6 minutes.
