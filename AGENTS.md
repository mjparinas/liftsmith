# Liftsmith: guide for agents

Liftsmith is an Android-first adaptive strength training app. It plans each workout from the lifter's equipment, recovery and training block, then gets out of the way while they lift. This file records every product and technical decision made so far, and why. Follow them. If a task seems to need one changed, raise it with the owner (Melvin) first, and when a decision changes, update this file in the same change.

The full plan with stages lives in the plan doc: https://claude.ai/artifact/S24kx43ZkQ8g3gGtGew34n

## Commands

```bash
npm run dev                  # http://localhost:3000 (public site), http://localhost:3000/app/ (the app)
npm test                     # unit + integration tests (Vitest; engine in node, screens in jsdom)
npm run test:coverage
npm run test:mutation        # Stryker on the engine; report in reports/mutation/
npm run lint && npx tsc --noEmit
npm run build                # server build (Vercel): pages plus API routes (route.api.ts)
npm run build:static         # static export to out/ (native shells, browser tests)
node scripts/e2e.mjs         # full playthrough (serves out/ itself, or pass a base URL)
node scripts/e2e-offline.mjs # real offline after one visit
node scripts/e2e-devices.mjs # layout on 13 phones and tablets (DEVICES=ios|android|full|names)
DEVICE='iPhone 16' node scripts/e2e.mjs  # the playthrough on another device
node scripts/e2e-a11y.mjs    # axe WCAG 2.2 AA on every screen
node scripts/site-screenshots.mjs # real app screenshots for the home page (public/screens/)
npx cap sync                 # copy out/ into the Android and iOS shells (after npm run build:static)
```

There is no Android SDK in cloud sessions; APKs and AABs build in GitHub Actions (`.github/workflows/android.yml`).

## Platform parity (rule, Melvin, 2026-11-09)

- **Every feature goes in both apps, plus the web app wherever it makes sense** (Melvin, 2026-11-09). Each feature lands on Android and iOS in the same change: native Android code (Java or Kotlin in `android/`) and native iOS code (Swift in `ios/`) for anything the web layer can't do. The web app (`/app/`) gets it too when the browser can do it (for example, `.ics` files instead of calendar access, and manifest shortcuts instead of widgets).
- **One-platform features are allowed when they're very useful** (Melvin, 2026-11-09). If a feature is very useful on one platform but the other ecosystem can't support it, build it anyway. Record the gap under "Platform deltas" below, and in the pull request description, say what each platform does instead.
- Platform equivalents: Health Connect ↔ HealthKit (Apple Health); foreground-service notification ↔ Live Activity (lock screen and Dynamic Island); Play Billing ↔ StoreKit; Sign in with Google ↔ Sign in with Apple (both offered on iOS); Wear OS ↔ Apple Watch.
- CI builds both apps together (`android` and `ios` jobs in `ci.yml`): on every pull request that touches native code, Capacitor or dependencies, and on every push to `staging` and `main`. Both always run or skip together.
- **Live workout notification today:** Android runs a foreground service (`WorkoutService.java`) with an ongoing notification: lock-screen rest countdown (chronometer), next set and plates, heart rate, and Log set / +30 s buttons, plus a rest-over alert. iOS (`WorkoutSessionPlugin.swift`) runs a **Live Activity** (lock screen and Dynamic Island: rest countdown, next set and plates, heart rate, Log set / +30 s links; drawn by the `LiftsmithWidgets` extension) and schedules a time-sensitive rest-over notification with the same two buttons. Heart-rate-only changes reach the Live Activity at most every 15 s, because iOS budgets updates. Both are driven by the same `WorkoutSession` calls in `src/lib/sessionNotify.ts`.
- Native code registered by the app: Android `MainActivity.registerPlugin`, iOS `MainViewController.capacitorDidLoad` (Capacitor 8 with SPM doesn't auto-register app-target plugins). `InstallInfo` (device and install source for analytics) is registered on both.
- Native apps open straight into the app (`server.appStartPath: /app/index.html`); the landing page is for the website.

## Product decisions

### Positioning
- **An original app.** It borrows ideas from Fitbod (daily adaptive workouts, equipment matching, recovery map, variability setting) and Gymverse (periodized blocks with RIR and deloads, exercise swaps, lock-screen timer). It never uses their names in the UI, their art, screenshots, exercise videos or exact look. Exercise names, setup text and cues are our own.
- **Focus on the workout, not the app.** One tap logs a set as planned. The next set is always pre-filled. The rest timer starts itself. Anything optional (feedback, swaps, info) appears between sets and never adds a tap during a set.
- **Explain every label that isn't obvious** (Melvin, 2026-11-09). Jargon and training terms (deload, build weeks, RIR, readiness, today's call, volume, estimated one-rep max, sets per muscle, exercise variety, recovery, warm-ups) get the one shared `Info` button (`src/components/Info.tsx`): a small "i" with a 44 px tap target that opens a short plain-language dialog. The text lives in `src/lib/glossary.ts`, so it can be translated in one place. `Section` (app) and `Panel` (web dashboard) take an `info` term. Any new label a lifter might not understand gets a glossary entry in the same change.
- **Dark, trustworthy, professional.** Deep navy-black background, one blue brand accent (`#4c8dff`, one CSS variable so cosmetics can recolour it), green, amber and red reserved for status (recovery bands, warnings). Large touch targets, tabular numbers, system font (Roboto on Android).
- **Light mode** (Melvin, 2026-11-09). **Settings › Appearance: Dark (default), Light, or Match system.** It sets `data-theme` on `<html>` (`src/lib/theme.ts`), saved on the profile and in localStorage so the next launch paints the right theme before the profile loads; it also sets the browser bar colour and the native status bar style, and the web dashboard follows it. **Every colour is a token** in `globals.css` with one dark and one light value, including badge tiers, crate rarities and heart rate zones (`--tier-*`, `--rarity-*`, `--hr-*`); never hard-code a hex in a component. The light accent is a darker blue (`#1d4fc4`) so text passes contrast, and an equipped accent cosmetic is darkened on light screens (`applyAccent`). The design pass's effects (primary gradient and its ink, screen glow, card sheen and shadow) are variables too (`--grad-*`, `--btn-ink`, `--glow-*`, `--sheen*`, `--shadow`); the light primary button is a deeper blue-to-violet with white ink. Earned themes (`themes.ts`) are dark palettes: on a light screen only their accent carries over, darkened, and the light surfaces stay. Order: Appearance, then the earned theme, then an equipped cosmetic accent. `src/lib/appearance.ts` is Appearance; `src/lib/themes.ts` is earned themes. The axe run checks the main screens in both themes. The share image stays dark.

### Visual design system (Melvin, 2026-11-09: "liven it up, but keep it simple and professional")
- **Tokens live in `src/app/globals.css`.** Brand blue plus four supporting hues used only as tints for marks, chips and card glows, never for body text: violet `#a78bfa` (levels, Pro, quotes), cyan `#38d6e8` (rest, time, easy days), ember `#ff8a3d` (streaks, push days, challenges), mint `#34d399` (done). Status colours keep their meaning. Named roles are in `src/components/app/theme.ts`: muscle families (push blue, pull cyan, legs violet, core ember) and the readiness call (push ember, normal blue, easy cyan).
- **The primary action is a blue-to-violet gradient with dark ink** (`.btn-primary`, 7:1+ contrast). One primary per screen. Cards are raised glass (`.card`, hairline border and a faint top light); `.card-tint` with `--tint` gives a card a hue for the hero card on each screen. A soft light sits at the top of every screen (`.aurora`).
- **Type:** 28–30 px extra-bold screen titles, tight tracking; big numbers use `.display` (tabular, 800). Section labels are small caps with an icon.
- **Icons:** one hand-drawn stroke set (`src/components/app/icons.tsx`, 24-unit grid, 2 px). No emoji in app chrome.
- **Empty states** use `EmptyState` (icon in a tinted tile, a title, one line of help, and an action when there's an obvious next step). No bare "nothing here" lines.
- **Motion:** short and purposeful (`rise`, `pop`, `fade`, `bump` on a stepper number, `burst` from Log set, `beat` on the live heart rate). Nothing moves during a set except what the lifter touched. `prefers-reduced-motion` and **Lean mode** (`profile.lean`, Settings) both cut motion and confetti (`.calm` on `<html>`, `calm()` in `juice.ts`).
- **Sound set:** every sound is one synthesized voice (a soft glassy mallet) in A major pentatonic (`juice.ts`), so sounds never clash: a near-silent tick for steppers and chips, a rising pair for Log set, a phrase for Start, a three-note chime for rest over, a falling pair for discard, a longer phrase for the end of a workout. No sound on navigation. One **Sounds** switch (`profile.restSounds`) covers them all.
- **Haptics** go through `@capacitor/haptics` on both Android and iOS (selection ticks for steppers, chips and tabs; medium for Log set; heavy at rest end; success and warning notifications), falling back to `navigator.vibrate` on the web. **Vibration** can be turned off in Settings (`profile.haptics`).
- Before/after screenshots: `node scripts/shots.mjs [base-url] [out-dir]` (after `npm run build:static`).

### Accessibility (Melvin, 2026-11-09: "accessibility checks, WCAG guidelines, colour blind support")
- **Target: WCAG 2.2 AA everywhere**, checked in CI. `scripts/e2e-a11y.mjs` runs axe on every screen in dark and light, again with colour-blind safe colours and more contrast, once under forced colours, then a **keyboard-only run** at the **largest text on a 360 px phone**: every Tab stop shows a focus ring, a workout starts and a set logs without a pointer, sheets take focus, keep Tab inside and close on Escape with focus returned, and no screen scrolls sideways. `src/lib/a11y.test.ts` checks the colour tokens: status colours 4.5:1 as text, recovery colours 3:1 against cards, and both colour sets simulated for protanopia, deuteranopia and tritanopia (Machado 2009) so they stay apart. Lint runs the full strict `jsx-a11y` rule set.
- **Settings › Accessibility** (`src/lib/a11y.ts`, saved as `profile.a11y` and in localStorage so the first paint is right):
  - *Text size:* Match my phone (default), Default, Large, Larger, Largest (100 to 150%). It scales the root font size; **every font size is in rem** (no `text-[Npx]`), so all text follows. On Android and iOS, Match my phone reads the phone's own size (font scale, Dynamic Type) through `@capacitor/text-zoom` and pins the WebView's own zoom at 100%, one path on both platforms. Layouts wrap rather than scroll sideways at the largest size.
  - *Colours:* Standard or **Colour-blind safe** (blue, light blue, orange and pink for recovery; blue, orange and pink for good, warn and bad). Status and recovery colours are tokens with `-std` and `-cvd` values per theme (`--band-*`, `--good-*`, `--warn-*`, `--bad-*`), picked by `data-cvd` on `<html>`. Heart rate zone colours already pass the simulation and stay as they are.
  - *Contrast:* Match my phone (follows `prefers-contrast: more`), Standard, or More (secondary text and borders mixed toward the ink colour; glows, sheen and gradient text removed). Built from each theme's own ink and background, so it works in dark and light.
  - Motion: Lean mode and the phone's reduce motion setting (unchanged).
- **Colour is never the only cue (WCAG 1.4.1):** the recovery map and its legend add dots (Recovering) and stripes (Fatigued); picked chips show a tick; every band also has a label and a percentage.
- **Screen readers:** the rest timer is a `timer`; a polite live region says when rest starts, at ten seconds left and when rest is over (not every second). Sheets are modal dialogs labelled by their title.
- **Forced colours** (Windows High Contrast): cards and buttons keep an edge, the focus ring uses `Highlight`, and the recovery map keeps its colours (`.keep-colours`).
- **Quick, one-handed input (Melvin, 2026-11-09: "the less manual typing the better"):** every screen should be fast to adjust in the gym. Prefer steppers with bump buttons, sliders, toggles and chips over text fields, and offer typing only as a fallback. Design for one hand, and respect left- or right-handed use.
  - Every − / + bump (`Bump` in `ui.tsx`) **repeats while held**, faster the longer it's held; a keyboard or screen reader click steps once.
  - Numbers a lifter would type use **`BumpField`** (− box +, typing still works): body weight in setup, Settings and the weigh-in on Progress and Body and photos, age and known lifts in setup, and bar weights in Gyms. An empty box bumps from a sensible start (the last weigh-in, 30 years, a common bar). New number inputs use it too.
  - **One-handed controls** (Settings › Accessibility: Off, Right hand, Left hand; `profile.a11y.hand`): during a workout the weight and rep bumps move down into a dock beside Log set, with Log set under that hand's thumb; the big numbers stay on the set card. Off by default.
- Every new screen gets an axe scan in the a11y run, and every new colour is a token that passes `a11y.test.ts`.

### Today screen (Melvin, 2026-11-09)
- The greeting uses the lifter's first name when one is set ("Good evening, Melvin"). Setup's first step asks for it (optional), and Settings can change it.
- **Daily quote:** one quote a day on Today about effort, health, hard work and discipline, from `src/lib/quotes.ts` (380 quotes, at least 365 so none repeats within a year; bundled, so it works offline). A fixed seeded shuffle picks the day's quote, so every device shows the same one and it changes at local midnight. Every quote has its author and, where known, its source; only documented quotes, with common misattributions left out (a test checks a few). Settings › Daily quote turns it off (`profile.quotes`).

### Training engine (src/lib)
- **Equipment and gym profiles.** Each gym has its own equipment list, bars, the exact plates owned (with counts), dumbbells, kettlebells and machine step. The generator uses only exercises whose every needed item is at the active gym (`available` in `exercises.ts`).
- **Bodyweight exercises** cover every major muscle, so a "Bodyweight" gym (hotel, park) gets full workouts. A test checks this.
- **Workout length.** A slider from 15 to 90 minutes. The plan is seeded by day and gym, so moving the slider adds or drops exercises at the end instead of reshuffling (`generator.ts`). **Every length counts warm-up sets and rest** (Melvin, 2026-11-09): an exercise is setup (60 s), its warm-ups with 60 s rest after each, its working sets, and the rest between them, and the rest before each exercise counts too (`itemSeconds`, `planSeconds`). Today shows each exercise's minutes and warm-up count. If the final order's warm-ups push the plan past the time asked for, sets come off the end.
- **Warm-up sets** (Melvin, 2026-11-09; `warmup.ts`). The first loaded lift for a muscle ramps up on weights the gym can make: the empty bar ×10 for barbells, then about 55%×5 and 80%×2 (or 50/70/85% for 100 kg and up). Machines and dumbbells get 50%×8 and 75%×4. A later barbell lift for muscles that are already warm gets one feeler set (70%×3). A first isolation exercise gets one light set, and bodyweight and timed exercises get none. Warm-ups are their own `warmup` event, so stats, recovery, progression, PRs and XP never count them. The workout screen shows "Warm-up 1 of N", with a 60 s rest and a Skip warm-up link.
- **Recovery.** Each set adds fatigue to its primary muscles (full) and secondary muscles (half), less when far from failure. Fatigue fades so 90% is gone after about 48 h for small muscles and 72 h for large ones. Bands: Fresh 90%+, Ready 70%+, Recovering 40%+, Fatigued under 40% (`recovery.ts`). The generator only targets muscles at 55%+ and avoids exercises whose primary muscles are under 40%.
- **Periodization.** Blocks of 3 to 6 build weeks (default 4) then a deload week. RIR steps down across the build weeks (3, 2, 1, 0 for four weeks); the deload is RIR 4 at half the sets. Weekly sets per muscle rise from 8–12 to 12–20 by experience (`block.ts`).
- **Progression.** Double progression on top of the RIR target: hit every set's target and the next session adds a rep; at the top of the rep range, the weight goes up one loadable step and reps go back to the bottom; a miss by 2+ reps drops a step. Post-exercise feedback (too easy, too hard) shifts it one more step (`progression.ts`).
- **First-session starting weights** (Melvin, 2026-11-09, after a 145 lb "experienced" lifter was offered a 175 lb squat). Each exercise's `start` is a share of body weight for about 10 reps. That gives an estimated one-rep max, scaled by experience (new 0.55, some 0.8, experienced 1.0, because self-reported experience runs high), sex (women 0.6 upper body and 0.75 lower; unknown sits between), and age (from 40, 0.92 down to 0.65 at 70+). The first session then aims 2 reps further from failure than the block asks (`FIRST_RIR`). Known numbers entered in setup (squat, bench, deadlift, overhead press as weight × reps) replace the estimate for that lift, and scale to close relatives at 85%. **Quick calibration:** if the first session shows the start was light ("too easy", 2+ reps over target, or the lifter raised the weight), the next session jumps to what the logged sets show, capped at +25%, instead of one step at a time. That 145 lb lifter now gets 120 lb × 6 (135 lb if they say male).
- **Variability.** Consistent keeps an exercise for a muscle about 75% of the time, Balanced 50%, Variable 25%.
- **Swaps.** Alternatives share primary muscles and must be doable at the gym, ranked by muscle overlap and movement pattern. A swap marked "not available here" keeps that exercise out of plans at that gym for 14 days.
- **Plates.** Every suggested barbell weight is one the lifter's plates can make. The plate solver is a bounded knapsack (a greedy fill misses some combinations), prefers fewest plates, then heaviest first, and works in the gym's unit so 45 lb plates stay exact (`plates.ts`). Plate colours follow the common competition convention.
- **Units.** Weights are stored in kilograms; a gym's plates, bars and dumbbells are stored in the gym's unit and converted at the edges (`units.ts`).

### Setup wizard (Melvin, 2026-11-09)
- First run opens a short wizard (`src/components/app/Onboarding.tsx`): goal and experience; gym and units; days a week, body weight, and optional age, sex and "I know my numbers" (best recent set of the four main lifts); notifications and a heart rate monitor. Health connections (Health Connect, Apple Health, readiness sources) join it as they land, and should prefill age, body weight and height when the user allows it.
- **It can be run again** from Settings ("Run setup again", `#/setup`). A rerun keeps existing gyms unless the user picks one to add, and never touches workout history.
- One question per screen, big tiles, every step optional except the first three, under a minute in total.

### Workout screen
- Big target weight and reps with steppers, the barbell plate graphic for every barbell set, a big Log set button, an automatic rest timer with +30 s and Skip, and the next set's plates shown during rest so the lifter can load while resting.
- **Live workout notification and lock-screen rest timer.** On Android, a foreground service shows an ongoing notification with a live countdown, the next set and plates, heart rate, and Log set and +30 s buttons; it sounds and vibrates when rest ends. On iOS the same content is a Live Activity on the lock screen and in the Dynamic Island. The web build falls back to a service-worker notification and an alert at rest end (`sessionNotify.ts`).
- The screen stays on during a workout (wake lock), unless the lifter turns it off in Workout preferences.
- **Workout preferences** (Melvin, 2026-11-09; Settings › Workout preferences, `#/training`, `TrainingSettings.tsx`, `src/lib/training.ts`, stored on `profile.training`). Every field is optional and missing means the automatic choice, so older profiles behave exactly as before. Everything is chips and taps (no typing), so it works one-handed in the gym.
  - *Rest between sets:* a default for big lifts and one for smaller lifts, plus a per-exercise time. Order: the exercise's own, then compound/isolation, then by goal (`restFor`).
  - *Rep ranges:* one for compound and one for isolation lifts, plus a per-exercise range (`repRange`). Type ranges apply to loaded exercises only (bodyweight work keeps adding reps); holds stay in seconds. Double progression runs inside the chosen range.
  - *Sets per exercise:* Auto (3, 4 on the first big lifts, a filler set when time allows) or a fixed 2–6, plus a per-exercise count. A chosen count gets no filler sets; deload weeks and easy days still use fewer.
  - *Effort scale:* RIR or RPE (RPE = 10 − RIR, RIR 4+ shows as RPE ≤6). Stored as RIR either way; only the labels change (Today's week chip, the aim under the numbers, the optional set-effort row).
  - *Rest timer:* auto-start on (default) or off. Off leaves a **Start rest** button after Log set; the rest still counts from Log set. Rest-over alert: follow Sounds and Vibration (default), both, sound only, vibration only, or silent; it drives the in-app chime and buzz, the native alert and the web notification. Keep screen on (default on).
  - *Favourites:* a star in the exercise's How to sheet, or picked by muscle in Workout preferences. The generator weights a favourite 6× and prefers it over keeping last time's exercise when both fit; it still needs the gym's equipment, recovery and the day's muscles.
  - *Muscle priorities:* up to three. They aim for a third more weekly sets (`PRIORITY_VOLUME`), rank higher when recovered, and get leftover-time sets first. Recovery rules are unchanged, so a fatigued priority muscle still waits.
  - *Default workout length:* the Today slider goes back to it on the first open of each day (`minutesForToday`, `profile.minutesDay`); "Last used" keeps the old behaviour.
  - *Week starts on:* Monday (default) or Sunday, for streaks, freezes, quests, recaps, weekly stats and the web dashboard's calendars. `derive.ts` holds it as module state set from the profile (`setWeekStart`, `weekOf`, which replaced `mondayOf`). Training blocks keep their own 7-day weeks from `blockStart`.
  - *kg or lb:* Settings › Units is the display unit. Each gym also switches its plates between kg and lb (Gym › "This gym's plates are in"), which swaps the kit for a standard set in the new unit, because plates don't convert. When the gym's unit differs from the display unit, the workout shows the weight in both.
  - Per-exercise rest, reps and sets are also editable from the How to sheet during a workout; they apply from the next plan.
- **Supersets** (table stakes, Melvin, 2026-11-09; `src/lib/superset.ts`). A chain button between two exercises links them, on Today's plan and in the workout's "Coming up" list; tapping it again splits them, and three or more can be chained. Linked exercises share `PlanItem.group` and alternate: one set of each with a 15 s switch (`SWITCH_REST`), then the longest of their rests before the next round; when one runs out of sets the other carries on with its own rest. Warm-ups run the first time each exercise comes up. Plan length counts one rest per round, so linking shortens the estimate. Each set event records its `superset`, so "Same as last time" brings the pairing back. Links made on Today survive a rebuild of the plan (length, call) while both exercises are still neighbours. The generator never pairs exercises by itself yet. Pure web code, so Android, iOS and the web get it together.
- **Saved routines** (table stakes, Melvin, 2026-11-09; `src/lib/routines.ts`, `Routines.tsx`). The lifter's own list of exercises, set counts and supersets, used instead of the adaptive plan for a day. Today's **Routines** chip opens the list: Use today (the chip then shows the routine's name, and "Back to today's adaptive plan" undoes it), edit, delete, **Save today's plan as a routine**, or **Build a new routine** from the exercise library (search by name or muscle; what the gym can do comes first). The summary has **Save as a routine**, which takes what was actually done, swaps and supersets included. Weights and reps still come from progression and warm-ups from `warmup.ts`, so a routine keeps moving forward; exercises the gym can't do are left out for that day. Custom exercises can go in a routine (the lifter chose them, unlike the generator). Routines live on the profile (`profile.routines`, newest first, at most 50 of 20 exercises each), so they're in the backup and will sync with the profile; `sessionStart.routine` records which one a workout came from. Free, like the logger. The length slider doesn't change a routine. When the programs work (`Profile.planSource`) lands, a routine becomes `{ kind: "routine", id }` there. Pure web code, so Android, iOS and the web get it together.
- **Notes, set effort and custom exercises** (table stakes, Melvin, 2026-11-09). Each is its own event (`note`, `effort`, `customExercise`), so it syncs and exports like everything else.
  - *Notes:* written in the exercise's info sheet (500 characters at most). The latest note on an exercise shows under its name every time it comes up, in any workout.
  - *Set effort:* during rest, an optional "Reps left in the tank on that set?" row (0 to 4+) for the set just logged; it never adds a tap during a set and disappears once answered. In `progression.ts` (`effortSignal`), sets that had 2+ more reps left than planned count like "too easy", and sets closer to failure than planned count like "too hard". Explicit post-exercise feedback wins when both exist.
  - *Custom exercises:* "+ Add your own exercise" at the bottom of the swap sheet (name, main muscle, equipment, whether it's a big lift), then it's used straight away. They're registered into the library on load (`registerCustom` in `exercises.ts`), get starting weights, progression, recovery and stats like any other lift, but **the generator never plans them**, because we can't know their movement well enough to programme them.

### Workout data and coaching (Melvin, 2026-11-09: "win on data")
- **Capture everything, automatically, with no extra taps.** Every set stores weight, reps, the planned weight, reps and RIR, when the work started, its duration, the rest actually taken before it, and heart rate during the set (average, peak, and the value at Log set). Every session stores its length, time under load, total rest, average, max and min heart rate, and the call it was built with (push / normal / easy, readiness score, whether the lifter overrode it). The **full heart rate stream** (one sample a second) is saved as an `hrSeries` event at the end, and the in-progress stream is checkpointed to localStorage every 15 samples.
- **Set duration** runs from the end of the rest (timer ran out or Skip) to Log set. When the lifter logs before the rest ends, or the gap is far longer than a set could take, the duration is left out rather than guessed. A watch or HR-based set detector can refine this later.
- **Forgotten workouts end themselves** 3 hours after the last activity (`AUTO_END_MS`), checked on open, every minute, and when the app comes back to the foreground. The end time is set to where the lifter stopped (last activity plus a minute), not when it was noticed, and the session is marked `auto`.
- **The data drives the next workout** (`src/lib/readiness.ts`). A daily readiness score (50 baseline) from big-muscle recovery, days since the last workout and back-to-back days, target reps hit in the last two workouts, how sets felt, rep speed against the lifter's own history for the same exercises, and session heart rate against their usual. Sleep, HRV, resting HR and the pre-workout check-in plug into the same score when connected (integrations roadmap, step 2).
  - 65 or more is a **push day**: the first compound lift goes one rep closer to failure. 35 or less is an **easy day**: one set fewer per exercise (minimum 2), a step lighter, one more rep in reserve, and no extra filler sets. A deload week is never a push day.
  - **Challenges:** on about 30% of push days, at most one a week and never in a deload, the first compound's last set is as many good reps as possible. Challenge sets are flagged, so they don't skew the missed-reps signal.
  - Today shows the call, the score, the top three reasons, and Go easy / As planned / Push buttons. **The lifter can always override**, and overrides are recorded.
  - Weights and reps for the next session keep coming from `progression.ts` (double progression plus feedback), now on richer data.

### Heart rate and health
- **Live heart rate comes over Bluetooth**, not Health Connect, because Health Connect gets Fitbit data in batches, often minutes late. Any standard heart rate broadcaster works (Heart Rate Service 0x180D): Fitbit Charge 6 and Pixel Watch "share heart rate", Polar, Garmin, Wahoo straps (`heartRate.ts`).
- **Health Connect** (Android) and **Apple Health** (iOS) go through one plugin, `@capgo/capacitor-health` (`src/lib/health.ts`). Reads (weight, height, body fat, resting HR, HRV, sleep, HR) prefill the wizard's body weight step ("Fill in from Health Connect / Apple Health"). Finished workouts are written as active calories (about 5 METs) and average HR, because the plugin can't write workout sessions yet. The Android Health Connect privacy rationale is `public/privacypolicy.html`.
- Native heart rate uses `@capacitor-community/bluetooth-le` on both platforms (keeps reading with the screen off; iOS has the `bluetooth-central` background mode). The web build keeps Web Bluetooth.

### Cycle-aware readiness (Melvin, 2026-11-09; built)
- **Opt-in, with its own consent sheet** (Settings › Cycle-aware readiness › Set up). The sheet says what is logged, that it stays on the phone (only the user's own backup/sync moves it), that it is never used for analytics or ads or included in feedback reports, that it isn't medical advice, contraception or a fertility tool, and that turning it off deletes it. `profile.cycle.consentAt` records the agreement.
- The lifter logs the first day of a period with one tap ("Period started today" / "Started yesterday"), stored as `cycle` events. `src/lib/cycle.ts` estimates the cycle day and phase from their own median cycle length (gaps of 21 to 45 days, default 28), and says nothing if nothing was logged in the last two cycles.

### Injury mode (Melvin, 2026-11-09; built)
- The lifter logs an injury by body part (15 parts: neck, shoulder, elbow, wrist or hand, chest, upper back, lower back, abs or core, hip, groin, front of thigh, hamstring, knee, calf, ankle or foot) from Today ("Something hurts?"), Settings, or the swap sheet mid-workout. Screen: `#/injuries` (`src/components/app/Injuries.tsx`); rules: `src/lib/injury.ts`.
- **Matching is deliberately broad** (better to skip one exercise too many): an exercise is affected when the part's muscles are primary (or, for some parts, secondary), its movement pattern loads the joint (knee: squats and lunges; lower back: hinges; shoulder: vertical presses and pulls), or it is listed by id. Each affected exercise can be marked "Doesn't hurt".
- **Default is skip** until the lifter taps "I'm fully healed". Instead they can keep one exercise, or all of them, **lighter at 50, 60, 70, 80 or 90%** of the usual load (default 70). Lighter means the load rounded down to one the gym can make (reps for bodyweight and timed work), at least 3 reps in reserve, no filler sets, never the push-day exercise or a challenge, and it isn't lightened again on an easy day.
- **Every move from skipping to training** (lighter or "doesn't hurt") shows a risk warning that needs "I understand the risks" ticked; the acknowledgment is stored on the event (`ack`). Changing the share while already lighter doesn't warn again.
- **Wording is neutral and never diagnoses.** Every injury screen says Liftsmith isn't a medical app, this isn't medical advice, and a doctor or physiotherapist can say what's safe, and lists the stop signs (sharp pain, pain that builds, swelling, numbness, tingling, a joint giving way).
- **Swaps:** skipped exercises never appear in swap lists, and ones that avoid the injured area are listed first. The injury card shows two that avoid it for each skipped exercise. Logging or changing an injury mid-workout swaps (or drops) the exercises not started yet and re-targets lighter ones.
- **Progression** ignores sessions done lighter (`SetEvent.injuryPct`), so after healing the plan picks up from before the injury. The healed sheet tells the lifter to ease back in and use "Too hard" feedback.
- Stored as `injury`, `injuryRule` and `injuryHealed` events, derived in time order so devices merge cleanly. Injury data is health data: it stays on the device (and the user's own sync) and is never sent to analytics or feedback reports.
- **Programs and routines honour it too** (`injuryPass` in `generator.ts`): on a fixed program day or a saved routine, a skipped lift is swapped for the closest exercise that isn't skipped, keeping the program's sets, reps and lift slot (or dropped if nothing fits), and a lighter lift is scaled set by set with no AMRAP. Split programs plan through the generator, so they get it there. Sets done lighter never move a program lift (`programSessions` ignores them).
- **Free, not Pro**, because it's a safety feature. Pure web layer, so it is identical on Android, iOS and the web (parity).
- **Pain ratings (0–10)** (folded in from the coaching-features thread's "pain-aware training", Melvin picked it 2026-11-09): asked right after logging an injury (skippable), any day on the injury card ("How does it feel today?"), once per exercise per workout during the rest after a set of an exercise trained despite the injury (lighter, marked fine, or in a graded return), and on the summary after a workout. Never during a set. Stored as `pain` events (with the session and exercise when there is one). The card shows a sparkline of the last 14 ratings with a dashed line at 2, the latest score and the change.
- **Graded return** (`gradedReturn`, `returnReady` in `injury.ts`): offered once pain has stayed at 2 or below for about a week (low ratings going back 6+ days, the latest within 4 days). Starting it shows the same risk warning and needs the tick (`injuryReturn` event with `ack`). Skipped exercises then come back lighter: 50%, then 70%, then 90%. Each step lasts at least a week and needs a rating of 2 or less in it to move on; a 3 or 4 restarts the week; 5 or more stops the return and the exercises are skipped again until pain settles and the lifter starts it again. After a week at 90% with low pain the card suggests marking it healed, which stays the lifter's call. Exercises the lifter set to lighter or "doesn't hurt" keep their own choice.

### Reminders and lifecycle messages (Melvin, 2026-11-09; built)
- **What:** workout reminders, a missed-day nudge, streak alerts, comebacks, milestones and Pro offers, by phone notification and by email, to keep people training and help conversion. One pure planner (`src/lib/messages.ts`) decides what goes out and when for both channels; the phone (`src/lib/reminders.ts`) and the server (`src/server/reminders.ts`) only deliver.
- **Kinds** (each has its own switch in **Settings › Reminders**, separately for push and email, `MessageSettings.tsx`):
  - *Workout reminders:* push on each training day at the workout time (Settings › Calendar's days and time; defaults spread the days-a-week goal at 18:00), skipped once there's a workout that day. The first one before any workout reads "Your first workout is ready". By email, one Monday 08:00 note with the week's days and last week's count, not one a day.
  - *Missed workouts:* once per lapse, the morning after the first missed training day (by email, the second), and only if that morning isn't a training day itself (its reminder says it). Then a check-in after 7, 14 and 30 quiet days (counted from setup if there's no workout yet), and nothing more.
  - *Streak alerts:* when the week's goal needs a workout on every day left and there's a streak of at least one week to keep. On a training day it's folded into that day's reminder. Streaks count weeks (game.ts `goalStreak`), so nothing asks anyone to train on a rest day.
  - *Milestones:* email only (the app already celebrates in the moment): the first workout, sent right away when the phone reports it, and streaks of 4, 8, 12, 26 and 52 weeks.
  - *Pro trial and offers:* two days before a trial ends ("or do nothing and stay on the free plan"), then four offers about what Pro adds, 3, 17, 31 and 59 days after the trial ends or is declined, then none. **Off by default on both channels** (Apple 4.5.4 needs explicit opt-in for promotional pushes; GDPR and CASL need it for marketing email). **None go out until billing is live** (`BILLING_LIVE` in messages.ts), because until then everyone has Pro and an offer would be misleading.
  - *Welcome:* the email after confirming, always sent (it's the confirmation of the sign-up).
- **Caps and quiet hours:** at most one message a day per channel; nothing between 21:00 and 08:00 except the reminder at the time the lifter picked (06:00 to 21:00). Email also caps at three a rolling week and one Pro email a fortnight (`CAPS`). Priority on a busy day: reminder, streak, missed, Pro.
- **Push is local, not FCM/APNs.** Every message can be worked out on the phone from its own data, so the phone schedules the next 14 days with `@capacitor/local-notifications` (Android and iOS) when the app opens, comes back to the foreground, a workout ends or a setting changes. It works offline and needs no account, server, Firebase project or APNs key. Android uses its own "Reminders" channel (mutable on its own) and inexact alarms, so the lifter is never sent to the "Alarms & reminders" screen. On iOS, `WorkoutSessionPlugin.swift` owns the notification delegate and passes everything that isn't the workout's own notification to Capacitor's router, so reminder taps open the app on the right screen. Remote push (FCM/APNs) waits for a message the phone can't compute (friends, coach sharing); it will need a Firebase project and an APNs key.
- **The web app has email only** (Platform deltas).
- **Email is double opt-in.** Settings asks for the address and a consent tick (offers stay off), then `POST /api/reminders/` stores the subscription as pending and sends a confirmation email. Only the button on the confirmation page (a POST, so mail scanners that open links can't sign anyone up) confirms it and sends the welcome. Three confirmation emails a day at most per subscription, and the routes rate-limit per address. Changing the address or turning email back on after unsubscribing asks again.
- **What the server keeps** (`reminder_subs` and `reminder_sends`, `src/server/remindersDb.ts`, in the same database as analytics): the address, which kinds are on, when the lifter agreed, and the planner's numbers only: training days and time, time zone, days a week, setup time, last and first workout times, days trained this week, streak weeks and Pro state. **No workouts, weights, heart rate or health data.** The device keeps a random subscription id and secret in localStorage; the server stores only hashes of it and of the confirmation token. `account_id` is nullable so accounts can claim the subscription later and send the same fields from sync.
- **Scheduling:** a Vercel cron (`vercel.json`, once a day at 00:05 UTC, which works on every Vercel plan) runs `GET /api/cron/reminders/` (`CRON_SECRET`), plans each confirmed subscriber's next 26 hours in their own time zone and hands each email to Resend with `scheduled_at` and an idempotency key. When the phone reports a change (say, a workout that makes a missed-day nudge wrong), the server cancels the scheduled emails that no longer apply and schedules any new ones. If the phone is offline after a workout, a scheduled nudge can still go out; that's accepted.
- **Every email** carries a one-click unsubscribe link (an HMAC of the subscription id, so the token is never stored) and the `List-Unsubscribe` and `List-Unsubscribe-Post` headers (RFC 8058, required by Gmail and Yahoo for bulk senders), says why it was sent and where to change it, and includes the postal address (CAN-SPAM, CASL). The routes refuse to send without `MAIL_POSTAL_ADDRESS`. Unsubscribing stops everything and cancels what's scheduled; the app's syncs can't quietly resubscribe. **Stop all email and delete my address** in Settings, and **Erase this device**, delete the row and its history from the server.
- **Server environment:** `RESEND_API_KEY`, `MAIL_FROM` (a sender on a domain verified in Resend, e.g. `Liftsmith <coach@getliftsmith.com>`), `MAIL_POSTAL_ADDRESS`, `REMINDER_SECRET` (a long random string for unsubscribe links), `CRON_SECRET`, and the database. Without them `/api/reminders/` answers 503 and the app says it couldn't reach the server.
- **Later:** switch the streak alert to the gamification thread's `goalStreak` `atRisk` flag and freezes once that lands; a weekly-quest "almost done" nudge; win-back and receipts by email once accounts and billing exist.

### Coaching features (Melvin picked them, 2026-11-09; built)
From a ranked list of features Fitbod, Hevy, Strong and StrongLifts don't have. All run in the shared web layer, so Android, iOS and the web app get them in the same change; only remix links differ (see Platform deltas).
- **Why this weight** (free, `src/lib/explain.ts`, `WorkoutExtras.tsx`). Tapping "Why?" under the target opens the reasons in plain words: last session's sets, the double-progression rule that applied, feedback, the block week's RIR, today's push or easy call, and how the plates round it. It reads the same data as `progression.ts` and never changes the plan. Fitbod's most common complaint is that it's a black box.
- **Change the plan mid-workout** (Pro, `can("replan")`, `src/lib/replan.ts`). The ⏱ button: "N min left" trims sets from the least important exercises first (core and isolation, then later ones; never below 2, never under what's done on the current one), then drops whole exercises from the end; the current exercise is never removed. "Bench or rack taken?" moves the exercise after the next one (only before its first set) or swaps it for one that needs other equipment, through the normal swap (so swap events and injury rules still apply). Bars, bands and small gear don't count as "taken".
- **Plateau detective** (Pro, `can("plateauDetective")`, `src/lib/plateau.ts`, Progress screen). A weighted lift is stalled when its estimated one-rep max hasn't come within 1% of its best for 3 weeks, with 5+ sessions overall and 2+ recently, outside a deload. Causes come from the lifter's own data, strongest first: missed reps (30%+ of sets), "too hard" feedback, weekly sets for the muscle under 70% of the block target, rest under 75% of plan, readiness averaging under 42, or the same rep range for 4+ sessions. Each maps to a three-week fix: reset (about 10% lighter once, then rebuild), a different rep range, one extra set, a minute more rest, or a close variation. Fixes live on `profile.plateauFixes` and are applied to the plan after `generate()` (`applyFixes`, called from `store.replan`), so the generator stays one thing. After a fix ends, Progress says whether it worked. A lift isn't re-diagnosed while a fix runs or for a week after.
- **Goal-date planner** (Pro, `can("goalPlanner")`, `src/lib/goals.ts`). Melvin: "it should be realistic". Goals are one-rep maxes by a date (`profile.goals`). The forecast blends typical monthly gains by experience (new 4%, intermediate 1.5%, advanced 0.6%; slowing each month, nothing added in deload weeks) half and half with the lifter's own 12-week trend, which is capped at twice the typical rate so one good month can't promise too much. It shows a range (half to one and a half times the rate) and says "very likely", "on track", "a stretch" or "not realistic", and when it isn't, the likely date and what's realistic by the date. In the last two weeks it gives taper advice and three loadable attempts (90% and 96% of the expected max, then the goal only if the forecast supports it).
- **Workout remix links** (free, `src/lib/remix.ts`, `Remix.tsx`, route `#/remix/<code>`). "Share this workout" on the Done screen makes a link holding only exercise ids, sets, reps and rest (format `1~id.sets.reps.rest~…`, at most 20 items; no weights or anything personal). Opening it rebuilds the workout for the opener's gym (swaps to the closest available exercise, or leaves it out) at their own weights: their history's estimated max at the shared reps. Unknown exercises and bad numbers are dropped.
- **What to buy next** (free, `src/lib/buying.ts`, `BuyNext.tsx`, Gyms screen, home gyms only: under 15 equipment items). Plate pairs ranked by running out of plates first, then a smaller jump (aiming for a 2.5 kg or 5 lb total jump), then more loadable weights up to 25% past the heaviest recent barbell set; and equipment that unlocks the most exercises and first loaded work for a muscle (big machines left out). "I got them" / "I have it" adds it to the gym. Advice only: no shop links or sponsored picks (no ads, ever).
- **Machine settings memory** (free, `src/lib/machineSettings.ts`). "Save setup" under the exercise name: up to 4 labelled values per exercise per gym (seat, pads, foot position, pulley height, J-hooks, bench angle…), offered from the equipment the exercise needs, stored on `gym.settings` (last-write-wins with the gym) and shown as "Seat 4 · Back pad 2" before the first set.
- **Pain-aware training** was picked too; the injury mode thread owns it (pain rating, trend and graded return on top of injury mode).

### Programs (Melvin, 2026-11-09; built)
- Settings › Program (`#/programs`) picks how Today is planned: **Adaptive** (the default), a **fixed program**, or a **split**. The engine is `src/lib/programs.ts`; the choice is `Profile.planSource` (`adaptive` / `program`; a `routine` kind is reserved for a routine followed as the standing plan). A saved routine picked for today (`routines.ts`) replaces that day's plan, adaptive or program, and doesn't count as a program day, so the program's next day stays next.
- **Fixed programs follow their own published rules**, not readiness or RIR blocks: no length slider and no push/easy call on Today. Classic 5×5 (A/B, +2.5 kg a session, +5 kg deadlift, −10% after three misses in a row), Novice 3×5 (squat every session, +5 kg squat and deadlift, power cleans 5×3 replace the B-day deadlift after six sessions), 5×5 plus arms (5×5 plus 3×8 accessories), Ramping 5×5 (heavy / light / top-set days ramping 12.5% a set, a triple 2.5% over the top set that becomes next week's top, miss and repeat the week), Tiered progression (T1 5×3+ → 6×2+ → 10×1+ → restart at 85%; T2 3×10 → 3×8 → 3×6 → 3×10 at the last 3×10 weight + 7.5 kg / 15 lb; T3 3×15+, add weight at 25), Training max waves (TM 90% of e1RM, 65/75/85, 70/80/90, 75/85/95 and a deload, 5×10 at 50% plus one assistance lift, TM +2.5/+5 kg a cycle or −10% after a short last set) and Bodyweight skills (ladders for pull-up, squat, dip, hinge, row, push-up and core; 3×5–8, step up after 3×8; holds 20–60 s).
- **Splits** (push/pull/legs, upper/lower) pass each day's muscles to the adaptive generator (`GenerateInput.muscles`): only exercises whose main muscles are all in the day, muscles at 40%+ recovery, and they keep RIR blocks, deloads, readiness and the length slider.
- **Progress is derived, never stored.** The starting weights are frozen when a program is picked (`planSource.start`, from the lifter's own logged sets, else `startE1rm`), and the current weights come from replaying the program's sessions (`sessionStart.program`). Each set records the program lift it counts for (`SetEvent.slot`), so swaps and stand-in exercises keep the lift's progress, and `amrap` marks "as many as you can" sets. When the lifter lifted what was planned, the next weight builds on the exact planned weight, so small jumps the plates can't make yet still add up; when they changed it, on what they lifted.
- Per-set targets (`PlanItem.setTargets`) drive ramps and percentages: the workout screen loads each set's weight and shows a banner on AMRAP sets. Programs run through `withWarmups`; ramped lifts keep only the empty-bar warm-up, since their first sets are the warm-up.
- A lift the gym can't do is swapped for the closest exercise it can, at a weight scaled by the two exercises' usual loads, with a note on Today. Ladder steps the gym can't do are skipped. Ladder-only steps (`LADDER_ONLY` in `exercises.ts`) stay out of adaptive plans.
- **Names (trademark check, 2026-11-09):** STARTING STRENGTH, JIM WENDLER 5/3/1 and STRONGLIFTS are registered US trademarks; no registrations found for Madcow, Ice Cream Fitness or GZCLP. Every program has a plain descriptive name, credits the original in its info text ("Based on Starting Strength by Mark Rippetoe"), and the picker says the names belong to their owners. Never use a trademarked name as a program's name (a test checks this).
- The picker shows each program's steps, credit, level, days a week, tier, a typical week of hard sets per muscle, and any kit the active gym lacks.
- Web-layer only: no native code, so both apps get it from the same build.

Until a listing exists the badge is dimmed with "Soon" and a link to the web app sits beside it. The badges are drawn in the stores' standard black style; swap in the official artwork from Apple's and Google's badge pages before launch.
  - **Pricing** reads `PRICES` (`trial.ts`) and the trial length from the `trialDays` flag, so the page can't drift from the app.
  - **Dark only.** The home page stays on the dark tokens whatever the app's Appearance setting, because the hologram only reads on a dark ground (like the share image). Its few fixed hologram colours (ember labels, heart red) match the demo engine's.
- **Comparison pages** (`/compare/fitbod/`, `/compare/hevy/`, `/compare/strong/`, `/compare/gymverse/`, `/alternatives/fitbod/`): every competitor fact lives in one data file with its source URL and the date checked, and the build fails when any row is more than 90 days old. Competitors are named in text only (no logos or screenshots), with a trademark line. Claims are factual and dated, never disparaging.

## Architecture decisions

- **Stack copied from Gradelings** (`mjparinas/gradelings`): Next.js 16 static export, React 19, TypeScript, Tailwind 4, Zustand, Vitest.
- **Capacitor, not Bubblewrap (Melvin chose it, 2026-11-09).** A TWA can't run a foreground service, show a live lock-screen countdown, read Health Connect, keep Bluetooth heart rate going with the screen off, or use StoreKit (it has no iOS app). Capacitor wraps the same static export and adds those through native plugins; it also builds the iOS app. The cost is a store release for each app change.
- **Offline-first, like Gradelings.** Everything the lifter does is an event with a unique id (set, session start and end, feedback, swap), appended to IndexedDB first (`localdb.ts`). Stats, PRs, recovery, streaks, XP and progression are recomputed from events, never stored (`derive.ts`), so merging devices is order-independent and duplicate-safe. Profile and gyms are last-write-wins on `updatedAt`.
- **Two builds** (`next.config.ts`): `npm run build` is the Vercel server build with API routes named `route.api.ts`; `npm run build:static` (`STATIC_EXPORT=1`) is the static export for the native shells and CI, and it leaves those routes out. Native apps call the API on `SITE_URL`.
- **Sync (later):** push unsynced events and pull new ones by cursor (`POST /api/sync/`), when online, when the app becomes visible, and shortly after a change. Server on Vercel with libsql or Turso, as in Gradelings.
- **One static page for the app** with hash routes (`#/today`, `#/workout`, …), so it works offline from one cached page.
- **The active workout** is also kept in `localStorage`, so killing the app mid-set loses nothing.
- **Seeded randomness only** in the generator (`random.ts`), never `Math.random`, so plans are reproducible and testable.
- **Native code** lives in the Android project as small Capacitor plugins (WorkoutSession foreground service; Health Connect), called from `src/lib/sessionNotify.ts` and friends, which fall back to web APIs when not native.

## Testing (Melvin asked, 2026-11-09: like Gradelings)

- **Unit tests** (`src/lib/*.test.ts`, node) for every engine rule: plates, recovery, blocks, progression, generator, stats, game.
- **Component and integration tests** (`*.test.tsx`, `// @vitest-environment jsdom`, Testing Library, fake-indexeddb): the whole app from first run to a saved workout through the real store and IndexedDB, steppers, swaps, a bodyweight gym, and a workout surviving a reload.
- **Browser tests** (Playwright, `scripts/e2e*.mjs`): playthrough, offline, a device layout sweep (no sideways scroll, Log set fully on screen and 48 px+, controls 44 px+), and axe WCAG 2.2 AA with no serious or critical problems. Any console error fails a run.
- **Device coverage** (Melvin asked, 2026-11-09: "comprehensive but not too many"). One list in `scripts/devices.mjs`, 13 devices, each adding a screen size the others don't: iPhone SE (3rd gen), iPhone 16, iPhone 17 Pro Max, iPad Mini, iPad Pro 11 landscape; Galaxy S9+ (320 wide, the narrowest), Galaxy S24 (360, the most common Android width), Pixel 7, Galaxy A55, Pixel 7 landscape, Galaxy Z Fold 7 opened, Galaxy Tab S9 portrait and landscape. iOS devices run in **WebKit** (the iOS app is a WKWebView) and Android ones in Chromium. Every device gets the layout sweep plus a logged and saved set (about 2 s each); the full playthrough runs on Pixel 7 and again on iPhone 16 in WebKit. Offline and accessibility runs stay on Pixel 7. Add a device only when it brings a new size or engine, and drop one when another covers it. Cloud sessions have only Chromium, so WebKit devices skip locally and run in CI, where a missing engine fails the run.
- **Mutation tests** (Stryker, `stryker.config.mjs`, Gradelings' Vitest 5 runner in `scripts/stryker-vitest5.mjs`) on the engine, run by hand (not in CI); the run fails below the `break` score. It is a ratchet: the first run scored 34%, so `break` is 30 for now; raise it (target 60, Gradelings aims for 85) as engine tests land.
- A bug fix comes with a test that fails without it. Flaky tests are fixed at the cause, never retried.
- Colour tokens must pass contrast: `--color-faint` was raised to `#808c9d` because axe failed `#5b6777`.

## CI/CD (Melvin asked, 2026-11-09: like Gradelings)

- `.github/workflows/ci.yml` on every pull request and push to `main` and `staging`: types, lint (no warnings), dependency audit, unit and integration tests with coverage, build, then browser tests in three parallel jobs. **"CI passed"** is the one required check.
- `mutation.yml`: **on demand only** (Actions › Mutation tests › Run workflow). Mutation runs are long and expensive, so they never run on pull requests or merges and never gate a merge (Melvin, 2026-11-09). Run one after a batch of engine work and raise `break` when the score rises.
- `promote-staging.yml` (Melvin confirmed the Gradelings model, 2026-11-09): `main` is production and every pull request targets `staging`. At 09:00 UTC each night it opens a staging → main pull request and merges it when "CI passed" is green on staging's latest commit, then merges `main` back into `staging`. Run it by hand from the Actions tab to ship sooner. Scheduled workflows only run from the default branch, so the file must be on `main` before the nightly run starts. It needs "Allow GitHub Actions to create and approve pull requests" on, and `PROMOTE_TOKEN` if `main` requires reviews.
- `ci.yml` also builds an Android debug APK (uploaded as an artifact to install and try) and an unsigned iOS simulator build. Both are part of "CI passed".
- **CI speed (Melvin asked, 2026-11-09).** A `changes` job skips both native builds on a pull request that touches none of `android/`, `ios/`, `capacitor.config.*`, `package.json`, `package-lock.json`, `ci.yml` or `.github/actions/`, since the native compile can't change otherwise; pushes to `staging` and `main` always build both, so a break still shows before the nightly promotion. "CI passed" counts a skipped job as passed. The device sweep runs as two jobs (`DEVICES=ios` and `DEVICES=android`) and the iPhone playthrough moved into the playthrough job. Gradle uses its build cache (cached across runs) and `--parallel`. The iOS simulator build compiles arm64 only, with no index store, and uses a placeholder `out/` so it starts without waiting for the web build. Add a path to the `changes` filter whenever something new can affect native builds.
- `release.yml`: on every promotion to `main` and on demand, builds a signed Android App Bundle and uploads it to the Play **internal** track, and archives iOS and uploads it to **TestFlight**. Version name comes from `package.json`, build number from the run number. Each platform skips itself with a notice until its secrets exist. Promoting past internal testing stays a human step in the store consoles.
- Secrets: `ANDROID_KEYSTORE_B64` (base64 upload keystore, alias `upload`), `ANDROID_KEYSTORE_PASSWORD`, `PLAY_SERVICE_ACCOUNT_JSON`, `APPLE_TEAM_ID`, `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8` (App Store Connect API key, App Manager role). The first Android upload must be done by hand in Play Console before the API can upload.
- **Web hosting is Vercel** (Melvin, 2026-11-09). The Vercel project `liftsmith` (team `melvins-projects-b69f55c3`) is linked to this repo through Vercel's Git integration and runs `npm run build` (the server build, so API routes deploy as functions). Pushes to `main` deploy to **production** (`liftsmith-three.vercel.app` until a domain is registered). Pushes to `staging` deploy a **preview** that is always reachable at `liftsmith-git-staging-melvins-projects-b69f55c3.vercel.app`, and each pull request gets its own preview, linked from the "Vercel Preview Comments" check. One deployment serves the whole web surface: the public site, the web app (`/app/`), the web dashboard and `/admin/`, plus `/api/*`. `vercel.json` only adds the daily reminder-email cron; everything else uses the defaults.
- **Environment variables live in Vercel** (Project › Settings › Environment Variables), never in the repo. Set them for both Production and Preview: `RESEND_API_KEY`, `FEEDBACK_TO`, `FEEDBACK_FROM` (feedback), `MAIL_FROM`, `MAIL_POSTAL_ADDRESS`, `REMINDER_SECRET`, `CRON_SECRET` (reminder emails), `NEXT_PUBLIC_SITE_URL` once the domain exists, and the database and admin variables as those features land. None are set yet (2026-11-09).
- **Deployment protection:** Vercel Authentication is on for every vercel.app URL (`all_except_custom_domains`), so only team members can open production until a custom domain is attached. Custom domains are public. Previews stay behind the Vercel login.
- Dependabot targets `staging`, weekly.

## Borrowed from Gradelings (Melvin asked, 2026-11-09)

Patterns from `mjparinas/gradelings` adopted for Liftsmith. Copy the Gradelings code where it fits rather than rewriting it.

- **Branches and merging:** pull requests go to `staging`; a nightly workflow promotes `staging` to `main` when CI is green (one production build a day). **Agents watch CI on every pull request they open and merge it into `staging` as soon as every check, including "CI passed", is green; when a check fails they find the cause, push a fix and repeat until it merges** (Melvin, 2026-11-09). Agents never merge into `main`; only the nightly promotion does. Flaky tests are fixed at the cause, never retried.
- **Feature flags** defined in code (`src/lib/flags.ts`, built: `flag()`, `cacheFlags()`, a stable per-device `variant()`), state on the server (later), cached on the device for offline use, so a feature can be switched off without a store release. A/B tests read through the same path.
- **Admin panel** (`/admin/`, website only, admin emails from the environment, every change audited): built, see "Analytics and the admin panel". Still to come from Gradelings: maintenance mode, alerts, a users list once accounts exist. Test installs are left out of every metric.
- **Error reporting:** Sentry with a scrubber (no workout notes, names or health data leave the device), loaded only when something goes wrong.
- **Analytics:** first-party and cookieless on the public pages (page views and call-to-action clicks to our own database, replacing Vercel Web Analytics so visits can be joined to installs and funnels). In the app, the usage events in `src/lib/analyticsSchema.ts`, with consent rules, disclosed on `/privacy/` and in the store labels. Health data never leaves the device except through sync to the user's own account.
- **Security:** hashed Content Security Policy with no `'unsafe-inline'`, security headers, size-limited request bodies, hashed session tokens, `security.txt`.
- **More engagement, Gradelings-style:** streak freezes computed in `derive`, never stored; mystery crates picked from the session id so every device agrees; a weekly "you got stronger" recap; an "almost there" card ("1 more rep for a bench PR"); shareable milestone cards; seasonal events; a few Easter eggs. Nothing blocks a tap or pushes late-night use.
- **What's new** screen after an update, and **promo, referral and friends-and-family codes** (store promo codes on native).
- **Accessibility:** built, see "Accessibility" under Product decisions.
- **Browser tests like Gradelings':** a full playthrough, an offline run, a layout sweep across phones and tablets, and a tap-latency benchmark ("every tap answers within a frame or two").
- **Store tooling:** scripts that make Play and App Store screenshots and the feature graphic from the real app, plus `docs/PLAY_LISTING.md` and `docs/PLAY_CONSOLE_ANSWERS.md`.
- **Email** through Resend (in-app feedback and reminder emails today, see "Reminders and lifecycle messages"; receipts later), with unsubscribe tokens that are never stored and the CASL mailing address.
- **Exercise demos (Melvin approved, 2026-11-09):** a procedural 3D hologram wireframe built with three.js, not filmed videos. Male and female bodies are driven by the same motion, and there are toggles for the skeleton, the target muscles and the bar path. Being procedural, the demos ship inside the app and work offline. Prototype: https://claude.ai/artifact/WrmuLVALnkzLjBPoLcxN8i (source in the project files: `exercise-demos/wireframe-lift-demos.html`).
  - **Every exercise has one** (a test fails if a library exercise has no motion). It shows on the workout screen for the current exercise (tap it or "How to ›" for the how-to sheet with the full controls and the muscles worked).
  - **3D everywhere; 2D only when the device has no WebGL** (Melvin, 2026-11-09). The 2D version draws the same mesh with the 2D canvas; there is no low-power or user switch to 2D.
  - **Live heartbeat** (Melvin, 2026-11-09): when a heart rate monitor is connected, a heart on the figure's chest beats at the lifter's live BPM and the BPM shows on the stage. No monitor, no heart. Same on Android, iOS and web, because the BPM comes from the shared Bluetooth heart rate path (`heartRate.ts`).
  - Code: `src/lib/demo/` (rig, body tables, motions, mesh; pure and tested in node) and `src/components/demo/` (`LiftDemo` component, shared loop, WebGL and 2D scenes). three.js is imported only by `scene3d.ts`, loaded on first use, so it stays out of the main bundle (about 136 KB gzipped, cached for offline by the service worker). The inline demo caps at 30 fps and stops drawing when off screen, hidden or covered by a sheet; reduced motion shows a still pose.
  - `LiftDemo` props other screens use: `exerciseId`, `reps` (play that many reps, then stop), `label`, `body`, `view`, `still`, `controls`, `highlight` (muscle weights, for a standing figure), `bpm`. The body choice is remembered per device.
- **Data rights:** JSON export, erase device and delete account; a restore check for backups; a full-storage notice. **Built (2026-11-09):** Settings › Data › Export sets (CSV: every working set, in the lifter's unit, dumbbells marked per hand) and Full backup (JSON: profile, gyms and every event), from `exportData.ts`. On the phone the file goes to the share sheet (`@capacitor/filesystem` plus `@capacitor/share`, Android and iOS), and in the browser it downloads.
- **CSV import** (table stakes, Melvin, 2026-11-09; `src/lib/importCsv.ts`, `ImportCsv.tsx`): Settings › Data › **Import workouts (CSV)** reads exports from **Strong** (comma or semicolon; the unit from a "Weight (kg)" header, otherwise the lifter picks kg or lb), **Hevy** (`weight_kg` or `weight_lbs`, warm-ups, supersets) and Liftsmith's own "Export sets" file. Cardio rows (a distance), Strong's rest-timer rows and empty sets are left out. Names are matched to the library by weighted word overlap, where equipment words fold into our load kinds and words like incline, front or Romanian must match. A sheet lists every name with its match for the lifter to check, and anything unmatched becomes their own custom exercise, with a guessed muscle and load. Workouts are written like hand-logged past workouts (`sessionStart.source: "manual"`, RIR 2 assumed, what was lifted taken as the target), under the active gym. Every id comes from the file, so importing the same file again adds nothing, and workouts dated in the future are skipped. The file is read on the device and never uploaded. Pure web code, so Android, iOS and the web get it together.
- **Body weight log** (table stakes, 2026-11-09): Progress › Body weight logs a weigh-in as a `bodyweight` event (it also becomes the profile's body weight), with a trend line and the change over 4 weeks. It's in the backup. Health Connect / Apple Health weigh-ins can feed the same event later.
- **Languages** (Melvin, 2026-11-09: "i18n and l10n, use as much native as possible"; `src/lib/i18n.ts`, `src/locales/`): English, Spanish and French.
  - *Which language:* the phone's. On Android and iOS it's read with `@capacitor/device` (`getLanguageTag`), so the system per-app language works: Android 13+ lists Liftsmith under Settings › Apps › Language (`res/xml/locales_config.xml`, `android:localeConfig`), and iOS lists it under Settings › Liftsmith › Language (`CFBundleLocalizations`). In a browser it's `navigator.languages`. **Settings › Language** (Match my phone, English, Español, Français; `profile.language`) overrides it. `<html lang>` follows.
  - *Formatting is the platform's Intl:* numbers (`num`, and `fmtNum` for weights: 82,5 in French and Spanish), dates and times (`date`), relative times (`relative`), lists (`list`) and plurals (`Intl.PluralRules`), all with the phone's full tag (es-MX, en-GB), so regional formats are right even when the text is the base language. **Input boxes and files keep a point** (`plainNum`), and typed commas are read as decimals (`parseNum`, `BumpField`).
  - *Text:* `t(key, vars)` from one catalogue per language (`src/locales/en.ts` is the source; `es.ts`, `fr.ts`), `{name}` placeholders, plural forms keyed by `Intl.PluralRules` categories. A missing key falls back to English; `i18n.test.ts` fails if a catalogue lacks a key or a placeholder. The translations are a first pass and need a native speaker's review before launch.
  - *Native text:* Android notification channels, the live workout notification's text and buttons, launcher shortcuts and the widget come from `strings.xml` with `values-es` and `values-fr`. iOS permission prompts come from `es.lproj` and `fr.lproj` `InfoPlist.strings`. The notification follows the phone's language (on Android 12 and below, the in-app choice doesn't reach it).
  - *Done so far:* the app shell, Today's greeting and start, the whole workout screen (including the coaching sheets: change the plan, machine settings, the "Why?" sheet's frame), and Settings › Language. The "Why?" reasons themselves (`explain.ts`) are still English. **Still English:** the other screens, the glossary, exercise names and cues, quotes, achievements, reminders and emails, the website, and the iOS widget, Live Activity and Siri phrases. Each new screen moves its text into the catalogues as it's translated; new UI text goes into `en.ts` from the start.
