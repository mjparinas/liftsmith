# Friends and the workout feed

Part of the decision record. [AGENTS.md](../../AGENTS.md) has the rules that apply to every change and the list of topics. Record decisions about this topic here, in the same change as the code.

Melvin, 2026-11-11, from the missing-features list: "Friends and a feed: follow people, see their workouts, like and comment", with moderation, blocking and reporting and private defaults. Built in stages; stage 1 is below, stage 2 is in [Open items](open-items.md).

## Where it lives

- **Friends is a tab in the bottom bar** (Melvin, 2026-11-12: "it really should be a first class citizen at the bottom, but there could be too many buttons if you add it. can you demote one of them"). It replaced the people button on Today's header (Melvin's first pick, 2026-11-11, over a sixth tab). The bar stays at five: Today, Body, Progress, Friends, Awards. **Gyms left the bar** because it's set up once and rarely opened after that: switching gyms already happens from Today's gym chip (or by location), so the full Gyms screen moved to **Settings › Gyms and equipment** (the second row, under Account), keeps the gym chip and the plate calculator's link, and gets a "‹ Back" link. Awards stayed because it's visited after most workouts and is part of the reward loop. The Friends tab carries the dot (and "Friends, N new" for screen readers) while there's unread activity or a follow request waiting. With the `social` flag off the tab is hidden and the bar has four tabs. It opens **Friends** (`#/friends`): Feed, Activity and People as chips at the top, and a gear for Friends settings. A person's page is `#/person/<handle>`. One control each: the post's heart likes, its speech bubble opens the comments sheet, its "…" holds Report (or Delete on your own post), and the person page's "…" holds Block and Report.
- **Done** gets **Post to friends** under the stats once the lifter has joined (or posts by itself with "Post every workout" on), then shows **Posted to friends · Remove**. It asks the server whether this workout is already posted, so a reload or a second device doesn't post twice; the server also keeps one post per workout.
- Hidden everywhere when the `social` flag is off (admin Flags tab), and the server then answers 503, so it's a kill switch.

## Privacy by default

- **Signing in is required**, then **joining is opt-in**: a handle (3 to 20 of a–z, 0–9, _; unique; names that look official are reserved), a display name, and agreeing to four community rules. Both app stores require terms users agree to, a filter, reporting and blocking for apps with user posts (Apple 1.2, Google's UGC policy); the agreement time is stored (`agreed_at`).
- **Follow requests need approval** unless the lifter turns on "Anyone can follow me"; turning it on lets everyone waiting in. **Nothing is posted** until the lifter taps Post (or turns on "Post every workout", off by default). **Show weights** is on by default, like share cards; off, posts show sets and reps only.
- **Posts are for accepted followers only** unless the lifter makes their profile public (below). A post carries the workout summary only (`PostBody` in `src/lib/socialTypes.ts`): time, sets, volume, new-best count, muscles worked, and per exercise its id, sets and best set. The server keeps only those fields (`parsePost`), so heart rate, body weight or fat, measurements, cycle data, injuries, gyms and places can't get in. Exercises travel as ids, so each reader sees the names in their own language and weights in their own unit; a custom exercise's name goes along (through the word filter).
- **Finding people is by exact handle** or a shared profile link (People › Share my profile). There's no directory, search or suggestions, so the list of users can't be browsed or scraped, and lookups are rate-limited.

## Public profiles (stage 2)

Melvin, 2026-11-11: "make public accounts available on the web through a link and it should be added to the sitemap … only public users should be in the sitemap".

- **Public profile** is a switch in Friends settings, **off by default** and not offered while joining, so every profile starts private. Its hint says plainly that anyone can see the profile and workouts, on the web too, and that search engines can list the page. Public also means anyone can follow (turning it on turns on "Anyone can follow me" and lets everyone waiting in); turning "Anyone can follow me" off turns Public off too.
- **In the app**, anyone who isn't blocked sees a public profile's posts on its person page, and can like and comment (the same `canSee` check, so blocking still hides everything both ways). A public profile's posts still reach someone's Feed only once they follow it. The person page's kicker says "Public profile".
- **On the web**, `www.getliftsmith.com/u/<handle>/` (a rewrite to `src/app/api/people/page/`, server build only; data in `src/server/publicProfile.ts`, page in `src/server/profilePage.ts`). Plain HTML with no scripts and the share page's strict CSP (`SHARE_PAGE_CSP`), every typed value escaped, a canonical link, Open Graph tags and `ProfilePage` JSON-LD (a data block, never run). The page's language follows the reader's `Accept-Language` (six languages, `pub.*` in `src/locales/text/pub.ts`, read directly by the server), and weights are in pounds for `en-US` readers, kilograms otherwise. Custom exercise names show as the poster wrote them.
- **Desktop redesign** (Melvin, 2026-11-12: "we really should have a desktop version that has the same or similar headers as the home page, with the header and footer and more emphasis at trying liftsmith for users not already logged in"):
  - *The site's own header and footer.* Same links and text as every public page (`navFor` now lives in `src/components/site/nav.ts`, a plain module, so the server page reads the same list; the footer columns come from `siteText().chrome`). They're redrawn in HTML because the page can't load the site's React or stylesheet under its CSP; the phone menu is a `<details>`, so it needs no script. A test checks every header link is on the page.
  - *What it shows,* matching the app's person page for someone who can see the posts: the avatar (the same icons on a tinted disc, or the kettlebell), workout, follower and following counts, level and training-week streak, the best lifts (only while the lifter shows them and shows weights, the app's rule), the 12-week training calendar with the days they usually train (in UTC, because the page has no reader's time zone), and the last 12 workouts for everyone with up to eight exercises each, a "New best" tag on new bests and a "Follow in the app" button. Only posts for everyone count anywhere on the page.
  - *Layout:* from 960 px the profile column (sticky) sits left of the workouts; on phones it stacks.
  - *Trying Liftsmith:* a line under the header, a "Train with a plan, like {name}" card (in the profile column on wide screens, after the workouts on phones), the site's big "Get the app" banner with the store badges and a link to the free tools, and a bar along the bottom on phones. Without a script the page can't tell a signed-in reader, so everyone sees them.
  - *Links:* plain followed links to our own pages (exercise pages for each lift and workout exercise, `/tools/`, the home page) with no UTM tags, because each tagged address splits crawl and Traffic counts; only store links carry a `referrer` with `utm_source=profile`. Profiles that aren't public still get the same noindex "isn't public" page, now in the site frame.
- **Anything else gets one "This profile isn't public" page** with `noindex` and a 404: a private profile, a suspended one, a hidden handle or no such handle, so the page never reveals whether a private handle exists. Hidden (reported) posts are left out. The page is cached for 5 minutes at most, so turning Public off takes it down soon.
- **The people sitemap** `/sitemap-people.xml` (rewrite to `src/app/api/people/sitemap/`) lists only public, unsuspended profiles **with at least one workout posted** (an empty page is thin content), newest activity first, up to 45,000; `robots.txt` names it next to `sitemap.xml`. The static `sitemap.xml` stays the site's own pages.
- **Sharing:** People › Share my profile shares the web page when the profile is public, the in-app link otherwise; Friends settings has "See my public page" while it's public.
- Tests: `src/server/publicProfile.test.ts` (private shows nothing, the page and its escaping, the sitemap's rules, suspension, language and units) and the public cases in `social.test.ts`.

## Sending a workout to a friend (stage 2)

The original ask: "sending a workout directly to gym buddies".

- **Send to a friend** sits on Done (this workout) and in a saved routine's editor, next to Share routine. Both appear only once the lifter has joined Friends.
- It opens a sheet of the lifter's **friends: people they follow who follow them back** (`people` with `list: "friends"`). Tap a name to send. Mutual follows only, so nobody can push workouts at strangers. Blocking either way stops it, and there's a limit of 50 sends a day.
- **What travels is a routine code**, the same one routine links use (`encodeRoutine`). It holds the exercises, their set counts and supersets, and nothing else: no weights, notes or anything personal. From Done, the name is "Workout on <date>".
- **The server checks the code's shape** (`CODE_RE`). It reads the name out of the code itself and puts it through the word filter and the link check, so the name the friend sees on opening is the one that was checked. It's stored in `sent_workouts`.
- **The friend sees it in Activity** as "<name> sent you a workout: <workout>". It counts toward the unread dot. Tapping it opens `#/routine/<code>`, the shared-routine preview with Save.
- Leaving Friends or deleting the account deletes sends both ways.
- Analytics: `feature` `social_send`.
- Tests: the sending cases in `social.test.ts`, and the send-then-Activity flow in `Friends.test.tsx`.

## Push notifications (stage 2)

- **What:** a push when someone follows you or asks to follow, accepts your request, comments on your workout, sends you a workout, and (off by default) likes one. Friends settings › Notifications has a switch for each (follows and requests, comments, workouts sent to you, likes), stored on the profile (`push_*` columns). The Activity list and the people button's dot still carry everything.
- **Asking:** the permission prompt shows only when the lifter acts. That means joining Friends, or turning a notification switch on. After that, opening the app keeps the token current without asking (`startPush` in `src/lib/push.ts`). If the phone has notifications off, the switches say so.
- **Server:** `src/server/push.ts`.
  - The phone registers its token with `pushToken` (`push_tokens`: the token, account, platform and the phone's language; at most 10 per account, newest kept).
  - `notify` runs after follow, answer, like, comment and send, in the recipient's language (`push.*`, `src/locales/text/push.ts`).
  - Android goes through **Firebase Cloud Messaging HTTP v1** (a service account JWT for an OAuth token, cached for its hour). iOS goes through **APNs** (an ES256 token JWT over HTTP/2).
  - A dead token (FCM `UNREGISTERED`, APNs 410 or `BadDeviceToken`) is deleted. Sending never fails or holds up the action: errors are swallowed, and it gives up after 4 s.
  - **Off until the keys exist** (`pushConfigured`): `FCM_SERVICE_ACCOUNT_JSON` for Android, and `APNS_KEY_P8`, `APNS_KEY_ID` and `APNS_TEAM_ID` for iOS (`APNS_TOPIC` defaults to `com.getliftsmith.app`; set `APNS_SANDBOX=1` only for development builds).
- **While the app is open** (2026-11-12, found when a follow showed no push during testing): the system doesn't draw a push for an app in the foreground (Android hands it to the app; iOS does too without presentation options), so the app refreshes Friends when one arrives (`onPushWhileOpen`), and the tab badge and Activity show it at once. Test pushes with the app in the background.
- **Logs** (2026-11-12): `notify` logs, without ids or tokens, when the recipient has no registered phone, when FCM sign-in is refused, and when a message comes back as anything but ok, so a missing push can be traced in Vercel's runtime logs.
- **Taps** open the push's route: `#/friends`, or `#/routine/<code>` for a sent workout (`onPushTap`, wired in `App.tsx`).
- **Removing tokens:** signing out drops the token (`stopPush` before `signOut`). So does leaving Friends or deleting the account (`socialDeletes`).
- **Android** (`@capacitor/push-notifications`):
  - The release build writes `android/app/google-services.json` from the `GOOGLE_SERVICES_JSON` secret.
  - Without it the app builds the same, but `InstallInfo` reports `push: false` (no `google_app_id` resource), so the app never asks Firebase for a token (that would crash).
  - Pushes use a "Friends" channel (created by the app; its name is `push.channel`) and the app's status bar icon, set as Firebase defaults in `AndroidManifest.xml`.
- **iOS:** `AppDelegate.swift` hands the APNs token to Capacitor. It needs the Push Notifications capability and the `aps-environment` entitlement, which are under "iOS (deferred)" in Open items. Until then registration fails quietly.
- **Web app:** no push; the dot and Activity carry it (Platform deltas).
- **Tests:** `src/server/push.test.ts` covers language, the switches with likes off by default, a sent workout's route, dead tokens, the token limit and sign-out, and staying off without keys.

## Posts, avatars and privacy (stage 3)

Melvin, 2026-11-11, from the social gaps list: "do 1, 2, 3, 4, 5 (yeah unlock different avatars through locker but have a few default ones), 6, 7, 8". This stage is 4 (richer posts), 5 (profile identity) and 6 (finer privacy); the rest follow in their own changes.

- **Captions.** "Post to friends" on Done now opens a compose sheet: an optional caption (280 characters, through the comment filter, so no links or slurs) and who sees it, then Post. "Post every workout" still posts straight away, without a caption, to the lifter's usual audience. Once posted, Done shows **Posted · Edit · Remove**; a post's "…" has **Edit post** too (`editPost`). The caption shows under the poster's name, and on the public web page.
- **Who sees each post** (`posts.audience`): **Followers** (`all`: everyone who can see the profile, so anyone while it's public), **Friends** (`friends`: only people the lifter and they both follow) or **Only me** (`me`: kept on the lifter's own profile, a private log). The default for new posts is a Friends setting (**Who sees new posts**, `social_profiles.audience`, Followers to start), and the compose sheet can change it per post. One SQL rule (`seesPost` in `social.ts`) is used by the feed, a person's posts, a post's thread, likes, comments and the post count, so a post nobody may see can't be reached by id either. The public page and the people sitemap only ever use `all` posts. A post that isn't for Followers says so beside its time ("· Only me") on the lifter's own copy.
- **Save a friend's workout.** **Do this workout** in the whole-workout view (it was "Save as a routine" in the post's "…" until gap list 2): the exercises in order with their set counts become a routine code (`postRoutineCode`, the same code as routine links) and open the shared-routine preview with Save. Custom exercises the reader's app doesn't know are left out, and nothing personal (weights, reps) goes with it, because the reader's own progression fills those in.
- **Avatars** (Melvin: "unlock different avatars through locker but have a few default ones"). Eleven avatars, each one of our own icons on a tinted disc or the mascot (`AvatarFace.tsx`): **four for everyone** (Dumbbell, Bolt, Leaf, Night owl, in `STARTER`), five from **levels** (3, 8, 14, 22 and 30, levels that had no item, so no one's existing rewards change), and two from **badges** (Unbroken · Silver for On fire, Pro member · Silver for Pro spark). They're Locker items (`kind: "avatar"` in `game.ts`) but never come from a crate (`cratePool` leaves them out), so every crate already opened still holds what it held. Pick one in **Awards › Locker › Friends avatar** or **Friends settings › Avatar** (which also offers the name's first letter, the default); both set `profile.cosmetics.avatar`, so it syncs like any setting. A locked avatar says how to get it. The app sends the pick to the server (`useProfileSync`, only a change and never the same change twice); the server only checks the id is a known avatar (`AVATAR_IDS`), because unlocks are worked out from the lifter's own event log on the device. Avatars show on posts, comments, Activity, people lists and profiles. The public web page keeps the first letter.
- **Best lifts showcase.** A profile shows the lifter's top three lifts by estimated one-rep max, each with the set behind it (`bestLifts` in `src/lib/social.ts`: loaded sets only, no cardio, no sets done lighter for an injury), in the reader's units, with the "i" for estimated one-rep max. **Show my best lifts** (Friends settings › Privacy, on to start) shows them only to people who can see the posts, and only while **Show weights on posts** is on (turning the showcase on turns weights on). With it off the app sends an empty list, so the server holds nothing.
- **Mute.** A person's "…" has **Mute**: their posts leave the lifter's feed, while following, their profile page and Activity stay as they were, and they aren't told (`mutes` table). **People › Muted** lists them with Unmute (shown only when someone is muted). Leaving Friends or deleting the account deletes mutes both ways.
- Analytics: `feature` `social_save_workout`.
- Tests: the stage 3 cases in `social.test.ts` (captions and the filter, each audience in the feed, threads, likes, counts and the public page, the default audience, mute, avatars and the showcase rules), `socialClient.test.ts` (best lifts, sending only changes, a post as a routine), the avatar rules in `game.test.ts`, and the edit and mute flows in `Friends.test.tsx`. The accessibility run adds the post menu, Friends settings with the avatar picker, and a profile with best lifts.

## Invites and the leaderboard (stage 4)

Items 3 and 1 of the same list.

- **Invite a friend** (People, first): makes the lifter's invite code (8 characters without 0/O or 1/I, like trainer codes; one live code per lifter, 30 days, up to 50 people; `social_invites`) and shares `www.getliftsmith.com/app/#/invite/<code>`. Whoever accepts it and the lifter **follow each other**, accepted both ways whatever their follow settings, because one sent the link and the other chose to accept it. The inviter gets the usual new-follower notification. Blocks either way, a suspended inviter, an expired or used-up code all answer "this invite has expired or been used up". Finding people stays exact handle or a link: there's still no directory, and no contact matching (Claude's call, 2026-11-11: uploading address books is a privacy cost for a small gain).
- **The invite screen** (`#/invite/<code>`, `InviteScreen`): signed in, it shows who invited them; not yet in Friends, the join form is right there and joining accepts the invite; in Friends, one tap (**Accept and follow each other**) does it and opens the inviter's profile. Signed out, it asks to sign in, and on the web it offers **Get it on Google Play** with the invite as the Play install referrer (`utm_source=invite&utm_campaign=<code>`), which the Android app reads on first launch (`startInvite`, the same `installReferrer` creator codes use). The code waits on the device (`liftsmith.invite` in localStorage) until the lifter has signed in and joined, wherever they join from (`useProfileSync` accepts it).
- **Android** opens the link in the app through App Links (the `/app` filter). **iPhone** has no install referrer and Universal Links are deferred, so the link opens the web app, where everything works; after installing, the lifter opens the link again or types the handle (Platform deltas).
- **Friends › Board** (a fourth chip, `board` op): this week or last week, Monday to Sunday in the lifter's own time zone (`weekStart`), for the lifter and everyone they follow, ranked by workouts, sets, minutes or volume. It counts **only workouts posted to Friends** that the lifter may see (the same `seesPost` rule), so an unposted or "only me" workout never shows and no new data leaves the phone. Ties share a place. Per the action-over-stats rule, one line above it says what to do: "Blair is 2 ahead in workouts. Your next workout closes the gap.", "You lead by 1 in workouts.", "You're tied with Blair.", or "Post a workout to get on this week's board." (`boardNudge`). Tapping a name opens the profile. With no one followed yet, it offers to find people.
- Analytics: `feature` `social_invite` and `social_invite_accept`.
- Tests: the stage 4 cases in `social.test.ts` (one reusable code, mutual follows, expiry, blocks, suspension; the board's people, week and audiences), `invite.test.ts` (codes, the referrer, the week's start, ranking and the nudge), and the invite-to-board flow in `Friends.test.tsx`. The accessibility run adds the board and the invite screen.

## Challenges and training partners (stage 5)

Items 2 and 7 of the same list.

- **Friend challenges** (Friends › Board, above the board; `challenges`, `challenge_members`). **Start a challenge**: a name (optional; it defaults to "Most sets" and friends), one measure (workouts, sets, minutes or volume, the board's four), a length of 1, 2 or 4 weeks from now, and up to 19 friends who follow the lifter back (mutual friends only, the same rule as sending a workout). The starter is in from the start; the others get an Activity line and a push ("Alex challenged you: Most sets", covered by the follows switch) and **Join** or **No thanks** on the card. Declining takes them off. Each card shows the days left, the standings (joined members only, ties share a place), how many invites are still unanswered, and, per the action-over-stats rule, the same one line as the board ("Blair is 45 min ahead in minutes. Your next workout closes the gap."; `challengeNudge` in `src/lib/challenge.ts`). Once it ends it shows who won ("Won by Blair") for two weeks (`CHALLENGE_KEEP`), then drops off.
- **Scoring and privacy:** a joined member scores from the workouts they **posted to Friends** inside the window, to anyone but themselves (an "only me" post never counts), the same sums as the board. Only the totals are shown to the other members, never the posts, and joining says so ("Joining shows your totals for it to the others in it."), because the members may not all follow each other. Someone blocked either way is left off the reader's card. Nothing new leaves the phone: it's built from posts.
- **Leaving:** a member can **Leave**; the starter's button is **End challenge**, which deletes it for everyone (**Remove** once it's over). Limits: 10 running challenges started per lifter (`SOCIAL_LIMITS.challengesActive`, "You have 10 challenges running"), 10 new ones a day (`DAILY.challenge`), 20 people each.
- **Tag training partners:** the compose sheet (Done's "Post to friends" and "Edit post") has **Trained with**: chips of the lifter's mutual friends, up to five (`post_partners`). Not offered for an "only me" post, and changing a post to "only me" removes its tags. The post shows "with Blair and Casey" under the header (partners who were suspended or who block the reader are left out). A newly tagged lifter gets an Activity line and a push ("Alex tagged you as a training partner", covered by the comments switch); editing doesn't notify the same person twice. A tagged lifter can **Remove me from this post** from the post's menu. Tags don't put the post on the tagged lifter's profile: who sees a post stays the poster's choice.
- Push kinds `challenge` and `tag` (`PUSH_PREF` in `push.ts`), text `push.challenge` and `push.tag` in six languages. Analytics: `feature` `social_challenge_start` (with the measure) and `social_challenge_join`.
- Deleting the account or leaving Friends deletes the challenges the lifter started, their memberships and every tag on or of them (`socialDeletes`); deleting a post deletes its tags.
- Pure web code calling the server, so Android, iOS and the web app get it together.
- Tests: the stage 5 cases in `social.test.ts` (mutual friends only, scoring in the window, audiences, invites and declining, the running cap, ending, tags and untagging, deletion), `challenge.test.ts` (standings, the nudge, days left, winners) and the challenge-and-tag flow in `Friends.test.tsx`. The accessibility run adds the board with challenges, the start sheet and a post with partners.

## Clubs and gym crews (stage 6)

Item 8 of the same list.

- **Friends › Clubs** (a fifth chip, also `#/friends/clubs`): the lifter's clubs, each with its member count. **Start a club** takes a name (the filter applies, no links); the starter is its first member and runs it. **Have a club code?** takes the 8-character code. Up to 10 clubs per lifter (`SOCIAL_LIMITS.clubsEach`), 100 people per club, 5 new clubs a day.
- **Joining:** anyone with the club's link (`www.getliftsmith.com/app/#/club/<code>`, `ClubScreen`) or code can join, including people who don't follow each other. That's the point of a gym crew, and it's why a club shows only totals. Signed out, the link asks to sign in; not yet in Friends, the join form is right there and joining also joins the club. Someone the starter blocked (or who blocked the starter) can't see or join it.
- **The club sheet:** **Invite to the club** (share the link, with the code under it), then **this week's board** of every member from workouts they posted to Friends (anyone but themselves; "only me" never counts), by workouts, sets, minutes or volume, with the board's one-line nudge (action over stats). Members see each other's **totals only, never the posts**; the join screen says so ("Joining shows your weekly totals from posted workouts to everyone in the club"). Someone blocked either way is left off the reader's view.
- **Running it:** the starter can remove a member (the bin button on their row), make a **New link** (the old code stops working, for a link that spread too far) and **Delete the club**. Members can **Leave**.
- Server: ops `clubCreate`, `clubs`, `club`, `clubInfo`, `clubJoin`, `clubLeave`, `clubManage`; tables `clubs` and `club_members`. Leaving Friends or deleting the account deletes the clubs the lifter started and their memberships (`socialDeletes`). No push: joining a club isn't news anyone needs on their lock screen.
- Analytics: `feature` `social_club_start`, `social_club_invite`, `social_club_join`.
- Pure web code calling the server, so Android, iOS and the web app get it together. Club links open the app through the same `/app` App Links filter on Android and the web app on iPhone (Platform deltas, like invite links).
- Tests: the stage 6 cases in `social.test.ts` (codes, the board, audiences, the starter's tools, blocks, the cap, deletion) and the start-and-join flow in `Friends.test.tsx`. The accessibility run adds the clubs list, a club and a club link.

## People you may know and richer profiles (gap list 2)

Melvin, 2026-11-12: "Are there missing friends features? Seems a bit light, no?" From the list that followed he picked 1 (people you may know), 3 (open a post to see the whole workout), 4 (training now and cheers, "it should also show the celebration emoji animation on their workout screen like google meets"), 5 (replies, mentions, who liked), 6 (club feed and goals), 7 (monthly challenges for everyone), 8 (richer profiles) and 9 (friend nudges in coach's notes), not 2 (photos on posts). Built in that order of value, one change each; this part is 1 and 8.

- **People you may know** (People, under any waiting requests; and on the Feed while the lifter follows fewer than five people): from real ties only (`suggest` op): someone who follows the lifter and isn't followed back, people they trained with (tagged on the same post, either way), club mates, and people followed by people they follow, strongest tie first, up to 20. Each says why in a short line ("Follows you", "You've trained together", "In Barn crew with you", "Followed by Blair and 2 others you follow"; `suggestionWhy`). **Follow** (or **Ask** for a private profile) is one tap, **Hide** stops suggesting that person (`suggest_hides`). Never someone already followed or asked, blocked either way, suspended or hidden. There's still no list of everyone and no address book matching.
- **Suggest me to people I may know** (Friends settings › Privacy, `social_profiles.suggest`) is **on to start** (Claude's call, 2026-11-12): a suggestion only goes to someone with a real tie, shows only the name, handle and avatar, and a private profile still approves each follow, which is how the big social apps do it and the reason feeds stop starting empty. Off, the lifter is suggested only to people they follow (the "Follows you" tie, which those people already see in Activity).
- **Finding by name** (the People find box, `search` op): as the lifter types two letters or more (after a short pause), **public profiles** are found by the start of their handle, the start of their name or a word in it, and **anyone** by their exact handle, public or not. Private profiles never come up by name: they didn't choose to be found. Same daily limit as lookups. Enter still opens an exact handle.
- **Richer profiles** (the person page, only for readers who may see the posts): the **level** and **training-week streak** (worked out on the lifter's device like the best lifts and sent only when they change, `profileChanges`), and a **training calendar** of the last 12 weeks, Monday to Sunday, from the posts the reader may see (`trained` on the profile card; "only me" posts never show). Per the action-over-stats rule the calendar carries one line to act on: "Usually trains on Monday and Wednesday. Pick one of those to train together." (`usualDays`: a weekday with a workout in a third of the weeks they trained, at least twice, once there are four workouts). The **Followers** and **Following** counts open those lists (`personPeople` op), with blocked people left out.

## Safety

- **Blocking** removes follows both ways; neither sees the other's profile, posts or comments again (lookups answer "no one with that handle"), and the blocked person isn't told. Unblock from People › Blocked.
- **Reporting** a post, comment or profile: one reason chip (spam, bullying, hate, sexual, dangerous advice, something else), then Send. One report per person per thing. **Three different people reporting a post or comment hides it** (`HIDE_AFTER`) until staff decide. A profile is reported by handle but stored by account, so changing the handle doesn't escape it.
- **The admin Reports tab** (`/admin/?tab=Reports`, `src/components/admin/Reports.tsx`) lists open reports grouped by what was reported, most reported first, with the content, author, reasons and notes. Admins can **Remove** (deletes the post or comment; for a profile, resets the name to the handle), **Dismiss** (shows it again), **Suspend author** (hides their profile and everything they wrote, and stops them following, posting and commenting) or **Unsuspend**. Every action is in the audit log. Support staff can read the tab.
- **The word filter** (`src/server/moderation.ts`) checks handles, names, comments and custom exercise names: whole words only, after undoing capitals, accents, leetspeak and doubled letters, against a short list of slurs kept as SHA-256 hashes (so they aren't written out in this public repo). **Links are refused** in names and comments. Comments are 280 characters.
- **Limits per account per day** (`DAILY`): 100 follows, 20 posts, 100 comments, 500 likes, 30 reports, 300 lookups. The post owner can delete any comment on their post.
- **Leaving Friends** (its settings) deletes the profile, posts, likes, comments, follows, blocks and the reports they made; a suspended profile's row stays, so leaving and rejoining can't undo a suspension. **Deleting the account** deletes all of it (`socialDeletes`, part of `deleteAccount`).

## How it works

- Server: `src/server/social.ts`, one route `POST /api/social/` with `{op, …}` (`me`, `join`, `update`, `leave`, `lookup`, `follow`, `unfollow`, `answer`, `people`, `block`, `unblock`, `mute`, `report`, `post`, `unpost`, `editPost`, `posted`, `feed`, `person`, `thread`, `like`, `comment`, `uncomment`, `activity`, `send`, `invite`, `inviteInfo`, `acceptInvite`, `board`, `challengeCreate`, `challenges`, `challengeAnswer`, `challengeLeave`, `untag`, `pushToken`, `pushOff`), so the phones need one CORS-allowed path. Tables in Turso: `social_profiles`, `follows`, `blocks`, `posts`, `post_likes`, `post_comments`, `reports`. The feed is posts from accepted follows plus your own, newest first, 20 at a time.
- **Activity is worked out, not stored**: new followers, requests, likes and comments on your posts, sent workouts, challenge invites and tags, from the tables themselves; `seen_at` on the profile marks what's been read.
- App: `src/lib/social.ts` (calls, the `useSocial` store, building a post from the event log) and `src/components/app/Friends.tsx`. Text in `friends.*`, six languages.
- **Platforms:** pure web code calling the server, like sync and share links, so Android, iOS and the web app get it together; no native code. Push notifications are stage 2 (Open items).
- Analytics: `feature` events `social_join`, `social_follow`, `social_post` (`tap` or `auto`), `social_report` (`<kind>:<reason>`), `social_leave`. No handles, names or text.
- Tests: `src/server/social.test.ts` (privacy defaults, following, the feed's visibility, likes and comments, blocking, report hiding and staff actions, suspension, account deletion) and `src/components/app/Friends.test.tsx` (the screens against the real server code). The accessibility run scans Friends signed out, the feed, comments, activity, people and a person's page.
