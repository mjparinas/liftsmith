# Analytics and the admin panel (Melvin, 2026-11-09: "whatever data we can store on users, save it")

Part of the decision record. [AGENTS.md](../../AGENTS.md) has the rules that apply to every change and the list of topics. Record decisions about this topic here, in the same change as the code.

- **Capture as much as the stores and privacy law allow, in first-party storage.** No third-party analytics SDK. The app queues events in localStorage (`src/lib/analytics.ts`) and sends them in batches to `POST /api/collect/`; the website sends page views and call-to-action clicks to `POST /api/pv/` (`src/components/SiteBeacon.tsx`, in the root layout, skips `/app/` and `/admin/`). Both are stored in the server database (`src/server/db.ts`, libSQL/Turso; tables `installs`, `events`, `page_views`, `subscription_events`).
- **What is captured:** a random install id (not an advertising id); platform, device maker and model, OS version, app version and build, form factor, screen, language, time zone, reduced motion; country and region from Vercel's geo headers (never the IP or city); install source (store, Play Install Referrer `utm_*` tags, Apple Search Ads attribution through AdServices, and for web installs the first site visit's UTM tags, referrer and landing page); screen views, setup wizard steps, feature use, permission answers, workout start/finish/discard with exercise and set counts and length, feedback sent (kind only), paywall views, trial starts and purchases with plan and price.
- **What is never captured:** weights, reps, heart rate, body weight, Health Connect / Apple Health readings, cycle data, location, names, emails, notes, anything typed. No IDFA, no Android advertising id (`AD_ID` permission is removed in the manifest), no ATT prompt. The allow-list in `src/lib/analyticsSchema.ts` is the only way an event or property reaches the server; the server drops anything else. Adding an event means adding it there, to `/privacy/` and to `docs/PRIVACY_LABELS.md` in the same change.
- **Consent:** usage stats start **on** outside the EU, EEA, UK and Switzerland and **off** inside them (by time zone) until the lifter switches them on. The setup wizard's last step has the switch, and so does Settings › Usage stats (it also shows the install id). Off stops sending and clears the queue; "Erase this device" also resets the install id. The site counter is cookieless (a daily-salted hash of IP and browser counts a visitor once a day) and respects Global Privacy Control.
- **Native parity:** `InstallInfo` plugin on both platforms. Android `InstallInfoPlugin.java` (Build model and version, installing store, Play Install Referrer via `com.android.installreferrer`); iOS `InstallInfoPlugin.swift` (model identifier, iOS version, App Store / TestFlight receipt, AdServices token). iOS has no per-install referrer like Play's: App Store campaign links (`pt`/`ct`) report in aggregate in App Store Connect, and only Apple Search Ads attributes per install.
- **Store privacy labels** are in `docs/PRIVACY_LABELS.md` (Play Data safety and App Store App Privacy answers) and `ios/App/App/PrivacyInfo.xcprivacy`. Everything collected is "not linked to identity" and "not used for tracking", except a feedback email the user gives. Keep them in step with the allow-list.
- **Admin panel** at `/admin/` on the **website only** (Melvin, 2026-11-09): `page.api.tsx`, so the static export that goes into the Android and iOS apps leaves it and every API route out. Sign-in is a one-time link emailed through Resend to an address on `ADMIN_EMAILS` (full access) or `SUPPORT_EMAILS` (read-only); only token hashes are stored, sessions last 7 days, taking an address off the list ends its sessions, and every sign-in and change is in the audit log. Without either list the panel and its API answer 404. (Gradelings adds an authenticator-app second step; add it here when accounts land.)
- **Tabs:** Overview, To Do, Inbox, then the numbers, then System (details of the three below). Overview (installs by store, DAU/WAU/MAU, setup and first-workout rates, time to value, MRR), Traffic (visitors, page views, pages, referrers, UTM sources and campaigns, countries, devices, browsers, call-to-action clicks), Acquisition (install sources, campaigns, Apple Search Ads, countries, stores, languages), Funnel (install → setup → workout → second workout → paywall → trial → paid, per store; website → CTA → web install; setup wizard step drop-off), Retention (D1/D7/D30 and weekly cohorts), Engagement (workouts a day, length, sets, auto-ended, screens, features, permission grant rates), Devices (platforms, OS versions, models, makers, app versions, form factors), Revenue, Creators, Users, Installs (latest installs; mark the owner's and CI devices as **test** to leave them out of every number; open one for its page), Flags, A/B Tests, Automations, System and Log.
- **Tab links and history** (Gradelings, 2026-11-10): each tab has its own address (`/admin/?tab=Users`; an open account or install adds `&open=<id>`), and every move goes in the browser history, so Back, Forward, a reload or a shared link land in the same place (`viewUrl` in `AdminApp.tsx`).
- **Users tab** (Gradelings' Users, 2026-11-10; `src/server/adminUsers.ts`, `/api/admin/users/`, `Users.tsx`): search accounts by part of an email or an account id; totals (accounts, new and seen in 30 days). An account's page shows its sign-in methods, the devices signed in (platform, last used, expiry), how much it has synced (event count, size, deleted, profile and gyms, first and last event time) and whether it has Pro on the server (only the review account). **What was synced is counted, never read or shown.** Store purchases belong to installs, not accounts. *Private notes* (`account_notes`, up to 1,000 characters, deleted with the account): any staff member adds one; support removes only their own, admins any. Admins can **sign out everywhere** (the devices keep their data) and **delete the account** with everything synced to it (type `DELETE`; the same `deleteAccount` the app uses, Apple token revoked). Every change is audited, and each account page a support account opens is logged as `account.view`; the log keeps the account id, never its email.
- **Install page** (`installDetail` in `adminUsers.ts`, `GET /api/admin/installs/?id=`, `InstallDetail.tsx`): the device, where it came from, each event name with its count and last time, the latest 50 events with their allow-listed properties, subscription events, the store entitlement and the creator code.
- **CSV downloads** (`GET /api/admin/export/?type=installs|accounts|subscriptions`, `src/server/adminExport.ts`, `src/lib/csv.ts` from Gradelings): admins only, since the accounts file holds emails; each download is audited. Device, account and subscription rows only, never synced data, health readings, anything typed or an IP address. A cell starting with `=`, `+`, `-` or `@` gets a leading apostrophe so a spreadsheet never runs it.
- **Log tab** (`/api/admin/audit/`, `Log.tsx`): the latest 200 sign-ins and changes, with their details.
- **Flags tab** (Gradelings' feature flags, 2026-11-10; `src/server/flags.ts`, `/api/admin/flags/`, `Flags.tsx`): every flag in `src/lib/flags.ts` with its label, default and options. An admin sets a value for everyone or for a share of installs (a stable hash of the flag and install id, so raising the share only adds installs), or goes back to the default (`feature_flags`, a row only once changed). **The apps read `GET /api/flags/`** (`src/lib/remoteFlags.ts`: on open, on return to the foreground and when back online; CORS for the native origins; rate-limited per address) and keep the last answer for offline use; the static web export has no API and asks nothing. **The install id goes with the request only while usage stats are on**; without it a partial rollout or a test gives the default or the control and nothing is recorded. A value set on the device itself (the hidden phone-motion switch in Settings, `setLocalFlag`) wins over the server. Adding a flag: add it to `FLAGS` with a label and description and read it with `flag()`.
- **A/B Tests tab** (Gradelings' experiments, 2026-11-10; `src/lib/experiments.ts` pure, `/api/admin/experiments/`): a test splits installs between a flag's values, at most one per flag; the first variant (the default) is the control. *Draft:* everyone sees the control. *Running:* each install gets a stable variant, recorded in `experiment_assignments` the first time it asks (only installs already in `installs`, so random ids can't fill the table). *Stopped:* everyone gets the winner picked; delete a stopped test to hand the flag back to the Flags tab. A test wins over the flag's own setting. Results per variant, test installs left out: installs, started a trial and paid (`trial_convert`, `purchase` or `renew`) after joining, and worked out in the last 7 days, each with a two-sided p-value against the control (two-proportion z-test), plus Gradelings' plain verdict on paying and on trials (too early until each variant has 30 installs; "Use … for everyone" is highlighted once a variant is 95% likely to be better). The setup wizard's trial length (`trialDays`, 7 vs 14) is the first flag ready to test; the public site keeps saying 14 days. Disclosed on `/privacy/` and in `docs/PRIVACY_LABELS.md`.
- **Inbox, To Do and System tabs** (Melvin, 2026-11-09: "similar to Gradelings"; copied from Gradelings' inbox, admin queue and system health, cut to what Liftsmith has). Support staff can read all three; changes need an admin and are audited.
  - *Inbox* (`src/server/inbox.ts`, `/api/admin/inbox/`, `Inbox.tsx`): mail Resend receives for the domain (receiving and its MX record were already on for getliftsmith.com, so no DNS change was needed). It's **read live from Resend's receiving API; bodies are never copied into our database**, only what an admin did with each message (`inbox_state`: done, answered by whom, archived). **One Resend account receives for Gradelings too, so only mail to or cc'ing `INBOX_DOMAINS` (default `getliftsmith.com`) is listed or opened.** HTML mail is sanitized (`emailHtml.ts`, from Gradelings) and shown from its own route (`/api/admin/inbox/view/`) in a sandboxed frame with a strict policy, remote images blocked until "Load images", or as plain text. Replies are plain text, threaded (`In-Reply-To`, `References`), sent from `FEEDBACK_FROM` (else `MAIL_FROM`), and mark the message answered. **Reading received mail needs a full-access Resend key, `RESEND_INBOX_API_KEY`;** `RESEND_API_KEY` is sending-only and keeps sending. Without it the tab shows the setup steps. Mail is "waiting" when it's from outside our domain, under two weeks old and not done, answered or archived; the tab shows that count. In-app feedback lands here too, since it's emailed to hello@. **Archive is saved in `inbox_state` (Turso), so it holds across sign-ins.** The panel's own sign-in emails are never listed or opened (`isSignInLink`): they're sent to the admin address, often hello@ itself, so a new one on every sign-in looked like archived mail coming back (Melvin, 2026-11-11). Other mail our servers send to hello@ (the morning digest, alerts), but not in-app feedback (subject `[Liftsmith …]`), files itself in Archived (`isRobotMail`); "Move to inbox" stores `archived_at = 0` so it stays put. No AI drafts or saved replies yet (Gradelings has both).
  - *To Do* (`src/server/adminTodo.ts`, `/api/admin/todo/`, `Todo.tsx`): what needs a person, worked out each time from the data: mail waiting, creators owed a payout ($25+), store payment failures in the last 14 days, a late or failed reminder job, and setup still to do (missing `RESEND_INBOX_API_KEY`, `ANALYTICS_SECRET`, `NEXT_PUBLIC_SITE_URL`, `UPTIMEROBOT_API_KEY`). Each can be snoozed (tomorrow, next week) or dismissed (`admin_todo_hidden`, by key; keys change with the data, so a new message or a bigger amount owed comes back). Plus the admins' own tasks with an optional note and due date (`admin_tasks`). A source that fails is left out with a note, never empties the list.
  - *System* (`src/lib/systemHealth.ts` pure, `src/server/systemHealth.ts`, `/api/admin/system/?check=` or `?page=`, `System.tsx`): one card each for the live site (pages, files and the build files they name, loaded from the www address), uptime (UptimeRobot; the account also watches Gradelings, so the card shows only monitors whose name or address says "liftsmith", `isLiftsmithMonitor`; Melvin, 2026-11-10), builds (GitHub Actions: CI on staging and main, the nightly promotion and releases), deploys (Vercel: the running deployment from its system variables, history with `VERCEL_TOKEN`), database (counts and the latest event), email (Resend domains and reminder sends), the daily reminder job, subscriptions (RevenueCat webhook events) and settings (names only, never values), plus Vercel's, GitHub's, Resend's, Turso's and RevenueCat's public status pages. Each card loads on its own and is cached a minute on the server ("Check again" skips it); a card that isn't set up says what to set. Every token stays on the server. **Scheduled jobs record their runs** (`trackJob` in `src/server/monitor.ts`, table `job_runs`, 60 days), so the System card and To Do can tell a late or failed job; wrap any new cron route in it. **`GET /api/health/`** is a public, uncached database check for UptimeRobot.
- **Maintenance mode** (Gradelings, 2026-11-10; `src/lib/maintenance.ts` pure, `src/server/maintenance.ts`, `src/proxy.api.ts`, `/api/admin/maintenance/`, `Maintenance.tsx`): an admin switches it on at the top of the System tab by typing TURN ON (audited); a banner then shows on every admin tab. While it's on, every page answers 503 with a short "back soon" page and every API route a 503 JSON error with `Retry-After`, except the home page, `/privacy/`, `/delete-account/`, the admin panel, the web app (`/app/`, which runs from the device), build files, `/api/health/`, the cron routes, the RevenueCat webhook and the reminder unsubscribe and confirm links, so the stores' and mail links keep working. The apps keep everything on the device and sync later. The switch lives in `admin_settings`; each server reads it at most every 15 seconds and **stays open if the database can't be read**. The proxy is named `.api.ts`, so only the server build has it.
- **Alerts and the morning digest** (Gradelings, 2026-11-10; `src/server/alerts.ts`, Automations tab, `/api/admin/automations/`): emails to `ADMIN_EMAILS` only (never support), each kind at most once every 6 hours, each switchable on the Automations tab, with a test button. Instant alerts: a new paying customer (a store-verified first purchase or trial conversion, from the RevenueCat webhook), a store payment failure, a scheduled job that failed, five failed staff sign-ins within 15 minutes (`staff_sign_in_failures`: used or expired links; the System tab's Security card counts them too), and a System check going down and coming back. The digest (daily, `/api/cron/admin/` at 13:00 UTC, also wrapped in `trackJob`) gives the last 24 hours in counts only: new installs, lifters who worked out, new accounts, trials, payments and cancellations, the To Do list and any System problems. Like the panel, no synced data, health data or anything a lifter typed.
- **System extras** (Gradelings, 2026-11-10): *Security* (failed staff sign-ins in the last day and week), *Capacity* (the database's size from `PRAGMA page_count` × `page_size`, sampled daily into `db_size_samples`; with optional `DATABASE_SIZE_LIMIT_MB`, the share used, amber at 70% and red at 90%, and days until full from the last 30 days' growth), *Backups* (Turso keeps point-in-time backups; amber until a restore practice is recorded and again 35 days after the last, see `docs/RESTORE.md`), and an **auto refresh** checkbox that rechecks every card each minute (remembered on that browser).
- **Two-step sign-in for staff** (Gradelings, 2026-11-10; `src/server/totp.ts` and `twoFactor.ts` ported, `/api/admin/2fa/`, `TwoFactor.tsx`): after the emailed link, the panel stays shut until the second step: a 6-digit code from an authenticator app (RFC 6238, one step of drift, a step never accepted twice) or one of 8 single-use recovery codes (hashes only). **Required for every staff address by default** (`ADMIN_2FA` unset), because the panel shows lifters' emails and can delete accounts; `ADMIN_2FA=optional` lets an address without it in, but an address that has it on always needs the code. Setting it up shows a QR code (`qrcode-generator`, drawn as SVG on our page, no outside service) and the key to type; a setup started but not confirmed carries on with the same secret at the next sign-in (so the entry already scanned into the app still works; "Start over" makes a new one; 2026-11-11); turning it on signs that address's other sessions out. Wrong codes are limited per address (8 in 10 minutes) and count as failed staff sign-ins (Security card, alerts). New recovery codes or turning it off need a fresh code; an admin can reset someone else's (System tab, signs them out everywhere) for a lost phone. Secrets are sealed with `TWO_FACTOR_KEY` (AES-256-GCM; set it before anyone enrols and never change it). The second step lives in `admin_session_steps`, so `admin_sessions` needed no migration. Every sign-in field is in a real `<form>`, so Enter submits it: the emailed-link address, the setup and sign-in codes, and the app's email sign-in (address and code) (Melvin, 2026-11-11). Audited: `2fa.enable`, `2fa.verify`, `2fa.backup-codes`, `2fa.disable`, `2fa.reset`.
- **Saved replies and Draft with AI in the Inbox** (Gradelings, 2026-11-10; `src/lib/savedReplies.ts`, `/api/admin/replies/`, `SavedReplies.tsx`, `src/server/replyDraft.ts`): admins insert a saved reply into the reply box (edited on the Inbox tab, kept in `admin_settings`; four defaults: cancelling and refunds through the stores, sync and a new phone, deleting an account, thanks). With `ANTHROPIC_API_KEY` set, **Draft with AI** asks Claude for a first draft from the public FAQ (`src/lib/faqs.ts`, the same list the home page shows) and the saved replies; it only fills the reply box, and a person always reads, edits and sends (decided in Gradelings, October 2026). The email is cut to 8,000 characters, sent through the official SDK with low effort, a cached system prompt and the server-side fallback on a safety decline; nothing about it is stored, only an `inbox.draft` audit row. `/privacy/` and the store labels name Anthropic as a service provider for this.
- **Running costs and profit on the Revenue tab** (Gradelings' monthly costs, itemised; `src/lib/runningCosts.ts`, `/api/admin/costs/`, `RunningCosts.tsx`): admins list what the business pays a month (a yearly fee as a twelfth; the first edit suggests Vercel, Turso, Resend, RevenueCat, the store developer accounts and Anthropic), and the tab shows the total, profit a month and a year (net MRR less costs) and how much of the costs revenue covers.
- **Revenue tab tracks the forecast's inputs by store** (forecast doc: https://claude.ai/artifact/CiXkRo29nsLCuTzKYkQfx7): downloads a week, setup completion, trial starts, trial-to-paid, download-to-paid at day 35, annual share, monthly churn, annual first renewal, refund rate, revenue per install at day 14 and 60, realised price against $6.99 / $39.99, gross MRR and net MRR (15% store fee, refunds, 6% VAT), and Play billing-failure cancellations, each beside the forecast's assumption; plus real gross MRR against the conservative, base and optimistic curves (`src/lib/forecast.ts`) from launch (first store install, or `LAUNCH_DATE`). Computed in `src/lib/adminMetrics.ts` (pure, tested).
- **Subscription data:** both stores' server notifications (Google Play RTDN, App Store Server Notifications v2) go to RevenueCat, which calls **`POST /api/billing/revenuecat/`** (`src/server/revenuecat.ts`, checked against `REVENUECAT_WEBHOOK_SECRET`). Each event becomes a `subscription_events` row with `source` `store` (kinds `trial_start`, `trial_convert`, `purchase`, `renew`, `cancel` with `reason` `billing` for payment failures, `uncancel`, `refund`, `expire`; `subscription` is the store's original transaction id; `usd_micros` from RevenueCat's USD price; family shares and sandbox purchases carry no revenue or are left out) and updates the install's row in `entitlements` (for accounts and sync later). Until that secret is set, the app's own `trial_start` and `purchase` events stand in (`collect.ts`); once it's set they stop being mirrored, so nothing counts twice.
- **Accounts environment:** the database, `RESEND_API_KEY` and `MAIL_FROM` (email codes); `NEXT_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `NEXT_PUBLIC_GOOGLE_IOS_CLIENT_ID` and `NEXT_PUBLIC_APPLE_SERVICES_ID` (public; also accepted as audiences by the server; extra ids in `GOOGLE_CLIENT_IDS` / `APPLE_CLIENT_IDS`); `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` (Sign in with Apple key, for revoking on delete). Without a database the account routes answer 503 and the app says accounts aren't switched on yet.
- **Server environment:** `DATABASE_URL` + `DATABASE_AUTH_TOKEN` (or the Vercel Turso integration's `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN`), `ADMIN_EMAILS`, optional `SUPPORT_EMAILS`, `RESEND_API_KEY` (already used by feedback), optional `ADMIN_FROM`, `ANALYTICS_SECRET` (salt for the visitor hash), optional `LAUNCH_DATE`, `REVENUECAT_WEBHOOK_SECRET` (subscriptions), and for the Inbox and System tabs `RESEND_INBOX_API_KEY` (full-access Resend key, to read received mail), optional `INBOX_DOMAINS` (default `getliftsmith.com`), `UPTIMEROBOT_API_KEY` (read-only), `GITHUB_TOKEN` (read-only Actions; without it GitHub's hourly limit for anonymous reads applies) and `VERCEL_TOKEN` (read-only, deploy history); `TWO_FACTOR_KEY` (seals staff authenticator secrets) and optional `ADMIN_2FA=optional`; optional `ANTHROPIC_API_KEY` (Draft with AI); optional `DATABASE_SIZE_LIMIT_MB` (Capacity card). Without a database, `/api/collect/` answers 503 and the app keeps its queue.
- **Vercel Web Analytics is on too** (Melvin, 2026-11-09), alongside our own counter, not instead of it: `<VercelAnalytics />` (`src/components/VercelAnalytics.tsx`, `@vercel/analytics`) in the root layout. Public website only: `beforeSend` drops `/app/`, `/admin/` and `/me/` (same `isPublicPath` as `SiteBeacon`), strips query strings, and sends nothing under Global Privacy Control. It renders nothing in the static export, so the Android and iOS apps and the browser tests never load it (`/_vercel/insights` exists only on Vercel). Cookieless; disclosed on `/privacy/`. It needs Web Analytics switched on in the Vercel project (Analytics tab › Enable). Speed Insights is not added (separate, metered product).
- **Google Search in the Traffic tab** (Melvin, 2026-11-10: "similar to Gradelings"; ported from Gradelings' `src/server/traffic.ts`). `src/server/searchConsole.ts` reads Search Console on the server through a Google Cloud service account with the read-only scope `webmasters.readonly`, signing its own RS256 JWT (no Google SDK); `GET /api/admin/search/?days=7|28|90|365` (staff), cached 10 minutes per period, **Check again** skips the cache, a failed read isn't kept. It shows clicks, times shown, click rate and average position against the period before, a daily chart, **Worth a better title** (searches at position 4 to 20 shown 20+ times with under 3% clicks, `nearMisses` in `src/lib/searchConsole.ts`; the action-over-stats part), top searches and pages, countries, devices and the sitemaps with when Google last read them. Google's numbers settle late, so the period ends three days ago. Setup: create a service account in Google Cloud (no roles) with a JSON key, enable the Google Search Console API in that project, add the service account's email to the getliftsmith.com property in Search Console as a **Restricted** user, and set `GOOGLE_SERVICE_ACCOUNT_KEY` in Vercel to the JSON key (as is, or base64). `SEARCH_CONSOLE_SITE` is optional (default `sc-domain:getliftsmith.com`; use `https://www.getliftsmith.com/` for a URL-prefix property). Until the key is set the section says "Not set up" with these steps.
- **Bing Search in the Traffic tab** (Melvin, 2026-11-10: "Add Bing"), under Google's. `src/server/bing.ts` reads Bing Webmaster Tools' JSON API on the server with its API key (`GET /api/admin/bing/?days=…`, staff, cached 10 minutes per period, **Check again** skips the cache, a failed read isn't kept; the key is in Bing's request address, so no error message repeats the address). Daily clicks and times shown come from `GetRankAndTrafficStats`; searches and pages from `GetQueryStats` and `GetPageStats`, which Bing reports by week, so they're added up over the weeks that end in the period (`addUpWeeks` in `src/lib/bing.ts`, position weighted by times shown). It shows the same tiles against the period before, a daily chart, **Worth a better title on Bing** (the same `nearMisses` rule as Google), and top searches and pages. Bing keeps about six months, so a longer period says from when it has numbers. Bing's index also feeds DuckDuckGo, Yahoo and ChatGPT search. Setup: in Bing Webmaster Tools › Settings › API access, generate an API key and set `BING_WEBMASTER_API_KEY` in Vercel (Production and Preview, sensitive). `BING_SITE_URL` is optional (default `https://www.getliftsmith.com/`, the site as verified in Bing). Until it's set the section says "Not set up" with these steps. It's listed on the System tab's settings card.
