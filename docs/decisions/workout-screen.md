# Workout screen

Part of the decision record. [AGENTS.md](../../AGENTS.md) has the rules that apply to every change and the list of topics. Record decisions about this topic here, in the same change as the code.

- Big target weight and reps with steppers, the barbell plate graphic for every barbell set, a big Log set button, an automatic rest timer with +30 s and Skip, and the next set's plates shown during rest so the lifter can load while resting.
- **Live workout notification and lock-screen rest timer.** On Android, a foreground service shows an ongoing notification with a live countdown, the next set and plates, heart rate, and Log set and +30 s buttons; it sounds and vibrates when rest ends. On iOS the same content is a Live Activity on the lock screen and in the Dynamic Island. The web build falls back to a service-worker notification and an alert at rest end (`sessionNotify.ts`).
- **The live notification shows on the lock screen by default** (2026-11-10, found while recording Play's foreground service video). Its channel was `IMPORTANCE_LOW`, which Android files under "Silent" and hides on the lock screen unless the user shows silent notifications there. It now uses `workout-live-v2` at `IMPORTANCE_DEFAULT` with no sound or vibration (`setOnlyAlertOnce`), and the old `workout-live` channel is deleted, because an app can't raise an existing channel's importance. Only the "Rest over" alert makes a sound or vibrates. iOS needed no change: its Live Activity is always on the lock screen.
- **Android 16 Live Updates and Samsung's Now Bar** (Melvin, 2026-11-10: "Can we support android live notification feature"; he uses a Galaxy S25+). The workout notification asks to be promoted (`setRequestPromotedOngoing`, with the install-time `POST_PROMOTED_NOTIFICATIONS` permission), so on Android 16 it gets a **status bar chip** and sits at the top of the lock screen and shade. The chip shows the rest time left while resting and the set while lifting (`chipText`: "2/4", "W1/2" for a warm-up; numbers only so it fits the chip's 96 dp in any language). The notification also carries a **progress bar of working sets logged of those planned** in the whole workout. Samsung's One UI 8 shows promoted notifications in the **Now Bar** and its Live Notifications with no Samsung SDK or allowlist; we use only the standard Android API, so other phones get the same. Promotion rules we keep: ongoing, has a title, BigText style, no custom views, not colorized, channel above `IMPORTANCE_MIN`. The lifter can turn Live Updates off per app in Android's settings; then it's the ordinary ongoing notification, unchanged. Older Android ignores the request. Heart rate stays in the notification body and follows the battery rule (a heart-rate-only change updates it at most every 5 s). **Rest time left** (Melvin, 2026-11-11: "the Live Update notifications on android should show me how much time for rest is left"; on his Galaxy S25+ the system chronometer alone didn't show it). While resting, the notification says the time left in words ("1:23 left · next: 80 kg × 5", and "1:23 rest left" at the top of the expanded text), puts "1:23" in the status bar chip and the Now Bar (`setShortCriticalText`), and swaps the workout bar for a **rest bar** that empties as rest runs out (its length is the whole rest, `restTotal`, so +30 s grows it back). The system chronometer stays in the header too. Not every surface draws the chronometer, so the service redraws once a second during rest only (`restTick`, aligned to whole seconds), stops when rest ends (and flips the notification back to the set view itself, chip "2/4", without waiting for the app) and when the workout ends. Text is `rest_left` and `rest_left_next` in all six `values-<l>` files. **iOS parity:** the Live Activity already counted rest down with the system timer on the lock screen and in the Dynamic Island; it now shows the same rest bar while resting (`ProgressView(timerInterval:countsDown:)`, `restFrom` in the state, animated by the system, no updates), labelled "Rest left" for VoiceOver in every language. The web fallback notification's "Rest until" and "Next" lines are translated too. The Live Activity shows the same set text in the compact Dynamic Island while lifting (instead of "Lift") and the same workout progress bar on the lock screen and the expanded island. Web: browsers have nothing like it (Platform deltas).
- The screen stays on during a workout (wake lock), unless the lifter turns it off in Settings › Workout.
- **Workout preferences** (Melvin, 2026-11-09; Settings › Workout › Plan details, `#/training`; the rest timer switches and "When rest ends" moved to Settings › Workout itself on 2026-11-10, `TrainingSettings.tsx`, `src/lib/training.ts`, stored on `profile.training`). Every field is optional and missing means the automatic choice, so older profiles behave exactly as before. Everything is chips and taps (no typing), so it works one-handed in the gym.
  - *Rest between sets:* a default for big lifts and one for smaller lifts, plus a per-exercise time. Order: the exercise's own, then compound/isolation, then by goal (`restFor`).
  - *Rep ranges:* one for compound and one for isolation lifts, plus a per-exercise range (`repRange`). Type ranges apply to loaded exercises only (bodyweight work keeps adding reps); holds stay in seconds. Double progression runs inside the chosen range.
  - *Sets per exercise:* Auto (3, 4 on the first big lifts, a filler set when time allows) or a fixed 2–6, plus a per-exercise count. A chosen count gets no filler sets; deload weeks and easy days still use fewer.
  - *Effort scale:* RIR or RPE (RPE = 10 − RIR, RIR 4+ shows as RPE ≤6). Stored as RIR either way; only the labels change (Today's week chip, the aim under the numbers, the optional set-effort row).
  - *Rest timer:* auto-start on (default) or off. Off leaves a **Start rest** button after Log set; the rest still counts from Log set. Rest-over alert: follow Sounds and Vibration (default), both, sound only, vibration only, or silent; it drives the in-app chime and buzz, the native alert and the web notification. Keep screen on (default on).
  - *Favourites:* a star in the exercise's How to sheet, or picked by muscle in Workout preferences. The generator weights a favourite 6× and prefers it over keeping last time's exercise when both fit; it still needs the gym's equipment, recovery and the day's muscles.
  - *Muscle priorities:* up to three. They aim for a third more weekly sets (`PRIORITY_VOLUME`), rank higher when recovered, and get leftover-time sets first. Recovery rules are unchanged, so a fatigued priority muscle still waits.
  - *Default workout length:* the Today slider goes back to it on the first open of each day (`minutesForToday`, `profile.minutesDay`); "Last used" keeps the old behaviour.
  - *Week starts on:* Monday (default) or Sunday, for streaks, freezes, quests, recaps, weekly stats and the web dashboard's calendars. `derive.ts` holds it as module state set from the profile (`setWeekStart`, `weekOf`, which replaced `mondayOf`). Training blocks keep their own 7-day weeks from `blockStart`.
  - *kg or lb:* Settings › Units is the display unit. Each gym also switches its plates between kg and lb (Gym › "This gym's plates are in"), which swaps the kit for a standard set in the new unit, because plates don't convert. When the gym's unit differs from the display unit, the workout shows the weight in both.
  - Per-exercise rest, reps and sets are also editable from the How to sheet during a workout; they apply from the next plan.
- **Supersets** (table stakes, Melvin, 2026-11-09; `src/lib/superset.ts`). A chain button between two exercises links them, on Today's plan and in the workout's "Coming up" list; tapping it again splits them, and three or more can be chained. Linked exercises share `PlanItem.group` and alternate: one set of each with a 15 s switch (`SWITCH_REST`), then the longest of their rests before the next round; when one runs out of sets the other carries on with its own rest. Warm-ups run the first time each exercise comes up. Plan length counts one rest per round, so linking shortens the estimate. Each set event records its `superset`, so "Same as last time" brings the pairing back. Links made on Today survive a rebuild of the plan (length, call) while both exercises are still neighbours, and so does splitting a pair the plan linked itself (a routine or "Same as last time"): the store keeps `a>b` for a link and `!a>b` for a split (`applyLinks`). **Pairing has to show** (Melvin, 2026-11-09: "the pairing of supersets doesn't do anything"; the link worked underneath but was easy to miss): on Today the link button sits on the line between the two exercises it joins (filled blue when linked), linked rows share a tint, a dashed join and one accent bracket down the left, each says "Superset A · 1 of 2", and the hint under the list says they alternate and how many minutes it saves. During the workout the superset chip has a "Then <exercise>" line naming where the next set goes. **While a workout runs, Today's list is read-only** (Melvin, 2026-11-11: the link buttons there "do nothing"): it shows the live workout, links included, with no link or move buttons, and the hint under it says to use Coming up on the workout screen. Before, Today kept showing the plan the workout started from while its buttons changed the live workout by position, so nothing visible happened and a different pair could be linked. Coming up is the one place to link or reorder mid-workout. The generator never pairs exercises by itself yet. Pure web code, so Android, iOS and the web get it together.
- **Saved routines** (table stakes, Melvin, 2026-11-09; `src/lib/routines.ts`, `Routines.tsx`). The lifter's own list of exercises, set counts and supersets, used instead of the adaptive plan for a day. Today's **Routines** chip opens the list: Use today (the chip then shows the routine's name, and "Back to today's adaptive plan" undoes it), edit, delete, **Save today's plan as a routine**, or **Build a new routine** from the exercise library (search by name or muscle; what the gym can do comes first). The summary has **Save as a routine**, which takes what was actually done, swaps and supersets included. Weights and reps still come from progression and warm-ups from `warmup.ts`, so a routine keeps moving forward; exercises the gym can't do are left out for that day. Custom exercises can go in a routine (the lifter chose them, unlike the generator). Routines live on the profile (`profile.routines`, newest first, at most 50 of 20 exercises each), so they're in the backup and will sync with the profile; `sessionStart.routine` records which one a workout came from. Free, like the logger. The length slider doesn't change a routine. When the programs work (`Profile.planSource`) lands, a routine becomes `{ kind: "routine", id }` there. Pure web code, so Android, iOS and the web get it together.
- **Notes, set effort and custom exercises** (table stakes, Melvin, 2026-11-09). Each is its own event (`note`, `effort`, `customExercise`), so it syncs and exports like everything else.
  - *Notes:* written in the exercise's info sheet (500 characters at most). The latest note on an exercise shows under its name every time it comes up, in any workout.
  - *Set effort:* during rest, an optional "Reps left in the tank on that set?" row (0 to 4+) for the set just logged; it never adds a tap during a set and disappears once answered. In `progression.ts` (`effortSignal`), sets that had 2+ more reps left than planned count like "too easy", and sets closer to failure than planned count like "too hard". Explicit post-exercise feedback wins when both exist.
  - *Custom exercises:* "+ Add your own exercise" at the bottom of the swap sheet (name, main muscle, equipment, whether it's a big lift), then it's used straight away. They're registered into the library on load (`registerCustom` in `exercises.ts`), get starting weights, progression, recovery and stats like any other lift, but **the generator never plans them**, because we can't know their movement well enough to programme them.
- **One exercise browser** (Melvin, 2026-11-11: "maybe we need some kind of search or organization or both", with the library at 300). `ExerciseBrowser.tsx` over `searchExercises` (`src/lib/exerciseSearch.ts`): an optional search box (every word must match the name in the app's language or English, a muscle or the equipment, accents ignored), main-muscle chips plus a **Cardio** chip, and an **Only what this gym has** switch (on by default), with a live count. Names that start with what was typed come first, then A to Z. It's the one picker everywhere: adding to a routine, the swap sheet (under the best matches, "Browse every exercise", starting on the exercise's main muscle), Workout preferences' favourites and per-exercise settings (list hidden until a chip or a word narrows it), and **Add an exercise** under the workout (a sheet; the pick goes on the end, cardio as one set, three sets otherwise, with its own warm-ups, and the workout moves to it when everything else is done; `store.addExercise`). Swaps keep cardio with cardio and strength with strength. Pure web code, so Android, iOS and the web get it together.
- **Cardio sets** (competitor gaps, Melvin, 2026-11-11). For a cardio exercise the set card shows **Time** (min:sec, ±1 minute) instead of reps, and for distance work a **Distance** stepper too (km with kg, miles with lb; ±0.1, or ±10 m for a sled; `src/lib/cardio.ts`, `store.adjustDistance`). One tap logs it as planned, like any set; the set saves `distanceM`. The sets CSV has a **Distance km** column. Cardio gets no warm-ups and no bonus sets. Pure web code, so Android, iOS and the web get it together. Strong and Hevy imports still skip their distance rows (a later change).
- **Set types: drop sets, rest-pause and failure** (competitor gaps, Melvin, 2026-11-11: "do 1, 2, 3, 4"). During rest, an optional "Add a bonus set?" row offers **Drop set** (about 75% of the set just logged, rounded to what the gym has, at the plan's reps, no rest) and **Rest-pause** (same weight after a 15 s pause, about a third of the reps). Bodyweight exercises and timed holds get Rest-pause only, and neither shows during a set. Tapping one takes the lifter back to the exercise just logged, even when the plan had moved on to the next one; the set card says which kind it is, with **Skip the bonus set** to go back to where they were (`store.extraSet`). The set is logged with `tag: "drop" | "restPause"` on its `set` event. It counts in volume and stats, but not toward the plan's set count (`setsDone`, the set label and the notification's progress), and `progression.ts` `sessionsOf` leaves it out, so progression, ghost mode, "same as last time" and plateaus read only the planned sets. Fixed programs (`programSessions`) skip them too, and readiness, the fatigue note, quests and achievements judge hit or missed reps on planned sets only (`gradedSet`, which also leaves out cardio, whose target is just last time's; bug audit, 2026-11-11). **Failure** is the reps-left rating of 0 (RPE 10), and the rating row now says so. The sets CSV has a **Type** column (`drop`, `rest-pause`, `failure`), and the import reads it back, as well as Strong's `D` set order and Hevy's `dropset` set type. Glossary term `setTypes`. Pure web code, so Android, iOS and the web get it together.
