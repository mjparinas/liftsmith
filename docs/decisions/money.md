# Money

Part of the decision record. [AGENTS.md](../../AGENTS.md) has the rules that apply to every change and the list of topics. Record decisions about this topic here, in the same change as the code.

- **No ads, ever** (Melvin, 2026-11-09). No ad SDKs, sponsored placements, interstitials or rewarded videos, in either app or on the site. The subscription is the only revenue.
- **Prices (confirmed by Melvin, 2026-11-09):** Pro is $6.99 a month or $39.99 a year. The annual plan is pushed as "about $3.33 a month, less than half of Fitbod". **No lifetime plan.** (Lifetime Pro *codes* exist as free comps from us, never sold: [Marketing and growth](marketing-and-growth.md), 2026-11-11.)
- **Trial (Melvin, 2026-11-09, revenue forecast; replaces the earlier 7-day trial on the annual plan):** every new user sees a **14-day Pro trial offer as the last step of setup**, annual plan first, then monthly, then "Not now, keep the free plan". Anyone who declines keeps the free logger and 5x5. The offer isn't shown again on "Run setup again". The length comes from the `trialDays` flag (`src/lib/flags.ts`, 7 or 14) so it can be A/B tested. Why: about 82% of trials start on install day, and trials of 17+ days convert at 42.5% against 25.5% for 4 days or fewer (RevenueCat data; forecast doc https://claude.ai/artifact/CiXkRo29nsLCuTzKYkQfx7). The offer's buttons start the store's own trial (`Plans` in `Pro.tsx`), and the choice is also recorded on the profile (`profile.pro`, `trial.ts`). **Until billing is live the offer step is hidden** (`billingLive()` in `src/lib/billing.ts`; Melvin, 2026-11-09), because Play and App Store review reject a priced offer with nothing to buy behind it; setup then ends on the notifications step. Neither plan is pre-selected: each is its own button.
- **Free tier:** the workout logger, plate graphic, rest timer and live notification, "why this weight", remix links, what to buy next and machine settings, plus **every fixed program** (Melvin, 2026-11-09: classic 5×5, novice 3×5, 5×5 plus arms, ramping 5×5, tiered progression, training max waves, bodyweight skills; built, see "Programs"). **Pro:** adaptive programming (generator, progression, RIR blocks and deloads), the **adaptive splits** (push/pull/legs, upper/lower; Melvin, 2026-11-09), the recovery map, advanced stats, health signals (sleep, HRV, resting HR, breathing rate) moving today's call (`healthReadiness`; seeing the health twin is free, Melvin, 2026-11-09), changing the plan mid-workout, the plateau detective and the goal-date planner. The split gate is `adaptiveSplits` in `entitlements.ts`.
- **Family sharing on the annual plan only** (Melvin, 2026-11-09), through Google Play's and the App Store's own family sharing; the monthly plan stays individual. Turn it on for the annual product in both store consoles when billing lands, and make the entitlement check accept a family-shared purchase on both platforms.
- **Billing is native, through RevenueCat** (Melvin chose it over wiring Play Billing and StoreKit directly, 2026-11-09). `@revenuecat/purchases-capacitor` sits on top of Google Play Billing and StoreKit, so the store's own sheet takes the payment, which is what both stores require. RevenueCat checks receipts, tracks renewals, grace periods, refunds and family sharing, and sends one webhook for both stores. It's free up to $2.5k a month in revenue, then 1%. Leaving it later is possible, because the stores own the subscriptions. Code: `src/lib/billing.ts` (SDK, entitlement, offers, buy, restore, manage), `src/components/app/Pro.tsx` (the paywall `#/pro` and the `Plans` buttons reused by setup), and Settings › Liftsmith Pro.
  - *Products:* Play has one subscription `pro` with base plans `monthly` and `annual`, each with a 14-day free-trial offer. The App Store has a subscription group "Pro" with `pro_monthly` and `pro_annual`, each with a 14-day free introductory offer. RevenueCat has an entitlement `pro` on all four and a current offering with `$rc_monthly` and `$rc_annual` packages. The `trialDays` flag at 7 picks an offering named `trial7` when one exists, so the A/B test needs a second set of 7-day offers there. Prices and trial lengths shown are the store's own (`priceString`, the intro price); iOS checks trial eligibility, and Android only offers a trial to people who can still get one.
  - *Live only when built with a key:* `NEXT_PUBLIC_REVENUECAT_ANDROID_KEY` and `NEXT_PUBLIC_REVENUECAT_IOS_KEY` (public SDK keys, from the `REVENUECAT_ANDROID_KEY` and `REVENUECAT_IOS_KEY` secrets in `release.yml`). Without a key (CI, the web app, tests) billing is off: everyone has Pro and no price is shown anywhere in the app, setup included. The release build stops if a key has the wrong prefix (Android `goog_`, the Play Store app's public key; iOS `appl_`), because a wrong key (a secret `sk_` or Test Store `test_` key) builds fine but every store call then fails with "Invalid API Key" (2026-11-10, the first Android test build).
  - *Entitlement:* `isPro()` is `hasPro()`: Pro while billing isn't live, otherwise the store's `pro` entitlement. The last answer is cached in localStorage, so Pro works offline and the first paint is right, with 3 days of grace past the last expiry seen (`OFFLINE_GRACE_MS`). The RevenueCat user id is the analytics install id (random, not an advertising id), so webhook rows join the install. A reinstall or "Erase this device" makes a new id; Restore purchases brings Pro back from the store account. Entitlements move to Liftsmith accounts when sign-in lands (the server's `entitlements` table is ready for it).
  - *Without Pro:* Today follows the free classic 5×5 (`store.applyAccess`, which keeps the lifter's own plan in `profile.proPlan` and restores it when Pro arrives), the recovery map shows a locked state, and Pro programs, splits and coaching tools open the paywall. Fixed programs, routines and the logger stay free.
  - *Shown, never hidden* (Melvin, 2026-11-10: "pro features are not hidden but have a small pro tag on it… we want to let people know what they are missing"). Every Pro entry point stays on screen for free lifters with the shared **`ProTag`** (`ui.tsx`, the small amber "Pro" pill) and opens the paywall at that feature (`#/pro/<from>`) instead of doing nothing or disappearing. The screen reader name says "…, a Pro feature: see Pro" (`pro.locked`). Today: an "Adaptive workouts · Pro" chip beside the free program (`today`). Programs: the adaptive plan and the splits (`programs`, `splits`). Recovery: the locked map (`recovery`). Health twin: "Make today an easy day" and "See Pro" when Pro would call the day differently (`twin`). Workout: the change-the-plan button (`replan`) and Count reps (`count`, PR #169). Progress: the goal planner section (`goals`) and, on a single stalled lift, coach's note button "Find the cause" (`plateau`). The web dashboard's advanced stats already show a locked panel. No Pro tag ever adds a tap during a set: the buttons were already there for Pro lifters.
  - *The paywall says exactly what's gated.* "What Pro unlocks" lists one row per feature in `PRO_FEATURES` (`entitlements.ts`) with a line on what it does (`pro.ft.<feature>`, `pro.fb.<feature>`), so a new Pro feature can't be left off (`Pro.test.tsx`). The feature the lifter tapped is moved to the top and marked "You tapped this" (`proFrom` maps the route argument to the feature and the screen behind it). Under the list, one line says what stays free. Setup's trial step shows the same list as titles only.
  - *Paywall rules:* annual first, neither plan pre-selected (each is its own button), the trial length and the price after it in the button, the store's renewal and cancellation terms, Restore purchases, Terms of use (Apple's standard EULA on iOS) and the privacy policy, and Manage subscription opening the store's own page. No countdowns or fake discounts.
  - *Thank-you after buying* (Melvin, 2026-11-10: "when you subscribe and it's successful, there should be confetti, haptic feedback and a congratulations for subscribing and taking your health seriously"): a purchase or trial start that unlocks Pro, from the paywall or setup's last step, runs `celebratePro` (`ProWelcome.tsx`): big confetti, the `celebrate` haptic and the fanfare, then a sheet that thanks the lifter for subscribing and taking their health seriously, lists what Pro unlocked (`ProFeatures`), and for a trial says how many days are free and that it can be cancelled in the store. "Let's train" goes to Today. Restore purchases, a cancelled or failed purchase get none of it. Confetti and the sound follow Lean mode and reduce motion, the buzz follows Settings › Vibration; the sheet always shows. It's rendered by `App.tsx` over every screen (setup included), because a purchase moves on straight away. Web code, so Android and iOS get it together (haptics through `@capacitor/haptics` on both); on the web app it shows when the lifter comes back from Stripe Checkout and the account has Pro (`#/pro/paid`). Text: `pro.welcome.*`.
- **Pro on the web, through Stripe** (Melvin, 2026-11-11, from the features brainstorm: "gate Pro on the web app with Stripe subscriptions, sharing entitlement with RevenueCat/Play purchases and creator/lifetime codes"). Code: `src/server/stripe.ts` (Stripe's REST API through `fetch`: no SDK and no Stripe.js, so no outside script on the site), routes under `src/app/api/billing/stripe/` (GET plans, POST checkout, `portal/`, `webhook/`), `src/server/access.ts`, and the web half of `src/lib/billing.ts`.
  - *Same plans, same prices:* one product with a monthly and an annual recurring price in USD, the same $6.99 and $39.99. The paywall shows Stripe's own price in the app's language (`money()`), annual first with "about $3.33 a month", neither pre-selected, the trial and the price after it on the button, "Paid by card through Stripe" terms, our terms of use and privacy links, the same rules as the stores'.
  - *Needs an account.* A web subscription belongs to the Liftsmith account, never to a browser, so it survives cleared site data and unlocks the phones too. Signed out, the paywall shows the plans with a "Sign in or create an account" card, and a plan button says to sign in first. Stripe gets the account's email, account id, install id and code as metadata, nothing else.
  - *Checkout and manage:* a plan button asks the server for a Stripe Checkout page (`checkoutUrl`) and the browser goes there; Stripe returns to `/app/#/pro/paid` (or `#/pro/settings` when cancelled), always our own `SITE_URL`, never an address from the request. `#/pro/paid` waits up to about 12 seconds for the webhook to reach the account, then runs the thank-you (`celebratePro`). Manage subscription opens Stripe's customer portal (plan change, card, cancel, invoices). "Restore purchases" on the web is "Already subscribed? Check again": it asks the account.
  - *Trials:* the trialDays A/B (7 or 14), or a live creator or promo code's own trial (30 days) first, set as the subscription's trial; none for an account that already had a web subscription or a store subscription on a linked phone (`trialEligible`), so nobody gets the trial twice by switching platforms. A card is taken at checkout, as in the stores. Promo codes that give a discount offering in the stores give no discount on the web yet (Stripe coupons can come later); their trial days still apply.
  - *One Pro, any platform (`access.ts` `accessFor`):* the account has Pro from, in order, the store review account, a lifetime code (`pro_grants`), a web subscription (`stripe_subscriptions` in trialing, active or past_due, and not more than 3 days past its period end, like the apps' offline grace), or a Play or App Store subscription on a phone linked to the account. A phone is linked when it syncs while signed in (the sync request carries its install id, which is RevenueCat's user id; `account_installs`), so its `entitlements` row from the RevenueCat webhook counts on the web. Sync and `GET /api/account/` send `pro`, `proVia` and `sub`; `hasPro()` adds the account's Pro on every platform. So a web subscriber who signs in on Android or iPhone has Pro there, and a Play subscriber who signs in on the web has Pro there.
  - *No paying twice:* checkout answers 409 when the account already has Pro from anywhere, and the paywall says so. On a phone, Pro from the account shows where it comes from as plain text ("from a subscription on the Liftsmith website… manage or cancel it there"), with **no link or price** to the website, because Google Play's and Apple's rules don't allow pointing in-app buyers to another way to pay (Platform deltas). On the web, a store subscription says to manage it in that store.
  - *Setup's offer step stays native-only.* The web app's setup ends without the trial offer (it would need a sign-in in the middle of setup); the Pro tags and the paywall sell it there.
  - *The webhook* (`storeStripeEvent`, signature checked with the endpoint secret in constant time within 5 minutes) keeps each subscription's status, plan, period end, trial end and cancel-at-period-end, newest event wins. Live events also write `subscription_events` with store `web` and source `store` (Stripe signed them, so they count for creator commission like the stores' webhook): `trial_start`, `purchase` or `trial_convert` on the first paid invoice, `renew`, `cancel`, `uncancel`, `expire` (reason `billing` when the card failed), `refund`. USD amounts fill `usd_micros`; other currencies keep their own amount only. The creator code from the metadata is claimed for the install (`claimFromStore`), and a new paying customer emails the admins like the stores do. Test-mode events are ignored by a live key and the other way round.
  - *Deleting the account cancels its web subscription in Stripe straight away* (`forgetStripe`) and removes the link rows; the in-app delete confirmation says so when there is one. A store subscription isn't touched (it's the store's).
  - *Off until set up:* with any of `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_MONTHLY` and `STRIPE_PRICE_ANNUAL` missing, `GET /api/billing/stripe/` says `live: false` and the web app stays fully unlocked, as before. The answer is cached in localStorage so the first paint and offline use are right. The static export (CI, browser tests) has no server, so it never asks.
  - Pure web code for the selling, and the account flag reaches Android and iOS through the shared web layer, so no native code changed.
