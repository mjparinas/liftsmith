# Connected apps (Melvin asked, 2026-11-10: "an integrations page in settings… Health Connect and whatever else we can or will support… Strava and whatever else is in the plan, build it all")

Part of the decision record. [AGENTS.md](../../AGENTS.md) has the rules that apply to every change and the list of topics. Record decisions about this topic here, in the same change as the code. The order things were planned in is in [Integrations roadmap](integrations-roadmap.md).

## The page

- **Settings › Connected apps** (`#/connections`, `Connections.tsx`). Settings has one row that opens it (the Settings restructure keeps that one row in its main list). It's the one place to check, sync and fix every integration. Sections, top to bottom:
  1. **Health Connect** (Android) / **Apple Health** (iOS): connected or not, last synced (`ls.health.last`, written by each import), **Sync now** (runs both imports and says how many new readings came in), and what's allowed. Android lists every read and write with a tick (`healthPermissions`, from the plugin's `checkAuthorization`) and **Change permissions** opens Health Connect's own screen (or its install page when it's missing). Apple Health never tells an app which reads were allowed, so iOS says so and explains where to change it (Health app › Apps › Liftsmith); "connected" there means a sync has run or a write was allowed. A line names what reaches us through the health store: smart scales, the Hume Body Pod, Oura, Samsung Health, Garmin, Fitbit and most watches. The web app says Health is in the phone apps.
  2. **Heart rate monitor:** what it does, the last monitor used on this device (`ls.hr.last`, saved by `connectHeartRate`), and **Test my monitor**, which connects and shows live bpm so a strap can be checked before the gym. The workout screen's heart button is still where it's paired for a workout. Browsers without Web Bluetooth get a line saying so.
  3. **Fitness services: Strava, Oura, WHOOP.** They need an account (the roadmap's "connecting one explains that it creates a free account"), so a signed-out lifter sees what each does and one **Sign in or create an account** button. Signed in, each row shows connected (Strava shows the athlete's name), not connected, or **Coming soon** when the server has no keys for it yet, with Connect or Disconnect.
  4. **Garmin watch** (2026-11-10): each Garmin watch the phone knows, and whether it's ready, needs the Liftsmith watch app, or isn't connected; **Choose my watch** on iOS (Garmin Connect's picker). Details in [Watch apps](watch-apps.md).
  5. **Music:** None, Spotify, Apple Music or YouTube Music (`profile.connections.music`, synced with the profile).
  6. **Coming later**, in order: Samsung Health directly, bar speed sensors. (The Garmin watch app moved out of this list on 2026-11-10.)

## Workouts saved to Health Connect and Apple Health (2026-11-10)

- The health plugin can only write samples, so finished workouts used to arrive as loose calories and heart rate. Our own small plugin now writes each one as a real workout: **`HealthWorkoutPlugin.kt`** (Android, the app module's first Kotlin file, because Health Connect's client is Kotlin-first; it asks only for `WRITE_EXERCISE` and writes a strength training `ExerciseSessionRecord` whose client record id is the workout id, so a second write updates it) and **`HealthWorkoutPlugin.swift`** (iOS, `HKWorkoutBuilder` with a traditional strength training workout, `HKMetadataKeyExternalUUID` set to the workout id and skipped if it's already there). Both are called `HealthWorkout` (`status`, `request`, `save`) from `saveWorkout` in `health.ts`.
- Title and notes are the same as Strava's (`stravaWorkout`): "Strength training" and the sets, one line per exercise. iOS has no notes field, so only the title goes in (as the brand name).
- **Calories and heart rate:** on iOS they go inside the workout (so the Move ring counts them once, and the plugin's separate samples are skipped); on Android they stay separate records over the same time, which is how Health Connect apps link them. Without the workout permission, both platforms write the samples as before.
- The permission is asked for right after the health plugin's sheet when Health is connected (`connectHealth`), and Connected apps shows "Workouts (written)" with a **Save my workouts to …** button for lifters who connected before this existed.
- Play: `WRITE_EXERCISE` must be added to the Health Connect declaration in Play Console (docs/PRIVACY_LABELS.md). The privacy policy and `public/privacypolicy.html` say workouts are saved with their time, title and sets.

## Strava, Oura and WHOOP: the server

- **Routes** (server build only): `GET /api/connect/` (which services have keys, which this account connected), `POST /api/connect/<service>/` (a one-time sign-in link), `DELETE /api/connect/<service>/` (disconnect), `GET /api/connect/<service>/callback/` (the service sends the lifter back), `GET /api/connect/<oura|whoop>/daily/?days=45&tz=…` (readings), `POST /api/connect/strava/upload/` (one workout). All but the callback need the account's Bearer token. Code: `src/server/connect.ts`; shared types `src/lib/cloud.ts`; app side `src/lib/connections.ts`.
- **Sign-in flow:** the app asks for a link while signed in; the server stores a random one-time state (15 minutes, `connect_states`) with the account and platform and returns the service's authorize URL. The app opens it (`openOutside`: on Android and iOS a navigation to another site goes to the browser). The callback uses up the state, swaps the code for tokens and stores them. The website goes straight back to `/app/#/connections/<service>`; the phone apps get a small page with **Back to Liftsmith** (`liftsmith://connected`, a link both apps already open, ignored by the shortcut handlers), and the page refreshes its status when the app comes to the front. No native code was needed.
- **Tokens** live in `connections`, one row per account and service, **encrypted** with AES-256-GCM under a key made from that service's client secret, so a copy of the database alone can't use them (changing a secret means lifters connect again). They refresh 2 minutes before they run out (Whoop asks for `offline` again on refresh). **Disconnect** revokes at the service (Strava deauthorize, Oura revoke, WHOOP's user access delete) and deletes the row; **deleting the account** does the same for every service (`forgetAll` in `deleteAccount`).
- **Scopes:** Strava `activity:write,read`; Oura `daily heartrate`; WHOOP `offline read:recovery read:sleep`. Nothing more, so the consent pages ask for little.
- **Strava gets finished workouts.** When a workout ends (`Workout.tsx` → `queueStrava`), the app builds the activity from the events (`stravaWorkout`: "Strength training", `WeightTraining`, start as local clock time, elapsed time, and the sets, one line per exercise, from the language catalogue) and puts it in an outbox in localStorage, so a workout finished offline posts later (on open, return to the front, or back online). The server records each posted session (`connect_uploads`), so a retry never posts twice. A switch on the Strava row turns posting off (`profile.connections.stravaPost`, missing means on). A 409 (Strava removed the access) empties the outbox and refreshes the status.
- **Oura and WHOOP send readings in.** The app asks at most every 3 hours (and on Sync now) for the last 45 days; the server fetches them and maps them to the health twin's metrics without storing them: Oura's sleep periods (the night's total sleep; the main sleep's average HRV, lowest heart rate as resting heart rate, and breathing rate) and finished days' steps; WHOOP's scored sleeps (in bed minus awake, the night's breathing rate) and recoveries (HRV RMSSD, resting heart rate), each on the local day the night ended (WHOOP's own time zone offset, or the phone's). The app stores them as `health` events with ids `oura-…`/`whoop-…` (`importCloudReadings`), so the health twin and the readiness call use them like Health's, re-imports add nothing, and they sync with the lifter's account like every other health reading.
- **Without keys a service shows "Coming soon"** and its routes answer 503, so the page can ship before each developer app is approved. Each service also caps a new app at a few users until it's reviewed (Strava, Oura and WHOOP each list 10 or so); apply early (roadmap item 4).

## Music

- Curated **public** playlists for the day's call (Melvin, 2026-11-09; no Spotify API). Today shows one chip, "Play push day / training / easy day music", next to the gym and week chips, only when a music app is picked and no workout is running. Spotify opens a fixed editorial playlist (Beast Mode for push, Power Workout for normal, Mood Booster for easy; checked by hand on 2026-11-10); Apple Music and YouTube Music open their search for the same kind of playlist, because their playlist links vary by country. Change the picks in `PLAYLISTS` in `connections.ts`.

## Keys Melvin creates (set in Vercel, Production and Preview)

- **Strava:** https://www.strava.com/settings/api → create an app (category Training, website https://www.getliftsmith.com, **Authorization Callback Domain `www.getliftsmith.com`**) → `STRAVA_CLIENT_ID`, `STRAVA_CLIENT_SECRET`. Then ask Strava for more athletes than the starting limit.
- **Oura:** https://cloud.ouraring.com/oauth/applications → new application, redirect URI `https://www.getliftsmith.com/api/connect/oura/callback/`, scopes daily and heartrate → `OURA_CLIENT_ID`, `OURA_CLIENT_SECRET`. Oura's terms need written consent to use their data in a paid feature (readiness auto-adjust is Pro).
- **WHOOP:** https://developer-dashboard.whoop.com → create a team and an app, redirect URL `https://www.getliftsmith.com/api/connect/whoop/callback/`, scopes read:recovery, read:sleep and offline → `WHOOP_CLIENT_ID`, `WHOOP_CLIENT_SECRET`.
