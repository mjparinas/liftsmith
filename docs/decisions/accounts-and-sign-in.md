# Accounts and sign-in (built, 2026-11-09; Melvin chose to build them after "it's not clear how to save my information" on mobile web)

Part of the decision record. [AGENTS.md](../../AGENTS.md) has the rules that apply to every change and the list of topics. Record decisions about this topic here, in the same change as the code.

- **Accounts are optional.** The app works fully offline with no account; signing in turns on backup and sync. Everything stays on the device either way: signing out keeps the device's data and only stops syncing.
- **Where:** Settings' first row, **Account and sync** (`#/account`, `Account.tsx`), and "Already use Liftsmith? Sign in" on setup's first step (a sheet with the same `AccountPanel`). Signing in on a new device during setup pulls the account's profile, which ends setup.
- **Methods:** Sign in with Google, Sign in with Apple, and a six-digit code emailed through Resend (works everywhere, so nobody is stuck). Per platform (Platform deltas): Android has Google and email; iOS has Apple, Google and email (Apple requires Sign in with Apple whenever Google is offered, so they ship together); the web has Google, Apple and email. A Google or Apple button shows only when the build has its public client id (`AUTH` in `src/lib/auth.ts`, from `NEXT_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `NEXT_PUBLIC_GOOGLE_IOS_CLIENT_ID`, `NEXT_PUBLIC_APPLE_SERVICES_ID`; client ids aren't secrets, so they can be committed once created). Apple on iOS needs no id.
- **Native code is ours, not a social-login plugin** (`AccountSignIn`: `AccountSignInPlugin.java`, `AccountSignInPlugin.swift`). The common Capacitor social-login plugin links the Facebook SDK on iOS through Swift Package Manager whether or not it's used, which doesn't fit "no tracking SDKs". Android uses Credential Manager's Sign in with Google sheet (`androidx.credentials`, `googleid`); iOS uses `ASAuthorizationController` for Apple and Google's OAuth code flow with PKCE in an `ASWebAuthenticationSession` (iOS client id, no Google SDK). The web loads Google Identity Services and Sign in with Apple JS only on the account screen. iOS has the `com.apple.developer.applesignin` entitlement.
- **Tokens:** every method ends with the provider's ID token (or the emailed code) checked on the server (`src/server/idToken.ts`): RS256 signature against Google's or Apple's published keys, issuer, audience (our client ids, `GOOGLE_CLIENT_IDS` / `APPLE_CLIENT_IDS` plus the public ones and the bundle id), expiry, and a nonce (the app makes a random value, gives the provider its SHA-256, and sends the raw value to the server). Identities with the same **verified** email join one account. The server returns a random session token (365 days, sliding); only its SHA-256 is stored, and the device keeps it in localStorage (`liftsmith.account`), sent as a Bearer header (no cookies, so the native shells work cross-origin).
- **Email codes:** 10 minutes, one use, 5 wrong tries, 5 codes a day per address, plus per-address-IP rate limits on every route. The answer is the same whether or not the address has an account.
- **Delete my account** (`DELETE /api/account/`) deletes the account, its identities, sessions and the whole synced copy at once (App Store 5.1.1(v), Play's account deletion rule; the web link for Play's form is `https://www.getliftsmith.com/app/#/account`). With `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY` set, Apple sign-ins swap their authorization code for a refresh token at sign-in and deleting revokes it, as Apple requires. "Erase this device" signs the device out and leaves the account.
- **Not yet:** Pro on the account (entitlements stay per install; the server's `entitlements` table can join accounts later), friends and a shared feed, and moving the email reminder subscription onto the account (`account_id` is ready).
