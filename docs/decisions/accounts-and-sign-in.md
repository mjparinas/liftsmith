# Accounts and sign-in (built, 2026-11-09; Melvin chose to build them after "it's not clear how to save my information" on mobile web)

Part of the decision record. [AGENTS.md](../../AGENTS.md) has the rules that apply to every change and the list of topics. Record decisions about this topic here, in the same change as the code.

- **Accounts are optional.** The app works fully offline with no account; signing in turns on backup and sync. Everything stays on the device either way: signing out keeps the device's data and only stops syncing.
- **Where:** Settings' first row, **Account and sync** (`#/account`, `Account.tsx`), "I already have an account" on the welcome screen before setup (a sheet with the same `AccountPanel`), and a muted **Sign in** link beside Start free in the website header (`SignInLink`, to `/app/#/account`). Signing in on a new device during setup pulls the account's profile, which ends setup and opens Today; an empty account carries on into setup (details in [Setup wizard](setup-wizard.md)). Signing in on the Account screen when it was opened from outside the app (that link, on a browser already set up) also goes on to Today. From the website link on a new browser, the welcome sheet points the app at Today the moment sign-in succeeds, before the first sync (2026-11-11): the sync brings the set-up profile back and the app replaces the welcome screen before the sync finishes, so waiting for it left the lifter on Settings › Account.
- **Signing in pushes everything already on the device** (fixed 2026-11-11). The outbox only fills while signed in, and sign-in used to start it empty, so workouts logged before signing in on a device never reached the account and the lifter's other devices never saw them. Now the first sync after a sign-in queues every event on the device once (`seeded` in `SyncState`, `seedOutbox` in `syncOutbox.ts`); a device signed in on an older version has no `seeded` and pushes its whole history once on its next sync. The server ignores ids it already has, so repeats cost nothing.
- **A profile that hasn't finished setup never syncs** (2026-11-11). The device doesn't send it (`localRecords`), the server doesn't store one from older app versions (`src/server/sync.ts`), and an account profile without `onboarded` never replaces a set-up one on a device (`mergeRecords`). Otherwise signing in on a new install's welcome screen could put a half-made profile on an account that had none yet, and send the lifter's other devices back to setup. The other way round, a device that hasn't finished setup always takes the account's set-up profile, even when its own is newer: a browser that signed in under an older version and then answered setup questions would otherwise stay in setup for good.
- **Methods:** Sign in with Google, Sign in with Apple, and a six-digit code emailed through Resend (works everywhere, so nobody is stuck). Per platform (Platform deltas): Android has Google and email; iOS has Apple, Google and email (Apple requires Sign in with Apple whenever Google is offered, so they ship together); the web has Google, Apple and email. A Google or Apple button shows only when the build has its public client id (`AUTH` in `src/lib/auth.ts`, from `NEXT_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `NEXT_PUBLIC_GOOGLE_IOS_CLIENT_ID`, `NEXT_PUBLIC_APPLE_SERVICES_ID`; client ids aren't secrets, so the defaults are committed in `src/lib/authIds.ts`, and the server accepts them as audiences too). Apple on iOS needs no id.
- **Native code is ours, not a social-login plugin** (`AccountSignIn`: `AccountSignInPlugin.java`, `AccountSignInPlugin.swift`). The common Capacitor social-login plugin links the Facebook SDK on iOS through Swift Package Manager whether or not it's used, which doesn't fit "no tracking SDKs". Android uses Credential Manager's Sign in with Google sheet (`androidx.credentials`, `googleid`); iOS uses `ASAuthorizationController` for Apple and Google's OAuth code flow with PKCE in an `ASWebAuthenticationSession` (iOS client id, no Google SDK). The web loads Google Identity Services and Sign in with Apple JS only on the account screen. iOS has the `com.apple.developer.applesignin` entitlement.
- **Tokens:** every method ends with the provider's ID token (or the emailed code) checked on the server (`src/server/idToken.ts`): RS256 signature against Google's or Apple's published keys, issuer, audience (our client ids, `GOOGLE_CLIENT_IDS` / `APPLE_CLIENT_IDS` plus the public ones and the bundle id), expiry, and a nonce (the app makes a random value, gives the provider its SHA-256, and sends the raw value to the server). Identities with the same **verified** email join one account. The server returns a random session token (365 days, sliding); only its SHA-256 is stored, and the device keeps it in localStorage (`liftsmith.account`), sent as a Bearer header (no cookies, so the native shells work cross-origin).
- **Email codes:** 10 minutes, one use, 5 wrong tries, 5 codes a day per address, plus per-address-IP rate limits on every route. The answer is the same whether or not the address has an account.
- **Delete my account** (`DELETE /api/account/`) deletes the account, its identities, sessions and the whole synced copy at once (App Store 5.1.1(v), Play's account deletion rule; the web link for Play's form is `https://www.getliftsmith.com/delete-account/`). With `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY` set, Apple sign-ins swap their authorization code for a refresh token at sign-in and deleting revokes it, as Apple requires. "Erase this device" signs the device out and leaves the account.
- **Store review account** (2026-11-10; Play Console's "Sign in details" asks for reusable sign-in that doesn't expire, and its reviewers can't receive an emailed code, make accounts, or buy or trial Pro). The address `review@getliftsmith.com` signs in through the normal email screen with a **fixed 12 to 16 digit code** kept only in Vercel as `REVIEW_SIGNIN_CODE` (Production and Preview; never in the repo, chat or a GitHub secret), and that account **has Pro on the server without a purchase** (`src/server/review.ts`). "Email me a code" sends nothing for that address; the code is reusable and works on Android, iOS and the web alike (same web code, no native change). Safety: the code works for that one address only, is compared in constant time, and guesses are held by the verify route's per-address limit (30 an hour), against a trillion or more codes; there's deliberately no shared lockout on the address, since anyone could then lock reviewers out. Unset or shorter than 12 digits, the path is off and the address is like any other, Pro included. The account's Pro reaches the device in the sign-in reply and on every sync (`pro`), is kept on the saved account (`Account.pro`), and `hasPro` in `billing.ts` adds it to the store's answer; the Pro screen says "Pro comes with this account" (`pro.status.account`). The code box takes 6 digits, or 12 to 16. Rotate the code by changing the variable and the Play Console entry together; existing review sessions keep working until signed out. The same details go to App Review on iOS (App Store Connect › App Review Information).
- **Not yet:** Pro on the account for purchasers (entitlements stay per install; the server's `entitlements` table can join accounts later), friends and a shared feed, and moving the email reminder subscription onto the account (`account_id` is ready).
- **Delete-account page** (2026-11-10, for Play Console's Data safety "Delete account URL"): `https://www.getliftsmith.com/delete-account/` (`src/app/delete-account/page.tsx`, static, in the sitemap and the site footer, linked from /privacy/). It names Liftsmith, puts the steps first (Settings › Account and sync › Delete my account, the same in the web app, or an email to hello@getliftsmith.com from the account address, done within 30 days after confirming from that address), and lists what's deleted at once (account, identities, sessions, the synced copy, the Apple link) and what's kept: database backups overwritten within 30 days, each device's own copy (Erase this device), anonymous usage stats under the install id for up to 25 months, the reminder address until stopped, feedback until asked, and purchase records for as long as tax law requires (deleting doesn't cancel Pro). Play's optional "delete some data without deleting the account" is answered **Yes**: cycle logs (deleted locally and from the synced copy), email reminders and usage stats in Settings, and anything else by email. Keep the page in step with `deleteAccount` in `src/server/accounts.ts` and /privacy/.
